# The intermediate representation

One IR, target-independent, in SSA form, produced by lowering the typed AST and consumed by the optimizer and the code generator. Document 10's MIR is a second, target-dependent representation and is specified there.

## 8.1 Shape

A module contains functions, global variables, and aliases. A function contains basic blocks. A block has **parameters** and a list of instructions ending in exactly one terminator.

**A module holds what the file has a reason to emit.** A function with internal linkage that nothing in the translation unit refers to is not in it. Nothing outside the file can name it, so it is a definition of something that can never run, and C 6.9p3 requires a definition only for one that is used. What counts as referring to it is naming it: a call, an address taken, a mention in an initializer and an operand of an `asm` are all the same node in the typed tree, and the set is computed transitively from the roots rather than one level deep, because two `static` functions may call each other and neither be reachable. The roots are the functions with external linkage, the objects with static storage, and anything the attributes in document 13 section 13.4 ask to be kept. The reason this is not merely a size question is that a `static inline` in a system header reaches every file that includes it: `<endian.h>` defines three functions over the byte swap builtins, and emitting them turned a program that never asked for a byte swap into a program that did not build.

**Block parameters, not phi nodes.** Cranelift, Swift's SIL and MLIR all made this choice and it is the right one. A phi node is a pseudo-instruction whose operands are positionally tied to a predecessor list that lives somewhere else, and every phi-based IR accumulates bugs where the two get out of sync during CFG edits. Block parameters put the correspondence in the branch instruction, where it belongs: `br_if v3, block2(v1, v2), block3(v4)`. Removing a predecessor is a local edit. There is no such thing as a malformed phi.

The entry block has parameters corresponding to the function's arguments after ABI lowering has not yet happened, that is, in their C-level form. Document 10 rewrites them.

## 8.2 Types

The IR type system is deliberately much smaller than C's. Everything C-specific has been resolved by document 07 and must not be re-derived here.

```
i1 i8 i16 i32 i64 i128        integers, by width, signless
iN                            arbitrary width, for _BitInt
f16 f32 f64 f80 f128          floating point
ptr                           opaque pointer, no pointee type
i8x16 f32x4 ...               fixed vectors
mem                           the state of memory, at -O2 and above
void
```

Four decisions embedded there.

**Integers are signless.** There is no `u32` and `i32`; there is `i32`, and the *operation* carries the signedness: `sdiv` and `udiv`, `slt` and `ult`, `sext` and `zext`. This halves the type space and removes a large class of "the type says unsigned but the operation is signed" confusion. It is what LLVM does and it has been vindicated.

**Pointers are opaque.** A `ptr` has no pointee type. LLVM spent years migrating to this and the reasons are decisive: typed pointers force a stream of no-op `bitcast` instructions that carry no information, they make it tempting to derive aliasing conclusions from a pointer's static type when C's rules do not license that, and they make the IR larger. Type information that matters for aliasing lives in TBAA metadata on the memory operation, where document 07's effective-type rules can be applied precisely. The *size* of a memory access is a property of the `load` or `store`, not of the pointer.

**Memory is a value.** A `mem` is the state of memory at a point in the function, and it exists so that memory has def-use chains the way everything else does. Nothing computes with one: there are no operations on `mem`, no constant of that type, and the back end never sees one, because memory SSA is built at `-O2`, read by the passes that need it, and taken back off before instruction selection. A function at `-O0` or `-O1` has no `mem` in it at all, and that is not a degraded form, it is a function whose memory operations are ordered by the alias analysis being asked directly. Document 09 of `spec/optimizer` is the design and section 8.3 below says how an instruction carries one.

**Aggregates are not IR values.** Structs and arrays live in memory. There is no `struct` type in the IR and no instruction produces one. A struct assignment is a `memcpy`; a struct passed by value is lowered by document 12's ABI rules into registers or a memory copy at IR construction time. This keeps the optimizer from having to reason about aggregate values, which is where a great deal of complexity in LLVM's IR lives, and it costs nothing because C's aggregate semantics are memory semantics anyway.

## 8.3 Instructions

The set is small enough to enumerate and it is closed. Adding an instruction is a spec change, because every pass, the verifier, the printer, the parser and the lowering rules must handle it.

**Arithmetic.** `add sub mul` on integers and vectors; `sdiv udiv srem urem`; `and or xor shl lshr ashr`; `fadd fsub fmul fdiv frem fneg`; `fma`.

**Comparison.** `icmp <pred>` with the ten integer predicates; `fcmp <pred>` with the ordered and unordered predicates. Both produce `i1` or a vector of `i1`.

**Conversion.** `trunc sext zext`, `fptrunc fpext`, `fptosi fptoui sitofp uitofp`, `ptrtoint inttoptr`, `bitcast`.

**Memory.** `mem_entry`, `alloca`, `load`, `store`, `memcpy`, `memmove`, `memset`, `atomic_load`, `atomic_store`, `atomic_rmw`, `cmpxchg`, `fence`. Address arithmetic is `getelementptr`-free: pointer arithmetic is plain integer arithmetic on `ptr` via `ptr_add ptr, offset`, with the structure offset computed by the frontend. C does not need GEP's multi-index form and its absence removes a notorious complexity source.

**Memory on an instruction.** Where a function carries memory SSA, the version of memory an instruction reads is its last operand and the version it produces is its last result, and both are written in the textual form as `[mem %3]` at the end of the line. Last, in both cases, so that every other operand and every other result keeps the position it had, and a pass that reads the address of a load as its first operand goes on working whether or not memory has been threaded through it. `mem_entry` is where a chain starts: it takes nothing, produces the version of memory the function was called with, and there is one of them, at the top of the entry block. A memory phi is an ordinary parameter of a block, which is what block parameters were for. Nothing about memory SSA is a side table, and the CFG updates that keep it in step with the blocks are the ones every other value already needs.

Memory is all or nothing within one function. Either every instruction that touches memory is on the chain or none of them is, because a walk that reaches an instruction with no memory operand cannot tell whether that instruction was left off the chain by a pass or does not belong on it, and the verifier is where that is caught. Memory is also not something a function takes or returns: it stops at the call, and what a call does to it is what the callee's attributes in section 8.4 say.

**Control.** `jump block(args)`, `br_if cond, block(args), block(args)`, `switch value, default(args), [case => block(args)]`, `indirect_br addr, block(args), block(args)`, `return values`, `unreachable`. GNU's computed goto is the last of those with `block_addr block`, which is the address of a block and the one instruction that names a block without arriving at it. An `indirect_br` lists every block it can arrive at, so the edges of a computed goto are ordinary edges and nothing else in the compiler has to know that an address decided which one was taken.

**Calls.** `call callee(args)`, `call_indirect sig, ptr(args)`, `tail_call`. The signature carries the ABI-relevant attributes from document 12.

**Intrinsics.** A closed set: `ctlz cttz ctpop bswap bitreverse`, `sadd_overflow uadd_overflow smul_overflow` and friends, `expect`, `unreachable_hint`, `prefetch`, `frame_address return_address`, `va_start va_arg va_end va_copy`, `stacksave stackrestore` for VLAs, `setjmp`-family markers, and the target-specific intrinsic namespace for vector builtins.

**Inline assembly** is an instruction, `inline_asm`, carrying the template, the constraint list, the clobbers, and for `asm goto` a list of successor blocks, which makes it a terminator in that case. Document 11 owns its semantics.

The constraint list is one comma separated list in the numbering the template uses, the outputs first and then the inputs, so `%0` in the template is the first entry of the list and nothing has to be renumbered to read the instruction. What each entry does with the operands is a scan of that list in order: an output that names a register produces a result, and takes an argument as well when it is `+`; an output that names memory takes an argument, which is an address, and produces nothing; and an input takes an argument, which is a value unless the constraint names memory, in which case it is an address. The instruction therefore has as many results as there are register outputs and the arguments are in list order, and a reader that has the list can say which operand each result and each argument belongs to without being told again.

The successor list of an `asm goto` puts the fall-through block first and the labels after it in the order they were written, which is what makes the outputs of an `asm goto` well defined. A result of the instruction is only in scope in the blocks the instruction dominates, and writing the outputs into their objects in the fall-through block means the label edges arrive carrying the values those objects had before the assembly ran, which is what document 11 asks for.

## 8.4 Flags, attributes, and the absence of poison

Instructions carry flags. The set is small and every flag has a precise meaning tied to document 07's UB list.

`nsw` and `nuw` on integer arithmetic mean the optimizer may assume no signed or unsigned overflow. `-fwrapv` simply stops the frontend from setting `nsw`, which is the whole implementation of that flag. Fast-math flags `nnan ninf nsz arcp contract reassoc` sit on floating point instructions individually, so `-ffast-math` is a frontend decision and not a global mode, which keeps LTO across mixed units correct. `exact` on `lshr`/`ashr`/`sdiv`/`udiv`. `volatile` and an atomic ordering on memory operations. `align` and TBAA metadata on memory operations. A memory operation also carries a `restrict` clique and base, which are two small numbers naming the `restrict` scope the access is in and the pointer inside that scope it went through, and which are what document 08's fifth aliasing layer reads. `noalias` and `provenance` on pointer values.

Attributes sit on a function rather than on an instruction, and the difference is when they are read: a flag is read by the optimizer when it is about to rewrite the instruction carrying it, and an attribute is read when the optimizer is looking at a call and has no other way to find out what the callee does. `noreturn` is an attribute because the block after a call to `exit` is unreachable and the only way to know that is to ask about `exit`. The set is the one C sources actually produce: `nounwind noreturn returns_twice willreturn`, `cold hot`, `inline_hint always_inline noinline optnone`, `readnone readonly argmem_only` for what a call touches, and `naked used stack_protect no_stack_protector` for how the frame is built. `fp_contract` takes a value rather than being set or not, because it is the question the code generator asks after the per-instruction flags are gone and the two operations it might fuse have arrived from different expressions.

**There is no `poison` and no `undef`.** This follows from document 07's policy and is the largest deliberate divergence from LLVM's IR design in this document.

The LLVM model is that an `nsw add` that overflows produces `poison`, a value that taints everything it touches and licenses arbitrary behavior in any consumer. It is powerful and it is the source of a well-known family of miscompilations that are extraordinarily hard to debug, which is why LLVM eventually needed `freeze`.

Our model: `nsw` licenses *specific rewrites*, the ones our rule set proves sound under the assumption that overflow does not happen, and the value produced when overflow does happen is unspecified but stable, meaning two reads of the same value give the same result. Nothing is tainted transitively.

The cost is real and is not hidden: we lose some optimizations that depend on poison propagation, principally aggressive speculation of arithmetic across control flow. The benefit is that every rewrite is locally justifiable, which is what makes SMT verification of the rule set in document 09 tractable, and that a miscompilation cannot propagate from a place the user cannot see. Document 19 makes measuring this cost open question five.

An uninitialized `alloca` read yields a target-defined stable value, not poison, per the same policy.

## 8.5 SSA construction

We build SSA directly during lowering from the typed AST, using the algorithm of Braun, Buchwald, Hack, Leißa, Mallon and Zwinkau, "Simple and Efficient Construction of Static Single Assignment Form" (CC 2013). Local variables become `alloca`s only when their address is taken; everything else is placed in SSA on the fly by the algorithm's `readVariable`/`writeVariable` with incomplete-block handling for loops.

This matters for axis 3. The classical alternative, emit every local as an `alloca` and run a mem2reg pass with dominance frontiers, allocates a stack slot and a load and a store per variable access and then deletes almost all of them, which is a large amount of garbage created and destroyed on every compilation, including at `-O0` where mem2reg is the only pass we run. Building SSA directly means `-O0` never materializes that garbage.

A dominance-frontier-based mem2reg (Cytron et al., TOPLAS 1991) still exists for the `alloca`s that do get created and later prove promotable after inlining.

## 8.6 CFG invariants

The entry block has no predecessors and its parameters are the function arguments. Every block ends in exactly one terminator and contains no terminator elsewhere. Every block is reachable, or is deleted. Critical edges, an edge from a block with multiple successors to a block with multiple predecessors, are permitted in the optimizer and **must be split before register allocation**; document 10 owns that.

Loop structure is not part of the IR. It is an analysis, recomputed or incrementally maintained by the pass manager in document 09, because an IR that stores loop structure has to keep it correct through every edit and that is a losing battle.

## 8.7 The verifier

The verifier is not a debug aid. It runs after every pass in debug builds, after every pass in CI, and on demand with `-fverify-ir`, and a pass that produces IR failing verification is a build failure, not a warning.

What it checks: SSA dominance, that every use is dominated by its definition; block parameter arity and type agreement with every predecessor's branch; terminator placement; type agreement on every operand of every instruction, using the type rules of 8.2; that no instruction references a deleted value; that `alloca` appears only in the entry block or is marked dynamic; that atomic orderings are valid for the operation; that `inline_asm` with labels is a terminator; that TBAA metadata forms a valid tree; that flag combinations are legal; and that the CFG is connected and every block reachable.

Roughly a thousand lines, written in M2, and it is the cheapest correctness investment in the entire project. Every from-scratch compiler that skipped it spent the equivalent time debugging.

## 8.8 The textual form

The IR has a printer and a parser and they round-trip byte-for-byte, per document 03. This is what makes the IR testable in isolation, what makes `-fdump-ir=after-<pass>` useful, and what lets the fuzzer generate IR directly to test the optimizer without going through the frontend.

```
; ModuleID = 'example.c'
; format 0
target triple = "x86_64-unknown-linux-gnu"
target datalayout = "e-p:64:64-i64:64-f80:128-S128"

global @counter : i32 = 0, align 4, linkage(internal)

func @sum(i32) -> i32, linkage(external), attrs(nounwind, fp_contract=on) {
block0(%0: i32):
    %1 = iconst.i32 0
    %2 = icmp sle %0, %1
    br_if %2, block2(%1), block1(%1, %1)

block1(%3: i32, %4: i32):
    %5 = iconst.i32 1
    %6 = add.nsw %4, %5
    %7 = add.nsw %3, %6
    %8 = icmp sge %6, %0
    br_if %8, block2(%7), block1(%7, %6)

block2(%9: i32):
    %10 = global_addr @counter
    store %9 -> %10, align 4, tbaa !1
    return %9
}

!0 = tbaa "omnipotent char", offset 0
!1 = tbaa "int", parent !0, offset 0
```

Design notes on the syntax. Types are suffixed on the opcode where the instruction is polymorphic, so a reader never has to look up an operand's declaration to know the width, and left off where the operands already say it, since a second copy of something the reader can already see is a thing that can disagree with the first. Block parameters are declared at the block and passed at the branch, so a CFG edit is readable in a diff. Metadata is defined at the end and referred to by number, so the instruction stream stays scannable. The `datalayout` string exists so a printed module is self-contained and can be re-parsed and compiled without the original command line, which is what makes an IR-level bug report actionable.

Values and blocks are numbered in the order they are printed rather than by the index they hold in the function's tables, and a call writes its signature at the call site rather than a number into a side table. Neither is cosmetic: a module read back from text will not in general land its values on the same indices, so printing an index would make the round trip fail on a module that is otherwise identical to the one that was printed. Nothing in the text is a fact about the tables, which is what the round trip means.

Reading is not the mirror image of writing, because an instruction can use a value defined further down the text: blocks are printed in layout order, and layout order need not put a definition before its uses. Building an instruction needs the types of the values it produces, and for most opcodes that is the type of the first operand, so a function is read in two passes. The first turns the text into instructions whose operands are still the numbers they were written as, and the second works out every value's type by a fixed point before anything is built. It terminates because the only cycles in the definition graph run through block parameters, and a block parameter has its type written at the block. The numbering is then checked rather than assumed: building in print order gives every value and every block the index its number says it has, and text whose numbers do not come out that way is turned down.

## 8.9 Debug information in the IR

Every instruction carries a source location, a `SpanId`, four bytes, in a side array per document 03's rule about not putting cold data in hot structs. Locations survive optimization by the standard rules: a folded instruction inherits the location of the instruction it replaced; an inlined instruction gets an inlined-at chain; a hoisted instruction keeps its original location.

Variable locations are separate: `dbg_declare` for variables with a stack home and `dbg_value` for SSA values, both as non-instruction annotations that the optimizer must update rather than as instructions the optimizer might treat as uses. Treating them as uses keeps dead code alive and is the classic mistake here. Document 11 turns them into DWARF location lists.

## 8.10 Stability

The IR's textual form is versioned with a single integer in the module header. It is **not** a stable interface before 1.0 and the crate carries that warning per document 18. After 1.0 it is stable within a major version, because by then people will have written tools against it and because a stable IR is what makes the compiler useful as a research platform, which is a secondary goal worth not accidentally foreclosing.
