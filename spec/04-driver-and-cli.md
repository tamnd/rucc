# The driver and the command line

The driver is the compatibility surface. Nobody types `rucc` directly at first; `configure`, `cmake`, `meson` and `Kbuild` type it, and they type it the way they type `gcc`. Every hour spent on flag compatibility saves a day of debugging someone else's build system.

## 4.1 The compatibility contract

**We are GCC, not Clang, where they differ.** `CC=rucc ./configure` must behave as if `CC=gcc`. Where Clang has added a better spelling for something, we accept both and document GCC's as canonical.

Three rules that sound minor and are not:

**Unknown `-W` flags warn, they do not fail.** Autoconf probes for warning flags by trying them. A compiler that errors on `-Wno-format-truncation` fails configure scripts written for GCC 8. Similarly, `-Wno-<anything>` is always accepted silently, matching GCC's rule that unknown *negative* warning flags are only diagnosed if some other error occurs.

Until there are warning groups there is no list to check a name against, so every `-W` argument other than the three that are not about warnings at all is taken and does nothing. `-w` is the exception, because it needs no group: it drops every warning at the one place each of them is rendered, and it drops it before the count, so `-w -Werror` compiles rather than failing on a warning nobody was going to read. Issue 485 is the groups.

**Unknown `-f` flags that we do not implement are accepted and ignored with a note under `-v`, not rejected**, when they are known-safe no-ops (`-fno-ident`, `-funit-at-a-time`). Flags that change semantics and that we do not implement are hard errors, because silently ignoring `-fno-strict-aliasing` is a miscompilation waiting to happen. Document 13 keeps the list of which is which; the default for an unrecognized `-f` flag is a hard error, and moving one to the ignore list is a deliberate act.

**Exit codes, output file naming, and stderr formatting match GCC.** `-o` semantics, the `.o` next to the source when `-c` without `-o`, `a.out` by default, one diagnostic per line with `file:line:col: severity: message`.

## 4.2 Phases

Each input file gets a phase sequence derived from its extension and the mode flags. The recognized extensions and their entry points:

| Extension | Meaning | Entry phase |
|---|---|---|
| `.c` | C source | preprocess |
| `.i` | preprocessed C | parse |
| `.ir` | this compiler's IR, in the text its printer writes | read the IR |
| `.h` | header, only with `-x c-header` or explicit | preprocess |
| `.s` | assembly | assemble |
| `.S` `.sx` | assembly needing preprocessing | preprocess then assemble |
| `.o` `.obj` | object | link |
| `.a` `.lib` | archive | link |
| `.so` `.dylib` `.dll` | shared library | link |

`.ir` is not a GCC input kind, because GCC has no textual IR. It is here because the IR's printer and its parser are a pair, and a pair is only known to agree if something reads back what was written, so `rucc --emit=ir a.c -o a.ir` followed by `rucc --emit=ir a.ir -o b.ir` is the round trip of document 08 stated as two files a byte comparison has an opinion about, over whatever code is at hand rather than over the modules a test happens to build. What comes in this way is verified the way what the walk builds is, since a module a person edited has not been through the verifier. An input file whose output would have the name it has itself is refused rather than written over.

`-x <lang>` overrides extension detection for subsequent inputs, with `-x none` reverting. `-E` stops after preprocessing, `-S` after code generation, `-c` after assembly, and no flag runs through linking.

`-###` prints the phase plan and the exact linker invocation without executing anything, and `-v` prints it while executing. Both are load-bearing for debugging other people's builds. The phase plan half of both landed in M0 with the phase graph, because a plan that is pure data is the thing that makes them possible and it costs nothing to print it; the linker invocation half arrives in M3 when there is one.

`@file` response files are expanded recursively, with the shell-like quoting rules GCC uses, before any other parsing. Windows builds need this; so do very large link lines.

## 4.3 Target selection

`--target=<triple>` selects the target. The triple is parsed into a `TargetInfo` in `rucc-target`, and *nothing downstream ever asks about the host*. Recognized triples at 1.0:

```
x86_64-unknown-linux-gnu      x86_64-unknown-linux-musl
aarch64-unknown-linux-gnu     aarch64-unknown-linux-musl
riscv64-unknown-linux-gnu     riscv64-unknown-linux-musl
x86_64-apple-darwin           aarch64-apple-darwin
x86_64-pc-windows-msvc        aarch64-pc-windows-msvc
x86_64-unknown-none           aarch64-unknown-none     riscv64-unknown-none
```

The `-none` triples are the freestanding ones and are what the kernel build uses. They imply `-ffreestanding`, no default libraries, and no assumptions about libc.

`TargetInfo` is a plain data structure, not a trait object, containing: pointer and integer widths, `char` signedness, `long double` representation, endianness, alignment rules, the object format, the ABI variant, the default `-fPIC` setting, the assembler dialect, the register file, and the predefined macro set. Adding a target means adding a `TargetInfo` and a lowering rule set, and nothing else. Document 10 and document 12 own the contents.

GCC-style flags are accepted as aliases where they are unambiguous: `-m32` and `-m64` adjust the triple, `-march=` and `-mtune=` and `-mcpu=` select the subtarget, `-mabi=` selects the ABI variant. Target-specific `-m` flags that gate instruction set extensions (`-msse4.2`, `-mavx2`, `-march=armv8.2-a+crypto`) set feature bits consulted by instruction selection and by the `__builtin_cpu_supports` and predefined-macro machinery.

The `-m` family arrives before any of that is built, and a build system passes it whether or not there is a second choice to make. The rule while there is only one answer is that a flag naming the answer we already give is taken and a flag naming a different one is refused. `-m64` against a target whose pointers are eight bytes is nothing to do; `-m32` against the same target is a request for a compilation that would not be the one asked for, and refusing it is how the person finds out. `-march=`, `-mtune=` and `-mcpu=` are taken and ignored, because they are a choice about how fast the output is and not about what it does. `-mabi=` is taken when it names the architecture's own convention and refused otherwise, and `-mcmodel=small` is taken while the larger models are refused, for the same reason.

## 4.4 Search paths

The include search order matches GCC exactly, because header shadowing bugs caused by a different order are miserable to diagnose: `-I` directories in command-line order, then `-iquote` for `"..."` includes only, then `-isystem`, then the configured system directories, with `-nostdinc` suppressing the last group and `--sysroot=` prefixing it. `-idirafter`, `-iprefix`, `-iwithprefix`, `-iwithprefixbefore` and `-I-` are supported for compatibility, and `-include` and `-imacros` name a file to be read before the source. `-M`, `-MM`, `-MD`, `-MMD`, `-MF`, `-MT`, `-MP` and `-MQ` produce make-format dependency files, and these are required by essentially every build system.

The older spellings are measured rather than read, because two of them do not do what the manual says. `-I-` moves every `-I` written before it into the quoted chain and takes the directory of the including file off the front of that chain, which is the second half of what it means and the half `-iquote` does not replace. A `-iquote` written before it stays in the quoted chain and lands after the `-I` directories that just joined it, because GCC holds `-iquote` back until every `-I` and `-I-` has been dealt with, so a `-iquote` is later in the chain than an `-I` whatever order the two were written in. `-iprefix` sets a string stuck on the front of every later `-iwithprefix` and `-iwithprefixbefore`, and a second one applies only to the flags after it. The manual says `-iwithprefix` adds to the `-idirafter` chain; it adds to the `-isystem` chain, and `-iwithprefixbefore` adds to the `-I` chain, and a cross build that uses either is relying on what the compiler does rather than on what the manual claims. GCC's prefix with no `-iprefix` is its own installed header directory with the last component taken off, which is a path that only exists for a compiler installed in a fixed place; there is no equivalent for a single binary that runs wherever it is copied, so here the prefix starts empty and `-iwithprefix` with no `-iprefix` names a directory outright.

`-include` and `-imacros` read a file before the first line of the source, which is how a build gets a definition into a tree whose files do not include it: the kernel compiles every object with `-include` of its configuration header, and a configure script gets its `config.h` into a third party source tree the same way rather than by patching it. The difference between them is that the text an `-imacros` file produces is thrown away and only its definitions are kept, which is what makes it usable on a header the source includes anyway. Every `-imacros` file is read before every `-include` file whatever order the command line wrote them in, and the order within one family is the order it was written; this too is measured, since the two flags the other way round produce the same output byte for byte. Each name is looked for the way a quoted include is looked for, starting from the working directory rather than from the directory of the source, so a source in `sub/` with `-include` of a header sitting beside it is an error and not a file found: the command line was not written in `sub/`. A file either flag named is a prerequisite in the `-M` rule the same as one a directive named, and it is subject to the guard optimization the same way, so `-imacros` of a guarded header the source also includes reads it once.

The dependency family belongs to the driver rather than to a separate tool because the answer is the set of files the preprocessor opened, and nothing outside the preprocessor knows what that was. `-M` and `-MM` write the rule instead of compiling, which is what a makefile recipe of the form `rucc -M $< -o $@` expects; `-MD` and `-MMD` write it beside the output and compile as well, which is what a build that includes its own generated rules passes on every compilation. The two spellings that end in `M` leave out headers found in a system directory, and nothing turns them back on once a flag has turned them off, so `-MM -M` is `-MM`. The rule goes where `-MF` says, or to the output name with its suffix replaced by `.d`, or to the source name with the same replacement; `-` means standard output. Its target is what `-MT` or `-MQ` gave, in the order given, where `-MQ` escapes what it is given and `-MT` writes it through untouched, and with neither of those it is the `-o` argument when the run produces something `make` could rebuild and the source name with a `.o` suffix otherwise, which is why `-MD -E -o out.i` writes `out.d` holding a rule for `a.o`. Prerequisites are the resolved paths rather than the names the directives wrote, since a rule naming `stdio.h` says nothing about which one, with the `.` components taken out, and they are wrapped at 72 columns, and a space is escaped as `\ `, a `#` as `\#` and a `$` as `$$`. Taking the `.` out is what GCC does and it disagrees with what GCC's own line marker for the same header says: `-I./d` gives a prerequisite of `d/f.h` and a marker and a `__FILE__` of `./d/f.h`. The two are answers to different questions. A marker names the file the way the search reached it, which is what a debugger and a `#line` are about, and a prerequisite names a file `make` has to compare a timestamp against, which the leading `./` says nothing about. `-MP` adds a target with no prerequisites and no recipe for every prerequisite except the source, which is what stops `make` failing outright on a header that was deleted.

One thing here is deliberately not what GCC writes, and it is that a file is named once. GCC keys its list on the pair of the directory the search started from and the name the directive wrote, because that is the key of the cache it reads files through rather than a decision anybody made, so `"x.h"` and `"./x.h"` are two prerequisites there and a header that two other headers in the same directory reach by different relative paths is listed twice. This one keys on the file itself. Naming a file once is what the flag means, and a repeated prerequisite means nothing to `make` either way, so the difference is visible only to somebody diffing the two rules.

Between `-isystem` and the configured system directories sits one entry that is not a directory at all. A hosted C implementation is two halves: the library ships the headers that declare functions you link against, and the compiler ships the handful whose contents only it can know. `<stdarg.h>` is the target's calling convention, `<limits.h>` and `<float.h>` are the target's types, `<stddef.h>` is the ABI, and no library can write any of them. Those headers are compiled into the binary and appear on the search path under the name `<builtin>`, which is spelled with the angle brackets so that no directory a user can create can shadow them or be shadowed by them, and so that a diagnostic naming `<builtin>/stdarg.h` reads as what it is. Keeping them in the binary rather than on disk means the compiler does not have to find its own installation before it can preprocess a file, which is what lets a single static binary work wherever it is copied. `-nostdinc` drops this entry along with the configured system directories, because the two halves of a hosted implementation are a pair and half a pair is worse than none. The set is `float.h`, `iso646.h`, `limits.h`, `stdalign.h`, `stdarg.h`, `stdatomic.h`, `stdbool.h`, `stddef.h`, `stdint.h` and `stdnoreturn.h`. `limits.h` and `stdint.h` chain to the library's with `#include_next` when there is one, because on a hosted system the library's is what the rest of the library was written against.

The other half of the pair is the library's own headers, and "configured" is the wrong word for them here. GCC decides where they are when it is built, which it can do because a GCC is built for the machine it will run on, and this compiler is one binary that runs wherever it is copied, so it asks the machine instead. What that means per platform is one list of candidates each, of which the ones that exist are taken: on Linux, `/usr/local/include` and then the multiarch directory and then `/usr/include`, which is GCC's order and every distribution's layout; on an Apple platform the SDK and nothing else, since there has been no `/usr/include` on a Mac since the command line tools stopped installing one, found from `-isysroot` or `SDKROOT` or by asking `xcrun`; on Windows whatever `INCLUDE` names, because there is no fixed place there and the environment `vcvarsall.bat` sets is what every compiler on that platform reads. Cross compiling to another operating system offers nothing at all without a `--sysroot`, because this machine's `/usr/include` describes this machine's library and handing it to a program being built for somewhere else moves the failure from an `#include` that could not be resolved to a declaration that is quietly wrong.

Library search is `-L` in order, then the target's defaults, with `-B` prefixes consulted for our own auxiliary files. `-nostdlib`, `-nodefaultlibs` and `-nostartfiles` behave as GCC's.

We do **not** implement GCC's `specs` file mechanism. It is a scripting language nobody should have to learn, and the parts of it that build systems actually rely on are the ones above. A `-specs=` flag is a hard error with a message pointing at the equivalent flags.

## 4.5 Predefined macros, and the trap in them

This is the single most consequential compatibility decision in the driver, and document 01 flagged it: the moment `__GNUC__` is defined, glibc's headers, the kernel's headers and every autoconf probe take the GNU path, and we have signed up for whatever those paths use.

The decision: **we define `__GNUC__` and we claim a specific version, and document 13's extension matrix is the list of promises that claim makes.** The alternative, not defining it, means glibc's `<sys/cdefs.h>` treats us as a pre-standard compiler and the result does not compile at all. There is no third option.

The version we claim is a tunable, `-fgnuc-version=`, and the default is the highest one measured to get a real header set through. Claiming too high a version means headers use features we lack; claiming too low means headers take slow or deprecated paths and some projects refuse to build, and below GCC 7 glibc writes `typedef float _Float32;` over a keyword we already have, which stops most of its headers outright. So the default is 7.0.0, and it moves when there is a measurement over glibc, the macOS SDK and the corpora in document 14 saying it can, not when document 13's matrix reaches some line.

We also define `__rucc__` and `__rucc_version__` so code can detect us specifically, and we do **not** define `__clang__`.

The rest of the predefined set is generated from `TargetInfo`: the `__SIZEOF_*__` family, `__CHAR_BIT__`, the limits macros, `__BYTE_ORDER__`, `__INT*_TYPE__` and the exact-width families, `__SIZE_TYPE__`, `__PTRDIFF_TYPE__`, `__WCHAR_TYPE__`, `__INTPTR_TYPE__`, the `__*_MAX__` family, `__FLT_*__` and `__DBL_*__` and `__LDBL_*__`, the architecture macros (`__x86_64__`, `__aarch64__`, `__riscv`, and their `_LP64` companions), the OS macros (`__linux__`, `__APPLE__`, `_WIN32`), `__ELF__` where applicable, feature-test results from `-m` flags, `__OPTIMIZE__` and `__OPTIMIZE_SIZE__`, `__NO_INLINE__`, `__PIC__` and `__PIE__`, and `__STDC_VERSION__` per the dialect.

`rucc -dM -E -` prints the whole set, and a CI job diffs it against GCC's on the same triple. Divergences are either fixed or recorded with a reason in document 13.

## 4.6 Dialect and semantic flags

`-std=` accepts `c89` `c90` `c99` `c11` `c17` `c23` and their `gnu` variants. **The default is `gnu23`**, matching current GCC. `-ansi` is `-std=c89`. `-pedantic` and `-pedantic-errors` diagnose extensions used in a strict mode.

`-fgnu89-inline` puts the whole unit under GNU's reading of `inline` rather than C's, and `-fno-gnu89-inline` puts it back. C99 swapped which of `inline` and `extern inline` leaves a definition behind, so a program written before that swap and compiled under a later dialect needs this flag to mean what it meant. The C89 dialects are under GNU's reading whatever the flag says, so `-std=c89 -fno-gnu89-inline` changes nothing here. gcc refuses that combination outright with `'-fno-gnu89-inline' is only supported in GNU99 or C99 mode`, and accepting it and ignoring it is the more permissive of the two answers on a command line that could only have meant one thing anyway. The flag also decides which of `__GNUC_GNU_INLINE__` and `__GNUC_STDC_INLINE__` is defined, since that is how a header asks which reading it is under, and `spec/13-gnu-compat.md` section 13.3 has the rest of what the two readings differ on.

`-fvisibility=default|hidden|internal|protected` says how far a name reaches outside a shared library when nothing in the source said. It is what a library is compiled with when it means to ship a small documented interface rather than every name it happens to define, and it is on every cmake project that cares about its exports, since cmake writes it from `CXX_VISIBILITY_PRESET` and `C_VISIBILITY_PRESET`. Four spellings and three answers: `internal` is `hidden` plus a promise about never taking the address across a component boundary, and nothing here derives anything from that promise, so it comes out as the weaker of the two rather than as a refusal over a distinction this compiler does not make. A spelling gcc does not take is refused, because a build that meant hidden and got exported is a library with the wrong interface and nothing said about it anywhere.

It is a default and not an override. An `__attribute__((visibility(...)))` in the source wins wherever one was written, which is what makes the flag usable: a library puts it on the whole tree and marks the dozen names it means to export one at a time. A compiler that let the flag win would export nothing at all. `spec/13-gnu-compat.md` section 13.4 has the attribute and `spec/11-asm-objects-debug.md` section 11.3 has what each answer reaches an object file and a listing as.

`-fpermissive` turns the rules gcc 14 promoted from warnings into errors back into warnings, and `-fno-permissive` puts them back. There are six of them: a declaration with no type in it, a call to a function nothing declared, a parameter named in an old style definition and never given a type, a pointer made from an integer with no cast, a pointer assigned from a pointer to something else, and a `return` whose value disagrees with what the function promised. Three of the six are rules C89 did not have, so under `-std=c89` and `-std=gnu89` there is nothing to say about them at all and the flag is not what decides that: the dialect is. A call to a name nothing declared declares `extern int f();` for the file whenever it is not refused, which is C89 6.3.2.2 and is what makes the rest of the call ordinary. The flag changes what is said and not what is compiled, since a program it accepts is compiled the way the rule it broke says it means. Measured against gcc 16.2.0 one file per rule, which is where the table in `Context::promoted` comes from.

The flags in this group change what the optimizer may assume and are threaded into the IR as module-level or function-level semantic attributes rather than consulted globally, so that LTO across units compiled with different flags remains correct. This is a real hazard: a project that builds one file with `-fno-strict-aliasing` and another without must not have the second file's assumptions applied to the first after inlining.

`-fwrapv` makes signed overflow defined as two's-complement wrapping. Postgres requires it. `-fno-strict-overflow` is both that and `-fwrapv-pointer`, and the kernel requires it. `-ftrapv` stops the program instead, through the same runtime routines gcc calls. `-fno-strict-aliasing` disables type-based alias analysis; the kernel requires it and a great deal of real C is quietly wrong without it. `-fno-delete-null-pointer-checks` forbids inferring non-nullness from a dereference; the kernel requires it. `-ffreestanding` removes the assumption that library functions behave as the standard says, which in particular means no recognition of `memcpy` idioms into calls that do not exist. `-fno-builtin` and `-fno-builtin-<name>` do this selectively. `-fexcess-precision=standard|fast` controls x87 intermediate precision; Postgres requires `standard`. `-ffp-contract=off|on|fast` controls fused multiply-add formation. `-frounding-math` and `-ftrapping-math` constrain FP transformations. `-fshort-enums`, `-fsigned-char` and `-funsigned-char` change the type system and therefore the ABI.

`-fwrapv`, `-fwrapv-pointer` and `-fno-strict-overflow` are three spellings of two questions, and all three are implemented by writing less rather than by writing anything. Every assumption about overflow this compiler makes is one flag on one instruction, put there by lowering: an add, a subtract, a multiply, a shift and a negation in a signed type each say they do not wrap, and so does the multiply that turns an index into a number of bytes. `-fwrapv` stops the first group being written, `-fwrapv-pointer` stops the last one, and `-fno-strict-overflow` is the pair, which is gcc's own reading of the older flag: its help text for `-fstrict-overflow` says it is negated as `-fwrapv -fwrapv-pointer`. Unsigned arithmetic is unaffected because it never claimed anything, since C says what an unsigned overflow produces and there is nothing to assume. The pointer addition itself claims nothing either, so there is nothing there to withdraw and the scaling multiply is the whole of the pointer question here.

Being an absent licence rather than a mode is what makes the flags correct across link time optimization, and it is why they are per instruction rather than per module. A body from a unit compiled with `-fwrapv` and a body from a unit compiled without it keep their own answers when they are inlined into each other, because what each of them was promised is written on the instructions rather than looked up on the way past. The effect is visible where a pass reads the flag: the count of a loop whose counter goes up one at a time rests on the counter not turning round, so a build where it may turn round does not get the count and keeps a check the other build hoists out.

`-ftrapv` is the other answer to the first of those two questions and is the only flag in this group that asks for something to be generated. Where `-fwrapv` says a signed overflow produces the number the machine gives, this says it stops the program, and stopping has to be code. Lowering turns each of the four operations that can overflow in a signed type into a call to the routine in the runtime that does it and checks it: an add becomes `__addvsi3`, a subtract `__subvsi3`, a multiply `__mulvsi3` and a negation `__negvsi2`, with `di` in place of `si` for a `long long` and `ti` for a 128 bit type. Those are libgcc's names and libgcc is linked already, which is what makes an object this compiler produced stop the same way as an object gcc produced beside it. A shift is not among them and neither is a divide, matching gcc: what a shift that moves a bit past the top does is undefined for a reason of its own, and the one division that overflows already stops on the hardware. Nothing narrower than a word is checked, because C promotes a `char` and a `short` before any operator sees them and the addition that could overflow is at `int` by the time it is lowered.

One difference from gcc is deliberate and is in the direction of stopping more rather than less. gcc folds a signed overflow it can work out at compile time and emits no check for it, so a build with `-ftrapv` that adds one to the largest `int` in a place the optimizer can see runs to the end and prints the wrapped answer. This compiler makes the call, and the program stops. That is what the flag asks for, the check that folding removes is the one a person who wrote the flag would most want kept, and the operations affected are only the ones written in a form no constant expression rule already evaluated.

A command line that writes `-ftrapv` and `-fwrapv` together has written a contradiction, since a program cannot both wrap and stop, and the last one written is the answer. That is gcc's behaviour and was measured against gcc 16 rather than read out of the manual, which says nothing about it. `-fno-strict-overflow` counts as `-fwrapv` for this, being the pair that contains it, and `-fstrict-overflow` does not count as `-fno-trapv`, because it says what may be assumed rather than what happens.

Both spellings of the aliasing flag are accepted today and neither does anything, and the reason is worth writing down because section 4.1 names this exact flag as the one that must not be quietly ignored. Nothing lowering writes says which type an access went through. The IR has a place for a type based aliasing node and the alias analysis reads one where it finds one, and lowering fills that place with nothing on every access, so no pass has a type to reason from. That makes `-fno-strict-aliasing` a description of what this compiler does, the same shape of thing `-fPIC` is, rather than a request being dropped. `-fstrict-aliasing` is a request for a stronger assumption than this compiler makes, and giving less than was asked for is safe here in a way the `-fno-pic` case is not: every program correct under the assumption is correct without it and only slower, and `-O2` implies the flag, so refusing it would stop builds for nothing. A test in `compile.rs` compiles the four access shapes that would carry a node and asserts none does, so the day lowering starts emitting them is the day the flag has to start turning them off.

Both spellings of the null pointer flag are accepted today and neither does anything either, for the same reason and with the same obligation attached. Nothing here concludes that a pointer is not null from the fact that the program read through it. There is no such conclusion to draw from, because no pass records one: a load says where it read and nothing else, and a comparison against null is an ordinary comparison of two values that no fact is held about. So a function that reads through a pointer and then tests it keeps the test, which is what `-fno-delete-null-pointer-checks` asks for and what gcc has to be asked for, since gcc draws the conclusion by default. `-fdelete-null-pointer-checks` is the request to draw it and goes the way `-fstrict-aliasing` does, for the same reason: assuming less than was asked for costs speed rather than correctness, and `-O2` implies it. This compiler is more conservative than gcc here in one place gcc is conservative in neither mode, which is the address of a member at a non zero offset: gcc folds a test of `&p->b` to true whether or not the flag is given, and this keeps it. `crates/rucc/tests/nullchecks.rs` compiles the three shapes at every optimization level and asserts each still asks its question.

The three flags that change the ABI are implemented and are the only ones in this section a program can be built half with and half without without anything reporting it. `-fsigned-char` and `-funsigned-char` say what a plain `char` is, and each has a second spelling, since gcc reads `-fno-signed-char` as `-funsigned-char` and `-fno-unsigned-char` as `-fsigned-char`, so there are four ways to write two answers and the last one written wins. Nothing is assumed until one of them is given, because the target's own ABI is the answer otherwise and it differs across the table: x86-64 and Apple's arm64 say signed and Linux's arm64 says unsigned. What the command line decides is put into the target rather than carried beside it, so every part of the compiler that asks what a `char` is gets one answer, and `__CHAR_UNSIGNED__` is defined when the answer is unsigned, which is gcc's spelling and the only way a header can see what was decided. A plain `char` stays a third type distinct from both `signed char` and `unsigned char` under either answer.

`-fshort-enums` represents an enumeration nothing wrote an underlying type for in the smallest integer type that holds its enumerators, so the candidates start at `unsigned char` and `signed char` rather than at `unsigned int` and `int`. The signedness is settled first, by whether any enumerator is negative, and the width second, by what fits, which is why `200` is one byte and `-200` is two. It changes nothing else: an enumerator is still `int` wherever the value fits in one, an enumeration the program wrote a type for under C23 is still that type, and an enumeration too wide for an `int` is the same size under both answers. The values were measured against gcc 16 in both `-std=c17` and `-std=c23`, which agree, and `crates/rucc/tests/abi_flags.rs` asserts each of them as a static assertion the program itself can see, compiled under both answers so that neither set of assertions can be vacuous.

The four flags about what may be done to an arithmetic are all accepted and this compiler sits on the restrictive side of every one of them. It fuses no multiply into an addition on any target at any level under any `-march=`, folds no floating point arithmetic in a function body, reassociates nothing, and computes every operation in the type it was written in, so `__FLT_EVAL_METHOD__` is 0. That makes `-frounding-math`, `-ftrapping-math` and `-fexcess-precision=standard` descriptions of what already happens, and makes `-fno-rounding-math`, `-fno-trapping-math`, `-fexcess-precision=fast` and `-fexcess-precision=16` licences that are taken and not used, which passes the test in section 4.1 because not taking a licence costs speed rather than correctness. The values of `-fexcess-precision=` are gcc's three and anything else is refused, and none of them is kept, since there is no x87 target here and x87 is the machine the question was invented for. `crates/rucc/tests/fpmath.rs` asserts each shape survives at every optimization level and that the module is byte for byte the same under every spelling.

`-ffp-contract=` is the one of the four that is kept rather than described. It takes gcc's three values, anything else is refused, and the value rides into the IR as `fp_contract` on every function with a body and on no declaration, so the code generator still has the answer by the time it would matter and a reader can see in `--emit=ir` that the flag was understood. The default here is `off` and not gcc's, which is `fast` under its own dialects and `off` under a strict `-std=`. Nothing fuses anything yet, so the two defaults are the same program, and `off` is the one that does not write a licence nobody reads onto every function in the file. When the code generator learns to form an `fma`, the default moves to gcc's in the same change.

`-ffast-math` is implemented as the documented union of its components and each component is individually available, because `-ffast-math` as an opaque blob is how numerical code silently breaks.

The four prefix mapping flags are what make a build reproducible from two different directories, and they are four spellings over three lists. `-fmacro-prefix-map=<old>=<new>` rewrites the paths the preprocessor turns into string literals, `-fdebug-prefix-map=` the ones the debug information holds, `-fprofile-prefix-map=` the ones the profile data holds, and `-ffile-prefix-map=` is all three at once. Each occurrence appends to its list rather than replacing it, since a build passes one per source root and expects all of them to be in force, and where two of them match the same path the later one acts. The match is on the characters at the front of the path and not on whole directory components, which is gcc's rule and means a rewrite that stops halfway through a name really does cut it in half. The argument splits at the last `=` rather than the first, which is also gcc's rule and is the only one that lets a directory whose name contains an `=` be the old half, and an argument with no `=` in it at all is refused.

Only the macro list acts today, because `__FILE__` is the only path that reaches the output: there is no DWARF and no profile data yet, so `-fdebug-prefix-map=` and `-fprofile-prefix-map=` are taken and recorded and rewrite nothing, which passes the test in section 4.1 because a flag that hides a path in an output that does not exist promises nothing it does not keep. The crate documentation in `rucc-debug` says that the DWARF work has to read `Options::prefix_map.debug`. What is rewritten is `__FILE__` and `__BASE_FILE__` and not `__FILE_NAME__`, since a mapping rewrites the front of a path and the last component is what is left when the front has been taken off, and what is not rewritten anywhere is the `-E` line markers and the diagnostics, since those are how the compilation and the person running it find the file again. gcc draws all three of those lines in the same places. `crates/rucc/tests/prefixmap.rs` asserts each of them, and asserts on the bytes of an object that the build directory's name is gone from it and the replacement is there. `-fcanon-prefix-map`, which makes the old half match a path that reaches the same file by a different spelling, is not implemented, because it is a question about the file system rather than about the string and it needs the include search to record what it resolved.

## 4.7 Optimization and code generation flags

`-O0` `-O1` `-O2` `-O3` `-Os` `-Oz` `-Og` select the pipelines in document 09. A bare `-O` is `-O1`, which is GCC's spelling of it, and `-Og` is `-O1` until there is a pipeline that keeps the debug info better than `-O1` does. `-Ofast` is accepted and maps to `-O3 -ffast-math`, with a warning, matching GCC's deprecation of it, and until fast math exists it is refused with a message saying so rather than silently compiled as `-O3`, because the difference between the two is the whole reason a program asks for it.

Individual `-f<pass>` and `-fno-<pass>` flags exist for every pass, which is required for bisection: when a project miscompiles at `-O2`, the first diagnostic step is to find the pass. `-fdisable-<pass>[=<functions>]` and `-fenable-<pass>[=<functions>]` take a pass and, optionally, the functions the answer is about, and `-fpass-fuel=<pass>=<n>` runs a pass for exactly *n* transformations and then stops, which is how a miscompiling transformation is bisected to a single site. `-fpass-fuel-global=<n>` is the same limit across every pass, which is the search that says which pass to run the other one on. Document 15 depends on all of them.

A gate covers the functions it names and nothing else, and the last gate that covers a function is the one that decides for it, so everything a gate does not name keeps the answer the level already gave. That is what makes `-fenable-<pass>=3` mean "also run it there" rather than "run it only there", and it is what makes which pass and which function two independent bisections rather than one search over both at once. A function is named either by the name it has in the source, which is what `-fopt-info` prints, or by the position it has in the module counting from zero, which is what a script has without having read the file. A pass a gate enables that the level did not choose joins the pipeline, so a gate reaches a pass at `-O0` as well, which is where a bisection would rather start. `rucc --print-pipeline` says which passes a gate touched and what it said about them.

A pass name is a name the compiler holds rather than a string the driver keeps a list of, so `-f<pass>` and `-fno-<pass>` are read by asking the optimizer whether it has a pass by that name, and a `-f` flag naming something that is neither a pass nor a flag the rest of the compiler answers to is refused as an unknown option rather than ignored. The flags are read in the order they were typed and applied to the level's pipeline in that order, so the last spelling of a name decides, and turning on a pass the level already runs leaves it where the level put it rather than moving it to the end. `rucc --print-pipeline` prints what that arithmetic came to, which is the thing to look at before concluding that a `-f` flag did not take.

`-fdump-ir=all`, `-fdump-ir=before-<pass>` and `-fdump-ir=after-<pass>` write the IR out around a pass, one file per dump, named for the input file and then the pass, so that a bisection that has found the pass has somewhere to look next. The pass a dump names is checked while the command line is read rather than when the dump is taken, because a misspelled pass name discovered after the compilation has finished is discovered too late to be any use. A dump that could not be written is an error and not a warning, for the reason `-Zrule-coverage=` gives in section 4.11.

`-fPIC` and `-fpic` say the object may end up in a shared library, and `-fPIE`, `-fpie` and nothing at all say it will end up in an executable. Everything this compiler writes is position independent either way, so that is not what the flags decide. What they decide is whether a name is one another object may define or replace, because a link that produces an executable puts every name in the same program and a link that produces a shared library does not. Under `-fPIC` a replaceable name is reached through the global offset table rather than from the instruction pointer, and section 11.3 says which names those are and why the static linker refuses the cheap form rather than picking one of the two answers. The expensive answer is the one that has to be asked for, which is gcc's arrangement and is why `-fPIC` appears on the compile line of every library and nowhere else. `-fPIC -fvisibility=hidden` costs a library nothing, since a name nothing outside can see is a name nothing outside can answer for.

`__PIC__` and `__pic__` are `2` on every target that has a loader, whichever of the two was asked for, because they say there are no absolute addresses in the text and that is true either way. `__PIE__` and `__pie__` are defined when the answer is an executable, which is the default here as it is on a distribution's gcc. A program reads the second pair to find out which link is coming, and the two pairs saying different things is what makes that possible.

It matters that these are accepted at all, whatever they then do: every autoconf and cmake project puts `-fPIC` on the compile line, so a compiler that refuses it cannot be the `CC` of anything with a configure script whatever else it can do. `-fno-pic` and `-fno-pie` are a third thing and not the other direction of either. They are a request rather than a description and not one this compiler can grant, so they are refused with a message that says why, per section 13.3, rather than accepted and ignored. Compiling them as position independent anyway would be answering a different question: the answer is right everywhere an ordinary program runs, and it is wrong in a kernel, which is the place the flag gets written because there is no loader to fill a global offset table in.

`-fsemantic-interposition` and `-fno-semantic-interposition` ask a different question from that pair, and it is the question every distribution build of a shared library answers. `-fPIC` decides how an address is reached, and this decides whether the optimizer may believe a body it can see, because a name the file exports under `-fPIC` is one the dynamic linker may find another definition of first, so the body in front of the compiler is not necessarily the one that runs and everything read off it was read off the wrong function. The positive spelling is the default and is the honest answer. The negative spelling is a promise the build makes and nothing checks, that the definition here is the one that will run, and a build that makes it wrongly gets a program that behaves as though the replacement were not there. Which names are covered is the same rule as the addresses, from section 11.3: an external or weak definition with default visibility, and nothing else, so `-fPIC -fvisibility=hidden` needs no promise for anything it hides and `static` needs none at all. The flag changes nothing about how an address is reached, which is what gcc does with it too, so it does not reach the code generator and only the analyses that read a body are given it. Outside ELF there is nothing for it to be about, since Mach-O binds a name a library defines to that library rather than looking it up in load order.

`-fasynchronous-unwind-tables` and `-fno-asynchronous-unwind-tables` decide whether a function is described to an unwinder, and the positive spelling is the default, which is gcc's arrangement wherever anything reads the table. The reason it is the default is that the programs which read it are not the ones being compiled: C++ exceptions, `backtrace`, a profiler sampling a stack and a crash handler printing one all walk frames belonging to code that knew nothing about them, so a unit that opts out stops a walk that started somewhere else. What `asynchronous` asks for on top of a table is that the answer is right at every instruction and not only where a call is, because a signal can arrive anywhere, including the middle of a prologue. `-funwind-tables` and `-fno-unwind-tables` are the weaker request, for a table that only has to be right where a call is, and there is nothing here that writes a smaller one, so the same table answers both and a build gets one when either request is standing. That is how gcc resolves a line that asks for a table and against an asynchronous one, and such a line turns up when a build turns the asynchronous one off globally and a directory asks for a table back. Section 11.4 says what is in the table and what checks it.

`-fno-common` is accepted and changes nothing, because it describes what already happens: a file scope declaration with no initializer is written into `.bss` as its own defined symbol here, never offered to the linker as a common symbol for it to merge with others of the same name, which is what the flag asks for and what gcc has done by default since 10. `-fcommon` is the request and it is refused with a message rather than ignored, because the difference is real: two files each writing `int g;` link under it and are a duplicate definition without it, and a build that means the old behaviour has to be told it is not getting it. `-pipe` is accepted and means nothing here, since there is nothing written between the phases of one compilation to put in a file. `-fdiagnostics-color`, `-fno-diagnostics-color` and `-fdiagnostics-color=` are accepted and produce no colour, which is what they would produce anyway; cmake writes the third of those on every compile line when the generator is ninja, so refusing it stops builds over a question about how text looks.

`-ffunction-sections` and `-fdata-sections` give each function and each variable a section of its own, and `-fno-function-sections` and `-fno-data-sections` are the other direction and are the default. They are what make `--gc-sections` able to drop anything: a linker can leave out a section nothing reaches and cannot leave out half of one, so a file whose functions share a section keeps every function it defines in the output as soon as any one of them is called. That is how a kernel and an embedded image get small, and the cost is a section header per name, which is why it is asked for rather than always done. Two flags rather than one because gcc has two, and a build that asks for one of them and not the other is a build that measured something: splitting the code is nearly free at link time, and splitting the data can defeat the linker's ordering of what is next to what. The name of a split section is the one it would otherwise have shared with the name after it, `.text.f`, `.bss.x`, `.data.rel.ro.local.p`, which is not merely gcc's convention: `--gc-sections`, the linker scripts a kernel is linked with, and the default placement rules all match on the part in front of the dot. Two kinds of variable are left where they are. A tentative definition is a request to the linker for that much zeroed space rather than an image, so there is no section to split off, and one the program gave a section name to already has the answer the source gave, which a flag must not overrule. Section 11.3 has what the three object formats do with this, which is not the same thing on all three.

`-fstack-protector`, `-fstack-protector-strong` and `-fstack-protector-all` put a word in the frame above everything a local reaches and compare it against the one it was copied from before the function returns, and `-fno-stack-protector` is the other direction and is the default, as it is in gcc. Four flags rather than one with an argument because that is how gcc spells them and how every build line writes them, and the last one on the line wins, because a distribution puts `-fstack-protector-strong` in its global flags and the one directory that cannot have a protector turns it back off on the line after. What they differ about is which functions get one, and the answer is a question about the locals a function declares rather than about anything it does, so it is settled in the lowering while the types are still around and carried to the back end as an attribute on the function. The plain flag takes a function with an array of at least eight bytes in it, which is gcc's `ssp-buffer-size` and has been eight since the flag was written. The strong one takes a function with an array of any size, an array anywhere inside a structure, or a local whose address is handed to something that could write through it, which is what every distribution builds with and what the ones left out of the plain flag are. The last one takes every function there is. A function whose stack grows while it runs is taken by all three, because that is a variably modified type or an `alloca` and nothing can bound a write into one of those.

Where the word is copied from is a fact about the runtime rather than about the machine, and on this platform it is forty bytes into the block a thread has to itself, reached through a segment register and named by no relocation, which is why `%fs:40` appears in every protected function glibc has ever linked. A target whose protector is a different mechanism refuses the flag with a message saying so rather than accepting it and writing an unprotected frame, since a build that looks protected and is not is the one outcome worse than the error. Windows is that case: its cookie is a global the loader writes, what goes in the frame is that global exclusive-ored with the frame pointer, and the check is a call rather than a comparison. A protected function is not a leaf whatever it calls, because the arm where the check fails calls the function that does not come back, so it loses the red zone and its frame leaves the stack pointer where a call needs it. Section 10.7 has where the word sits in the frame and why it sits above the locals rather than below them.

`-fstack-clash-protection` takes a frame a page at a time and writes something to each page as it arrives, and `-fno-stack-clash-protection` is the other direction and is the default, as it is in gcc. A switch rather than a level, because how the frame is taken is one question and which functions get a canary is another, and the two compose: a function under both walks its pages and then writes its canary into the frame it has just taken. What it defends against is the page the operating system leaves unmapped below every stack. That page is what makes a stack that grows into it fault rather than run into whatever is under it, and a frame larger than it moves the stack pointer clean over it in one subtraction, so the first local the function writes to is written past a guard that was never touched and into whatever the program mapped next. A large local array is the whole of what an attacker needs for that, which is why distributions that build with this build everything with it: the hole is in whichever function was left out. A frame that fits in a page is taken the way it always was, since the far end of such a frame is the near end of a page that is there, and that is most functions, so the flag costs a program almost nothing. The touch is an inclusive or of zero with one byte, which reads the byte and writes back what was already there, so it is safe on a page nothing has been put in yet and it needs no register at all in a prologue where the registers still hold the caller's arguments. Up to three pages the prologue is a subtraction and a touch repeated, and past that it works out where it is going into one of the registers the allocator was told to hold back and walks there in a loop, because a straight line is two instructions a page and a loop is four however many pages it walks. Four kilobytes is how far apart the touches are, which is what every operating system this compiler targets leaves and what gcc's `--param=stack-clash-protection-probe-interval` defaults to; the two `--param` spellings that would change it are not accepted yet.

`-fcf-protection=full|branch|return|none|check` says which of the two edges of a control flow transfer are checked, `-fcf-protection` on its own is `full`, `-fno-cf-protection` is `none`, and `none` is the default, as it is in gcc. The forward edge is an indirect call or an indirect jump, and it is checked by a landing pad at every address one is allowed to arrive at, so a corrupted function pointer reaches somewhere somebody meant rather than any byte of the program. The backward edge is a return, and it is checked against a second copy of the return address that the machine keeps and the program cannot write to, which needs no instructions at all. So `branch` writes a landing pad at the top of every function and `return` writes nothing anywhere, and `check` writes nothing either: it asks that the compilation be looked at for whether it could be built this way rather than built this way. Every function gets a pad, including a leaf that takes no frame, because the address a pointer to a function holds is the address of the function, and a function a compiler thought too simple to bother with is one the program cannot call through a pointer any more. Only function entries get one so far, because the only indirect branches this compiler writes are calls through a pointer: there are no jump tables yet and computed goto is not lowered, and both will need a pad at every address they can reach on the day they arrive.

What is recorded matters as much as what is written. The machine's checks are turned on for a whole process or not at all, never for one function, so each object records in a note which halves it was built for, the linker keeps only what every input agreed on, and the loader turns on what survives. One input built without the note is enough to turn the whole program's protection off, which is why the note goes in for a mode that changed no instruction and why a target with nowhere to put one refuses the flag rather than writing the pads and staying quiet. Windows is that case: it has the same hardware and asks for it as a bit in the image the linker is told to set, which is not something a compiler writes into an object. The note is `.note.gnu.property` holding one property, whose key is the x86 feature word and whose value is one bit for the forward edge and two for the backward one, and it is written by both output paths so that `-S` and `-c` on the same command line cannot disagree about what the file was built for.

`-pg` makes every function call a routine the runtime provides on the way in, `-p` is the same request under its older name, and neither is the default. A profiler wants to know which function called which and how often, and the moment a function is entered is the only place a compiler can tell it that. The routine takes no arguments and returns nothing: which function was entered is not passed to it, because it reads its own return address to find out, and that is the whole reason the call is written rather than something cheaper. `-mfentry` and `-mno-fentry` say where the call goes, and the difference between them is what the hook can see when it runs. The earlier one runs in front of the prologue, so the return address is the top thing on the stack and the arguments are still in the registers they arrived in; the later one runs once the frame is taken, so the hook can walk back through the frame pointer, which is why a function that calls it is given one whatever the rest of the command line said. On this platform the earlier one is `__fentry__` and the later one is `mcount`, and the earlier one is what a command line that named neither gets, as it is in gcc. Either flag is accepted on its own and does nothing on its own, which is also gcc's behaviour: it says where a call would go and a command line that asked for no call has nowhere to put one, and a build system that sets `-mfentry` globally and asks for the profile per directory needs that to be true rather than an error.

A tracer wants the same call for a different reason, and it is the reason the earlier hook exists. The call is one instruction the kernel can overwrite while the program runs, which is what makes a function traceable without rebuilding it, and what makes it replaceable is that the stack at that instruction is exactly what a `call` left. A hook written one instruction later has lost that property and nothing complains, so the position is what the tests assert rather than the presence. Linux's ftrace is built on exactly this, which is why every kernel is compiled with the earlier one. It costs a leaf nothing: the hook runs before the prologue has written anything, so a leaf that keeps its locals in the red zone is still a leaf afterwards, and such a function stays completely frameless under the flag, as it does in gcc. The later hook is a call in the ordinary position and costs what one costs: the function is not a leaf, it loses the red zone, and its frame leaves the stack pointer where a call needs it. gcc warns that the later hook may be unreliable with shrink wrapping; this compiler does not do shrink wrapping, so it says nothing.

The flag changes the link as well as the code. The counts a profiled program keeps have to be started before `main` runs and written out after it returns, and what does both is a startup file of its own rather than anything the compiler wrote, so a build that compiles with the flag and links without it produces a program that calls the hook on every function and never writes a profile. `gcrt1.o` replaces `crt1.o` and `Scrt1.o`, and `grcrt1.o` replaces it for a static position independent link, which is the same pair gcc selects. A target whose profiler asks for something else refuses the flag with a message saying so rather than writing a call to a name nothing defines, since a link error a long way from the flag that caused it is worse than the error at the flag. Windows is that case: it profiles a build by having the compiler call `_penter`, which is asked for by a switch of its own and takes its argument in a register rather than off the stack, so it is not this hook under another name.

`-fpatchable-function-entry=N[,M]` asks for the same thing a tracer wants without asking for the call, and it is the form a kernel is built with. Every function opens with N bytes of the shortest instruction the machine has that does nothing, and what makes those bytes worth reserving is that they are never run for long: something writes a jump or a call over them once the program is up, and all it needs from the compiler is a known address and a known count. M says how many of the N go in front of the function's own label, and the two sides are not the same thing. What is after the label is inside the function, which is what a patcher redirecting a call into it wants, and what is in front of it is outside, which is where a patcher that needs a whole instruction the first one can reach puts it. M defaults to zero, M greater than N is refused, and `=0` is a command line that asks for nothing and gets nothing written, all as gcc has it.

Where the room sits among the other things a prologue opens with is document 10's, and only one of the answers is visible from here: the room goes after the landing pad and in front of the profiler's hook. So a function built with both `-fcf-protection=branch` and a split room has the pad between the two halves of it, and the address recorded is the front of the whole thing rather than the function's first instruction or its symbol.

Recording that address is the other half of the feature and the half a build can silently lose. A tracer that wants to patch every function in a kernel has to find them without reading the symbol table, which a stripped image does not have, so each function's room is recorded as eight bytes in a `__patchable_function_entries` section carrying `SHF_WRITE`, `SHF_ALLOC` and `SHF_LINK_ORDER`, aligned to eight, whose `sh_link` names that function's own text section and whose one relocation points at the room. The link order is what makes a linker that throws the text away throw the record away with it rather than leave an address pointing at nothing, and it is why `-ffunction-sections` gives each function a record of its own. A target whose object format has no such section refuses the flag rather than writing the bytes and staying quiet, since a build that looks patchable and is not is worse than either answer: every function is bigger and nothing can find any of them.

Code generation flags: `-fno-plt`, `-fno-omit-frame-pointer`, `-fomit-frame-pointer`, `-mcmodel=`, `-mno-red-zone`, `-fpatchable-function-entry=`. The last is a kernel requirement, and what the kernel does with it is in document 13.

`-fsanitize=address,undefined,thread,memory` and the `-fsanitize=kernel-*` variants are code generation features. `-fsanitize=undefined` is the one to implement first because it is the cheapest and it is what finds bugs in the corpus, and the list of what each check detects is the table in section 7.7 of document 07, where every undefined behaviour this compiler exploits is written down beside the check that catches it.

None of them exist yet, and until they do a `-fsanitize=` that is still asking for a check when the command line ends is refused by name. This is the one family in this document refused for a reason that is not about the bytes. A flag is taken when ignoring it costs speed and refused when ignoring it changes what is produced, and a sanitizer is neither: it is a promise that the program is watched while it runs, so a build that asked for one and was quietly handed a program with no checks in it does not get a slower program or a file of a different shape, it gets a test suite that passes for the wrong reason. The refusal names the sanitizer that was asked for and names `-fsafety=detect`, which is the checking this compiler does have, because somebody reaching for `-fsanitize=address` wants the nearest thing rather than a list of options.

Which names are names is gcc 16's list, with three of this compiler's own added: `alias`, `restrict` and `memory`, which are checks in the table in section 7.7 that gcc has no spelling for, the last of them being a sanitizer gcc refuses outright because it is clang's. A name outside the list gets a different message from a name inside it, because somebody who wrote `-fsanitize=adress` has a typo and somebody who wrote `-fsanitize=address` has a compiler that cannot do it yet. `-fsanitize=all` is refused as a spelling, which is what gcc does: `all` is a value only the negative form takes.

The answer waits for the end of the command line rather than being given where the flag is read, because `-fno-sanitize=` takes a check back and a build whose shared flags ask for one and whose rule for a single file turns it off again has asked for nothing by the end. That command line compiles here. `-fno-sanitize=all` clears everything asked for so far, and a later `-fsanitize=` asks again, since the last word is the one that counts.

The flags that describe what a check does rather than asking for one are taken and dropped: `-fsanitize-recover=`, `-fsanitize-trap=` and both negatives, `-fsanitize-undefined-trap-on-error`, `-fsanitize-address-use-after-scope` and its negative, and `-fsanitize-sections=`. Each of them is an answer about checks that are refused above, so there is nothing left for it to change, and the names in the lists are still held to the same list for the same reason. `-fsanitize-coverage=` is the exception and is refused: it instruments every edge so that a fuzzer knows which input was worth keeping, gcc takes `trace-pc` and `trace-cmp` and nothing else, and a fuzzer whose calls into the coverage runtime were never generated runs blind for the length of the campaign without anything saying so.

`-fsafety=off|detect|enforce|kernel` selects a tier of the memory safety monitor, which is specified in `spec/safe-memory/` and whose flag surface is section 15.4 of that document set. It is a tier rather than a plane at a time because the tiers are the product and the modifiers are how somebody who has read the threat model departs from one. The default is `off`, and a command line without it is compiled by the pipeline it was compiled by before the monitor existed, which is what lets the feature be built in the open. Where a tier covers the same ground as one of the sanitizers above it supersedes it, and asking for both is an error rather than instrumenting twice.

`-flto` is specified in document 09, along with `-fprofile-generate` and `-fprofile-use`. None of that work exists, so the whole `-flto` family is read, checked and recorded rather than acted on. The spellings taken are `-flto`, `-flto=auto`, `-flto=jobserver`, `-flto=<n>` for any n above zero, `-fno-lto`, `-flto-partition=` over `balanced`, `1to1`, `one`, `max` and `none`, `-flto-compression-level=` from 0 to 19, `-ffat-lto-objects` and its negative, and `-fuse-linker-plugin` and its negative. Those are gcc 16's spellings and gcc 16's ranges, and a value outside them is refused the way gcc refuses it, `-flto=0` and `-flto=thin` included.

Taken rather than refused, which is the opposite of what `-gsplit-dwarf` gets in section 4.8, and the difference is what ignoring each of them does. Ignoring `-gsplit-dwarf` means a file a build asked for never appears. Ignoring this means a program that is correct and slower than it could have been, which is section 4.1's hint about speed and which is what every compilation at `-O0` already is. The objects carry the rest of the argument: gcc's `-flto` object holds the bytecode and no machine code at all, so it is only useful to a link that knows about it, and every object written here holds the code, which is precisely what `-ffat-lto-objects` asks gcc for. A build that passes `-flto` to this compiler gets objects that are more usable than the ones it asked for rather than different ones.

One thing has to be settled before the work in document 09 lands. That document calls its scalable form `-flto=thin`, which is clang's spelling of it and is a value gcc refuses, and this driver refuses it too because refusing is what gcc 16 does. Either the form gets a spelling gcc would accept, or taking a value gcc rejects is written down as a deliberate divergence with a reason. It cannot be decided by whoever implements it first.

The profile family is the same work and gets both answers, because it is the one family here that splits down the middle. Reading a profile is taken: `-fprofile-use` and `-fprofile-use=<path>`, `-fno-profile-use`, `-fprofile-dir=`, `-fprofile-abs-path`, `-fprofile-correction` and `-fprofile-partial-training` with their negatives. The path and the directory are recorded on the session for the pass that will read them, and nothing reads them today. Writing one is refused by name: `-fprofile-generate`, `-fprofile-generate=<path>`, `-fprofile-arcs`, `--coverage`, `-fcondition-coverage`, `-fpath-coverage` and `-ftest-coverage`. What is left describes instrumentation that is refused, so it is checked and dropped: `-fprofile-update=` over `single`, `atomic` and `prefer-atomic`, `-fprofile-reproducible=` over `serial`, `parallel-runs` and `multithreaded`, and `-fprofile-values`, `-fprofile-info-section`, `-fprofile-filter-files=`, `-fprofile-exclude-files=` and `-fprofile-note=`. The negative spellings of the refused half are taken, because not instrumenting is what happens.

The line between the two halves is the one section 4.1 draws, and gcc's own objects put it in the same place. `-fprofile-use` on a file with no counts beside it produces an object byte for byte identical to the one no flag produces, so ignoring it is already what gcc does when there is nothing to read, and a build that asks for it here gets the program it would have got anyway. `-fprofile-generate` on the same file grows the code from 71 bytes to 375 and adds 296 bytes of counters, and the program it produces writes a `.gcda` as it exits. Ignoring that means the counts a second pass was going to read are never gathered, the second pass optimizes against nothing, and the build has no way of noticing; `-ftest-coverage` is the plainer case of the same thing, since it writes a `.gcno` beside the object and a coverage report is assembled from files that would not be there. Those are changes to what is produced rather than hints about speed.

Two things are deliberately not copied. gcc warns under `-Wmissing-profile` when it looked for the counts and found none, and this driver does not, because nothing here looks: a warning about a file that was never opened would fire on the builds that have a perfectly good profile as well as on the ones that do not. And `-fauto-profile` is left out of the family entirely rather than taken with it. It reads a profile gathered by a sampling profiler rather than by instrumentation, gcc treats a file it cannot open as a hard error rather than a warning, and a flag whose whole argument is about the file it reads should not be taken by a compiler that will not open it.

## 4.8 Debug info

`-g`, `-g0` through `-g3`, `-gdwarf-4`, `-gdwarf-5` (the default), `-gsplit-dwarf`, `-gno-split-dwarf`, `-fdebug-prefix-map=`, `-ffile-prefix-map=`, `-gz` for compressed sections. `-fno-eliminate-unused-debug-types` and friends are accepted. Document 11 owns the emission.

The levels are a request for how much, and this compiler writes one amount, so `-g1` through `-g3` and the `-ggdb` spellings are `-g` and `-g0` is off. `-gdwarf-4` is refused rather than taken while document 11 writes DWARF 5 and nothing else, because a debugger handed version 5 when it was told version 4 is a worse outcome than a build that stopped.

`-gz` is how the debug sections are compressed. Its values are `none`, `zlib`, `zlib-gnu` and `zstd`, and the bare spelling means `zlib`, which gcc's manual describes the flag without ever saying. The answer is recorded on the session and a value outside that list is refused, because a build that asked for `zstd` and quietly got `zlib` would ship a file its reader may not understand and would have no way of finding out. Nothing acts on the answer while document 11 writes no debug sections at all, so an object built with `-gz=zstd` is byte for byte an object built without the flag, and that is what makes taking it a description of what happens rather than a promise. gcc also passes `--compress-debug-sections=` on to the linker, so that debug sections arriving from objects it did not compile are compressed too. This driver does not, and will not until it writes a debug section of its own: the flag is the compiler's answer about its own output, and a link line that gained an option nobody wrote is a change to what is produced.

`-gsplit-dwarf` is refused. It writes the debug information into a `.dwo` file beside the object, and gcc writes that file whether or not it found anything to put in it, so a build system that declares it as an output or a make rule that depends on it gets a file from gcc and nothing from here. Section 4.1 takes a flag that changes nothing and refuses one that changes what is produced, and a file that never appears is the plainest case of the second there is. `-gno-split-dwarf` is taken, because writing it all into the object is what happens.

`-g` at `-O0` must produce debug info good enough that every local variable is inspectable at every point in its scope, because that is the actual reason people use `-O0`. `-g` at `-O2` produces best-effort location lists and is honest in document 16 about what fraction of variables remain inspectable.

## 4.9 Linking

We do not have our own linker before 1.0. The driver locates one in this order: an explicit `-fuse-ld=<name>`, then `mold`, then `lld`, then the platform default (`ld` on Linux, `ld` on macOS, `link.exe` under the MSVC triples). `mold` first because it is dramatically faster and because a compiler that is 2x faster than Clang while the link takes twelve seconds has not helped anybody.

The driver constructs the link line with the right startup files, the right default libraries, the right dynamic linker path and the right `--sysroot`, per target. This is unglamorous and it is where cross-compilation actually breaks; document 14's corpus catches it.

`-Wl,` passes through and `-Xlinker` passes through, because the linker is a program we run and an argument for it is an argument we hand over. `-Wa,`, `-Wp,`, `-Xassembler` and `-Xpreprocessor` have nowhere to go, because the assembler and the preprocessor are both inside this compiler rather than programs it runs, and there is no command line for them to be added to. They are refused rather than dropped, since a build passing `-Wa,-mrelax` and getting a compilation that ignored it has been told something untrue.

`-pthread` is two things and both of them happen: `_REENTRANT` is defined for the compilation, and `-lpthread` joins the link. The library goes on after every object, because a static link takes from a library only what the files it has already read asked for, so a library in front of the objects answers nothing.

The linker is invoked directly rather than through the system `cc`, which is what makes the line above ours to get right rather than something a driver we did not write decides. Two consequences. The first is that the startup files and the library directories are looked for on the machine rather than configured, because a compiler that has to be told where `crt1.o` is on each installation is a compiler nobody can install. The second is that a `-l` is an input and not a setting: a library written between two files on the command line resolves for the file before it and not for the file after, so the driver keeps objects and libraries in one list in the order they were typed.

`crtbegin.o`, `crtend.o` and the runtime libraries are on the line, found on the machine the same way the startup files and the library directories are. The order is the C library, then our `librucc_builtins.a`, then the machine's `libgcc`, and where two of them define the same name the first of them is the one that answers. That is deliberate in both places it happens. The block routines are in the C library on a hosted target and in ours only for a freestanding one, and glibc writes them in assembly per microarchitecture while ours is a word at a time loop, so a link that took ours would be slower at the routine every program reaches. The wide arithmetic is in ours and in `libgcc` both and the two are ABI-identical on purpose, so which one answers is not a correctness question, and ours goes first because it is ours. A static link puts the whole set inside `--start-group`, because `libc.a` refers to the unwinder and the unwinder refers back into `libc.a`, and a linker walking the list once resolves whichever it reaches first and calls the other undefined. A dynamic link needs no group and asks for `libgcc_s` `--as-needed`, so a program that never unwinds does not acquire a dependency on it.

An internal linker remains a post-1.0 possibility, and document 11 says what would make it worth doing.

## 4.10 Driver-level diagnostics for build systems

Two features that exist purely to make other people's builds debuggable, both implemented in M2, and then the set of questions GCC already answers.

`rucc --print-config` dumps the fully resolved `Options` and `TargetInfo` as JSON: every search path, every predefined macro, every enabled pass, the chosen linker. When a build behaves differently under `rucc` than under `gcc`, this is the first thing to diff.

`rucc --print-pipeline` dumps the passes the level and the `-f` flags between them came to, in the order they will run, one per line with the description the pass gives of itself. It needs no input file, for the same reason `--print-config` does not: the question it answers is about the flags and not about a translation unit.

Beside those two are the questions GCC answers, which a build system asks before it compiles anything and which it asks by running the compiler and reading one line back. `-dumpmachine` prints the target triple, `-dumpversion` and `-dumpfullversion` print this compiler's version, `-print-multiarch` prints the name a distribution files this target under, `-print-file-name=` and `-print-prog-name=` and `-print-libgcc-file-name` print where a named file was found and print the name back unchanged when it was not found, `-print-search-dirs` prints GCC's three lines, and `-print-sysroot` prints the root the headers and the libraries are read under, which is empty for a compile against this machine and is the directory under the cache for a target that is not it. `-print-sysroot-provenance` prints what is inside that root and where each of it came from, which is `spec/cross-compile/13-distribution.md` section 13.5: the sysroot manifest as it stands, one tab separated line per input with its path, the release it came from, the URL that release was fetched from, its sha256, its licence and whether it was bundled, generated or fetched, and nothing at all for a tree that carries no manifest, since a sysroot somebody assembled by hand is one this compiler knows nothing about the origins of. That one is also spelled `--print-sysroot-provenance`, since it is ours rather than GCC's and section 13.5 writes it with two dashes, and a person who types what a document of ours says should not be refused. Each of them writes its line and exits, whatever else is on the command line, because that is what the script reading it expects. The answers are this compiler's own: `-dumpmachine` says the triple we were asked for and not the one GCC was built for, and `-dumpversion` says our version, since a build that switched compilers and is told otherwise will configure itself for the wrong one.

`-save-temps` keeps the files a compilation goes through rather than throwing them away, which is where the preprocessed source in a bug report comes from. The name they are given is the output file with its extension taken off, so `-c a.c -o out/a.o` writes `out/a.i` and `out/a.s`, and a command line that links has one output for however many inputs, so the input's own name goes on the end and `rucc -save-temps a.c` writes `a-a.i`, `a-a.s` and `a-a.o` from the `a` of `a.out`. `-save-temps=cwd` is the same name with the directory taken off, which is the whole of the difference between the two spellings. The bare spelling means `=obj` and not `=cwd`: GCC's manual says the opposite and GCC 16 does this, and following the compiler is what makes a build that read either of them find the files where they are. The object a link reads is kept as well, since it is one of the files that was asked for and the alternative is writing it into a directory that is removed at the end of the run.

Nothing is kept twice. `-E` writes the preprocessed text as its output and so keeps nothing, `-S` writes the assembly and keeps the text that came before it, and an input that arrives already preprocessed has no phase 4 to keep the result of. The two files come out of the run that produced the object rather than from preprocessing and compiling a second time, which is the only way the text a person reads is the text that was compiled: two runs of anything with a `__TIME__` in it are two different files.

`-time` says how long each step took, one line per step on standard error. GCC's two numbers are the user and the system time of a subprocess it ran, and this compiler runs no subprocess for anything but the link, so what is measured is the wall clock of the step and the second column is always zero. The shape of the line is GCC's so that the two can be read next to each other, and the name on it is the input file rather than the program that would have compiled it, since there is no such program here and several lines that all said the same name would not say which file was slow.

`RUCC_LOG=` provides structured tracing at phase and pass granularity via `tracing`, with timing. `-ftime-report` prints the per-phase and per-pass time breakdown in GCC's format, and it is how axis 3 regressions get attributed.

## 4.11 The unstable options

GCC has no `-Z`, which is what makes it the right prefix for the flags that are ours: a measurement or a debugging aid that no build system should ever be passing, spelled so that it cannot collide with a flag we are copying and so that a reader of a command line can tell at a glance which parts of it are compatibility and which are ours. Nothing under `-Z` is promised. One of them may change its spelling or go away in a patch release, none of them appears in `--help`, and every one of them is listed here.

`-Zrule-coverage=FILE` writes which lowering rules the run fired. The file holds one line per rule in the target's rule file, in the order that file writes them, each saying `fired` or `unused` and then the rule file, the line and the pattern. The whole rule set is listed rather than only the part that fired, so that one of these files says what there was to cover as well as what was covered, and one file is written for the whole command line rather than one per input, because the question is what this run of the compiler reached. What reads them is the harness in `tamnd/rucc-compat`, which unions them over a corpus and reports the rules the corpus never reaches; document 20 section 20.9 is the design and what it is for. It changes nothing about the code that comes out, and a file it could not write is an error rather than a warning, because a measurement that quietly did not happen is worse than one that stopped.

`-Zregister-pressure=FILE` writes what the register allocator had to put on the stack. The file holds one line per function the run allocated, in the order it allocated them, each saying how many of the function's values went to a frame slot, how many stores into a slot that cost and how many reloads out of one, and then the name of the function. A comment on the first line holds the totals. Every function is listed rather than only the ones that spilled, for the reason the rule listing gives: a file that says how much was measured is worth more than one that says only what the answer was, and a build that stopped early and a build that spilled nowhere should not look the same. What reads it is `cargo xtask pressure`, which compiles the benchmarks in `bench/safety` with the monitor off and with it on and reports the difference, because `spec/safe-memory/13-performance.md` section 13.1 asks for spill and fill counts as a first class metric and section 5.2.1 of document 05 says why. Like the coverage listing it changes nothing about the code that comes out and a file it could not write is an error rather than a warning.

`-Zverify-each` runs the IR verifier after every pass that changed anything, rather than only where the pipeline would have run it. It is off by default in a release build and on by default in a debug one, because the cost is a walk of the function per pass and the thing it buys is that a pass which breaks the IR is reported by name instead of being found later as a strange failure in the back end. A verifier complaint under it is an internal compiler error and names the pass, which is the whole point of the flag.
