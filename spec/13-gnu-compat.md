# GNU compatibility

This is the document most likely to be underestimated. Document 00 names the GNU extension surface as one of the two things that could actually sink the project, and the reason is that it is not one feature but several hundred, discovered one build failure at a time, with no specification and no complete list.

## 13.1 The obligation

Defining `__GNUC__` is a promise. glibc's headers, the kernel's headers, and a large fraction of every real C project branch on it, and each branch reaches for extensions that must then all work. Document 04 sets `-fgnuc-version=` to the highest version measured to get a real header set and a real corpus through, which is 16.0.0, and raises it on measurement rather than when this document's matrix reaches some line; this document *is* the matrix, and it is the list of promises the claim makes.

There is no version of this project where we implement "the important ones" and stop. `sqlite3.c` alone uses a couple of dozen; the kernel's `compiler-gcc.h` and `compiler_types.h` use over a hundred, and the ones it uses are not the obvious ones.

## 13.2 The matrix

The single most useful artifact in this document is not prose. It is `crates/rucc-gnu/features.toml`, a machine-readable table with one row per extension:

```toml
[[feature]]
name          = "attribute:cleanup"
kind          = "attribute"
gcc_version   = "3.4"
status        = "implemented"        # unimplemented | partial | implemented | rejected
used_by       = ["linux", "systemd", "glibc"]
has_builtin   = "__has_attribute(cleanup)"
tests         = ["tests/gnu/attr_cleanup.c"]
notes         = "Runs the destructor on every scope exit including goto out of the scope."
```

Four things are generated from this file at build time and are therefore incapable of drifting from reality: the `__has_attribute` / `__has_builtin` / `__has_feature` / `__has_extension` responses document 05 needs; the diagnostic for an unimplemented extension, which names the feature and links to its status rather than saying "unknown attribute"; the coverage report in CI; and the test manifest, so a feature marked `implemented` with no test is a build failure.

**Answering `__has_builtin` untruthfully is worse than answering no.** A header that gets `1` and then fails to compile is a much harder failure to diagnose than one that takes its fallback path. This is the whole reason the table is the source of truth.

The initial population comes from three sources: [MaskRay's inventory of the GNU C extensions the Linux kernel uses](https://maskray.me/blog/2025-09-14-c-extensions-used-by-linux-kernel), the GCC manual's attribute and builtin chapters, and the preprocessed output of the corpus in document 15. Grep the kernel's own build for `__attribute__` and `__builtin_` and the ground truth falls out.

## 13.3 Statement, expression and declaration extensions

**Statement expressions** (`({ ... })`) are everywhere in the kernel, every `min()`, `max()`, `container_of()` variant uses one. The hard part is not parsing but semantics: the value is that of the last statement, temporaries live until the end of the enclosing full expression, and a `goto` out of one must run cleanups. They interact with VLAs and with `__attribute__((cleanup))` in ways that need explicit handling. The last statement is still the last statement when it carries a label, so `({ __label__ again; again: n; })` is worth what `({ n; })` is worth, which is how a block that jumps back to its own start and then answers is written and how a block whose value is the address of a label inside it is written. Only a label is looked through that way. A `case` or a `default` in there is a jump into the middle of a statement expression from a `switch` outside it, which gcc refuses and which is not a statement with a value to take.

**`typeof` and `typeof_unqual`** are C23 now, which simplifies matters; `__typeof__` remains as the spelling that works in all modes.

**`__FUNCTION__` and `__PRETTY_FUNCTION__`** are gcc's spellings of `__func__`, described in document 07 along with it. In C the three say the same thing, and the pretty one spells out a signature only in C++.

**Labels as values** (`&&label` and `goto *p`) require an IR-level indirect branch with a successor list and constrain the optimizer: a block whose address is taken cannot be deleted or merged, and its address must survive as a relocatable value. Interpreters use these, and so do a few places in the kernel. The back end compiles both: the address is a `lea` against a label of the function and the jump is through the register holding it, with every possible target on the block so the liveness and the layout both know where control can go, and document 10 section 10.4 says what happens to the values such an edge carries. A label whose address was taken also opens with a landing pad under `-fcf-protection=branch`, since an indirect branch arrives there. The address written into a static initializer is compiled too, which is the relocatable constant rather than the instruction: a block a relocation names is given a local symbol in the section its function was assembled into, carried through the IR as the side table document 08 section 8.3 describes, and the block is live whatever the edges say because the arrival can be in another function. What is not compiled is the difference of two label addresses in a static initializer, which is a distance rather than an address and is tamnd/rucc#1198.

**Nested functions are not supported.** This is the settled exception from document 06. They require executable trampolines on the stack, which is incompatible with every modern hardening measure, GCC's own support is fragile, and the kernel does not use them. `-fnested-functions` produces an error that says exactly this.

**An assembler name on a declaration** (`extern int open (const char *, int, ...) __asm__ ("open64");`) says what symbol the name stands for, and it is read today. This is how the C library redirects a name: `open` under `_FILE_OFFSET_BITS=64` is declared with one of these, every `_FORTIFY_SOURCE` wrapper is the same trick, and a compiler that walks past it links the program against the wrong function or against nothing at all. What it renames is the name and not the one declaration that wrote it, so it is kept where the declarations of a name are merged and it reaches the definition below as well, which matters because the grammar has nowhere to write one on a definition and gcc stops at the brace too. A second name that disagrees with the first is dropped with a warning worded the way gcc words it, since the name may already have been used by then and every use of a name is one symbol. It stands for a `static` and for a local `static` as well as for a name the linker sees, because the question it answers is what to call the symbol and every kind of symbol has one. An object that lives on the stack has no symbol to rename and gcc warns and carries on, which is what happens here and in gcc's words. What it renames reaches the calls the program did not write out as well: a file that declares `memcpy` with an assembler name of its own and then writes `__builtin_memcpy` means the renamed function, since the prefix is how a program picks the library's function out and the declaration is where that function's symbol was said. gcc 16.2.0 emits the renamed name for both spellings, and `gcc.c-torture/execute/builtins/memops-asm.c` is a program that notices. Inside the compiler the two are separate declarations, because the prefixed spelling is one the compiler declares for itself and no file writes a label on it, so the labels a file wrote are collected before anything is emitted and the library name a builtin falls back to is looked up among them. The one reading of this syntax that is not here yet is the local variable kept in a named machine register, `register long r __asm__ ("r0")`, which is a feature of its own rather than a renaming, and it warns in its own words instead of being passed off as the case above: a program that writes one is about to hand that register to an `asm` statement and deserves to be told it did not get it.

**`_Complex` on an integer type** is gcc's own, since C wrote the complex types over the floating ones and never over the integer ones, and it is here today. The type is a pair of whatever the half is and nothing more, so `_Complex char` is two bytes with a byte's alignment and the ABI asks its question of the half rather than of the keyword, which puts one of these in integer registers where a `_Complex double` goes in SSE ones. Every operator over one is the operator over its two halves, which is the same walk the floating pair gets, and the difference is that the two the runtime answers for a floating pair are written out here instead: libgcc's multiply and divide family is written over the floating formats and has no member for an integer half, so there is no routine to call and gcc writes both out too. The multiply is the four products. The divide is Smith's method with an integer division at every step, which is what gcc lowers it to and not a shorter form of it, because an integer division truncates and a program can see which truncations happened, so the shape of the arithmetic is the answer rather than a detail underneath it. The folding follows the same two shapes for the same reason: a program that divides two constants and a program that divides two variables holding those constants are one program and have to agree. `_Complex void`, `_Complex _Bool`, `_Complex _BitInt(N)` and the three decimal types are refused in gcc's words, which name the pair rather than listing keywords that name nothing. The imaginary suffix reaches an integer constant as well, so `4i` is a `_Complex int` whose real half is a zero and `4li` is a `_Complex long`, and `-pedantic` says that neither the type nor the constant is C's.

The rest: `__builtin_choose_expr`, `__builtin_types_compatible_p`, binary conditional `x ?: y`, `case a ... b` ranges, zero-length arrays, arrays of length zero as the last member, casts to union type, arithmetic on `void*` and on function pointers, non-constant initializers for aggregates, designated initializer ranges (`[0 ... 9] = x`), `__extension__`, alignment-of on expressions, complex number extensions including `__real__`/`__imag__`, and empty structs.

## 13.4 Attributes

Both `__attribute__((...))` and `[[gnu::...]]` spellings, on declarations, types, statements and labels, at every syntactic position GCC allows, which includes several that are surprising and which real headers use.

The set falls into groups by what they affect:

**Codegen and calling convention:** `noinline always_inline flatten hot cold noreturn pure const malloc returns_twice naked no_instrument_function no_sanitize target target_clones optimize interrupt`.

**Layout and storage:** `aligned packed section used unused retain visibility weak alias weakref common nocommon mode transparent_union designated_init`.

**Diagnostics and analysis:** `deprecated warning error format format_arg nonnull returns_nonnull warn_unused_result sentinel access counted_by`. The `format` attribute has to actually work. It is the mechanism behind `printf` format checking, which is one of the few warnings that finds real bugs, and the kernel defines its own `printf`-like functions with it.

**Lifetime and cleanup:** `cleanup`, `constructor`/`destructor` with priorities.

**Kernel-specific pressure points:** `no_stack_protector`, `no_caller_saved_registers`, `naked`, `section` combined with linker-script placement, and `error`/`warning` attributes, which the kernel uses to turn a link-time failure into a compile-time message and which therefore must fire at exactly the right point, after optimization, when it is known the call survives.

Four of them are read today for one thing, which is whether the definition exists at all. A function with internal linkage that nothing in the translation unit refers to is not emitted, since nothing outside the file can name it either, and `used`, `retain`, `constructor` and `destructor` are how a program says that something reaches the definition from where the compiler cannot see it: a linker script or the run-up to `main`. The first two do nothing else yet. Both spellings of each are read, and so is the armoured `__used__` form, because a header writes the armour precisely so that a program's own macro cannot take the plain name.

`constructor` and `destructor` also do what they actually ask for, which is to run the function without anything calling it. What comes out is one pointer wide object per function holding that function's address, with internal linkage and a name no C program can spell, in the section the target's start-up code walks. On ELF that is `.init_array` and `.fini_array`, and a priority goes in the section name as `.init_array.00101`, because the linker sorts the numbered sections by name and puts the whole run of them in front of the unnumbered one, so the order comes out right however the objects were linked. A bare attribute is not priority zero and is not any number at all: it runs after every numbered one, and the C library runs the `.fini_array` entries in the reverse of the order it runs the others. On COFF it is `.CRT$XCU`, with a numbered one at `.CRT$XCA00101`, since that linker orders those sections by what follows the `$` and the C runtime walks everything between the `.CRT$XCA` and `.CRT$XCZ` markers. On Mach-O it is `__DATA,__mod_init_func`, whose section attribute is what makes dyld call what is in it, and there is no sorting of any kind, so the entries are written in priority order and run in the order the section holds them. The address is a relocation rather than a value on all three, since where a function lands is the link's answer and not the compilation's.

The attribute travels on whichever declaration wrote it, the way an assembler name and a visibility do, and the entry is emitted only where the same file defines the function. That is gcc's rule and it is what lets a header carry the attribute at all: an entry is an address, and a file that merely declares the function has none to put there. A function may be in both lists, since the two orders have nothing to do with each other. The two things said about a priority are gcc's and are worded the way gcc words them. A number outside nought to sixty five thousand five hundred and thirty five is an error, because the number is the whole of what orders the entries and there is nothing to round it to. A number of a hundred or less is warned about and then honoured, since those are the ones the implementation's own start-up code claims.

A `destructor` on COFF and on Mach-O is refused with `E0519` rather than quietly dropped. Mach-O had a terminator list and dyld stopped running it, so clang registers the call with `__cxa_atexit` from a constructor it writes for the purpose, and nothing in the C runtime a COFF target links against has been confirmed to walk one either. Writing that constructor is a feature of its own rather than a section name, and a program whose clean-up silently never runs has no way of finding out until whatever it was to undo is left undone, which is why there is a message there instead of nothing.

`cleanup` is the third of that group and it is read today. `__attribute__((cleanup(f)))` on a local asks for `f(&object)` on every way out of the block the object was declared in, which is the closing brace, every `return`, every `break` and `continue` that leaves the block, and every `goto` that lands outside it. Two objects in one block are given back in the reverse of the order they were declared, so a program that takes a lock and then takes what the lock protects lets go of them the other way round. A block inside a loop owes the call once for each time round, since the block is entered and left each time. The one way out that does not run it is `longjmp`, which gcc does not promise either. This is what glib spells `g_autoptr`, what systemd spells `_cleanup_free_` and what jansson spells `json_auto_t`, and a compiler that reads past the attribute leaks whatever the handler would have given back, which is the shape of wrongness hardest to notice: the program is correct, it compiles, and it grows.

The call is built where the block is left rather than by a pass that goes looking for the exits afterwards, so the ordinary ones cost nothing to find: the walk already closes a scope, already gives the stack back for a `break` that leaves several blocks at once, and already remembers a `goto` whose label it has not reached yet so that it can put a stack restore in front of the branch. The handler calls go in front of that restore, for the reason the restore is there at all, which is that the handler is given the address of an object the restore takes away. What is turned down is a computed `goto` or an `asm goto` out of a block that owes a call, because which label control arrives at is the address's business and the blocks it leaves are therefore not known: a jump with no calls in front of it would be the silent leak this attribute exists to stop, so there is a message instead. The handler has to be a function declared with a prototype taking one pointer, which is what there is anything to call with an address, and the attribute on anything but an object with automatic storage is dropped with the warning gcc drops it with, since a `static` outlives every block and has no way out to run it at.

The attribute is also the one reference to a function in a C file that is not an expression, and that matters more than it sounds. The handler a header writes is almost always a `static inline` sitting beside the type it releases, jansson's `json_decrefp` and glib's `g_free` wrappers both being that, and nothing else in the file that uses the type names it. The walk that decides which internal definitions are worth emitting is a walk over expressions, so an attribute it does not read is a definition it leaves out, and the program then fails at the link with an undefined reference rather than anywhere near the line that caused it. So a declaration reaches the handler its own attribute names, which is one line in that walk and is the difference between the feature working and the feature compiling.

`alias` is read for that and for the thing it actually asks for, which is a second name. `extern int b __attribute__((alias("a")))` defines `b` rather than declaring it, and what comes out is one more entry in the symbol table at the address, the size, the type and the section `a` already has, with no second copy of the bytes. The assembler is told `.set b,a` under whichever of `.globl` and `.weak` the declaration's own linkage asks for, and the object writer adds the same symbol directly, because both paths have to be saying the same thing and the way to be sure of that is for both of them to read the same list. The binding is the alias's own and the rest is the target's, which is what lets `extern int b __attribute__((alias("a")))` give a global name to a `static`, and a target reached only that way is kept rather than dropped as unreferenced. What is written in the parentheses is a string and not an identifier, deliberately, since it is the name the linker sees: a program may alias something no declaration in the file spells, and one that renamed a name with `__asm__` aliases the renamed spelling.

Two things are refused rather than emitted. The target has to be defined in this same file, which is GCC's rule too and follows from what an alias is: a second name for an address is not a reference to one, so there is nothing to point at and `E0697` says so where the attribute was written. An alias of an alias is refused the same way rather than written as a name pointing at a name. Since the binding travels with the declaration instead of being fixed, `weak, alias` works, which is the form the C library writes and the reason the binding was not fixed in the first place.

Two more are read for layout. `packed` gives a record and a member an alignment of one, and `aligned(n)` says what a record, a member, an object, a function or a typedef is aligned to, each in both spellings and in the armoured form as well. What `__has_attribute` answers about any of these is the status column of the matrix and nothing else, so a row that says unimplemented about an attribute this compiler honours costs a header the path it asked for, and a row that says implemented about one it ignores costs the program a compile.

`aligned` on a declaration is a raise and never a lower, which is the one place it does not agree with `_Alignas`. C23 6.7.5p5 makes an `_Alignas` below the type's own alignment a constraint violation and this compiler diagnoses it, and GCC's attribute below it is ignored without a word, so `int y __attribute__((aligned(2)))` keeps the four an `int` already had. `__alignof__` of such a declaration answers what that object got rather than what its type has, which is the question a program asking it is asking, and it is the answer whether the object is a global, a local or a function. The assembler is told the same number, as the `.p2align` in front of the label and, for a function, as the alignment of the text section as well, because a function sits at a fixed offset inside that section and is at a multiple of two hundred and fifty six only if the section is at one too.

On a typedef the same attribute means something else, and GCC lets it lower. There it says what the type is aligned to rather than putting a floor under it, so `typedef int L __attribute__((aligned(2)))` really is an `int` at a multiple of two and `struct { char c; L x; }` really is six bytes. The size is left alone, which is GCC's answer rather than something skipped here: `sizeof` an over aligned typedef is the size of what it stands for, and GCC refuses an array of one rather than padding the elements out to fit. The alignment is kept on the typedef node in the type table, so two names for one type that asked for different alignments are two types, and where a typedef of a typedef asked twice the nearer one wins, because that is the one the declaration was written with.

An unimplemented attribute warns and is ignored, matching GCC. An attribute whose *silent* ignoring would change semantics (`packed`, `aligned`, `section`, `no_sanitize`, `naked`) is an error instead if unimplemented, because ignoring those produces wrong code rather than slow code. The distinction is a column in the matrix.

`scalar_storage_order` is the third of the layout attributes and is the one that moves nothing. It says every scalar in a record is stored in the byte order it names, so on a target whose order is the other one a load through a member swaps the bytes it read and a store swaps them before it writes them, and a bit-field is counted from the top of the bytes it lies in rather than from the bottom. The record is the size and the alignment it would be without the attribute and every member is at the offset it would be at, which was measured against gcc 16.2.0 on x86-64 before any of it was written. Both of those halves are one statement: the bytes of the record read in the order they lie in, so the first byte of a scalar is its most significant one and the first bit of a bit-field is the top bit of the byte at its address. An argument that names neither `"big-endian"` nor `"little-endian"` is refused with `E0688` in gcc's own words, and the order the target already has asks for nothing at all. The one thing a program may not do is take the address of one of these scalars, which is `E0712`: the bytes are there and they are the other way round, so a pointer to them is a pointer to a value of that type that is not the value the member holds, and gcc refuses it for the same reason. A member that is not a scalar keeps its address, because the address of a nested record or of an array member is the address of the bytes as they lie and an access through it asks its own type which order it is in. That is also the answer to the nested case: a record written as a member of a reversed one keeps its own order and only an array member, which is not a type an order can be written on, is reached by the reversal.

What is left of it is the three shapes the writing refuses rather than getting wrong. A complex member of one of these records is two scalars where the image writes one, an address that the linker fills in has nowhere to say it goes in backwards, and a copy between two records of different orders would move the bytes rather than the values. Each of those is reported where it is reached, and none of them is written by a program in the corpus.

`vector_size` is the one attribute here that builds a type rather than changing a layout, and it is read today. `int __attribute__((vector_size(16)))` is four `int` in a row that every operator works on at once, which document 07 section 7.1 describes, and the attribute is read where the declaration is checked so that the typedef it is nearly always written on declares the vector rather than the lane. An argument that is not one integer constant is refused with `E0689`, and a size of zero, a size that is not a whole number of lanes, a lane count that is not a power of two and a lane type that cannot be one are refused with `E0690`. Each of those is worded the way gcc 16 words it, because a configure script greps for exactly those words. The lane type is the one place this is narrower than gcc: gcc builds a vector of pointers and this does not have one yet, so it says the same thing gcc says about a lane type it does refuse. Reading it was not optional: a compiler that walks past the attribute declares the lane type instead and quietly computes on one lane where the program asked for all of them, which is a wrong answer rather than a missing feature, and twelve programs in the GCC torture suite were getting one.

`mode(M)` is the other attribute here that builds a type, and it is read today. It says the declared type is whatever type this machine has in mode `M`, so `unsigned int __attribute__((mode(QI)))` is an unsigned type one byte wide and not an `unsigned int`. A mode is GCC's name for the shape a value has on the machine rather than a name C has for a type, so it says a width and a register file and nothing about what the type was called, and the class and the signedness come from the type it was written on: the same `mode(QI)` on an `int` and on an `unsigned int` gives two types that disagree about what all ones means. The integer modes are `QI`, `HI`, `SI`, `DI` and `TI`, the floating ones are `HF`, `SF`, `DF`, `XF` and `TF`, the complex ones are the same five letters with a `C`, and `byte`, `word`, `pointer` and `unwind_word` are the three that say what they want rather than naming a width, which is what a portable header writes.

Two of the three classes are settled by a format and not by a width, because a width does not tell one apart from another on every target: eighty bits of x87 and a hundred and twenty eight bits of quad precision are both sixteen bytes on x86-64 and are `XF` and `TF`, which are different modes. The order the floating types are searched in is what makes the answer right where two of them share a format, since `long double` is a `double` on Apple and on Windows and is quad precision on AArch64 Linux, so `DF` has to find `double` first and `TF` has to find `long double` first.

Three refusals are worded the way gcc 16 words them. A name that is not a mode is `E0698`, since every guess at it is a width and a width the program did not ask for is the whole bug this attribute prevents. A mode whose class is not the written type's class is `E0698` as well, because there is no reading of `mode(SF)` on an integer under which something is not thrown away. A mode this target has no C type for is `E0698` with GCC's own sentence, which in practice is `XF` on a machine with no x87.

The fourth refusal is the one place this does not agree with GCC. A vector mode, `V4SI` and the like, is `E0699` with a note pointing at `vector_size`, which is the spelling GCC's own deprecation note points at and the one this compiler does build. GCC builds the vector and warns, and ignoring the attribute instead would declare one lane where the program asked for four, so refusing is the honest answer until a mode can name a vector here.

Written after a `struct`, `union` or `enum` specifier the attribute is ignored rather than refused, because the parser gives the attributes in that position to the tag, which is where `packed` and `aligned` want them. GCC refuses it there. That is this compiler accepting a program GCC turns down, on a program that is wrong under both readings and gets the same type from either, rather than a different answer for a program that is right.

Reading it was not optional for the same reason `vector_size` was not. A compiler that walks past `mode` declares the type as written, which is four times the size for the `SI` on an `unsigned int` that this attribute is nearly always written as, and six programs in the GCC torture suite walk such an object byte by byte and go off the end of what they meant. That is tamnd/rucc#583.

`visibility` is read today and is the one attribute here that says something to the dynamic linker rather than to the static one. `__attribute__((visibility("hidden")))` on a function or an object means the name is still global to the static link, so two files in the same library reach each other by it, and is not in the dynamic symbol table afterwards, so nothing outside the library can name it or replace it. Four strings are written and there are three answers: `default` is exported and interposable, `protected` is exported and binds inside, and `hidden` and `internal` both come out hidden, because `internal` is hidden plus a promise the program makes about never taking the address across a component boundary and nothing here derives anything from that promise. Giving less than was asked for is safe in the way document 04 section 4.6 says accepting `-fstrict-aliasing` is safe, and refusing it instead would stop a build over a distinction this compiler does not make.

It is a fact about the name rather than about one declaration of it, so the first declaration to say something is the one that stands and the definition below a header that said it inherits it. gcc keeps the first one too and warns about a second that disagrees, and that warning is not here yet. An alias answers for itself, since the attribute is written on the alias and an alias is a symbol of its own: `weak, alias, visibility("hidden")` is a name a library keeps to itself while the thing it points at stays exported, which is how the C library writes half of the aliases in it. A `static` name is told nothing whatever it wrote, because a name the static link has already finished with is not in anybody's dynamic table, and gcc writes no directive for one either.

`-fvisibility=` is the same answer asked for over the whole unit instead of one name at a time, and document 04 section 4.6 has the flag. It is a default rather than an override, so an attribute in the source wins wherever one was written, and that is what makes the flag usable at all: a library puts it on the whole tree and marks the dozen names it means to export one at a time. A compiler that let the flag win would export nothing, which is the empty dynamic symbol table of tamnd/rucc#733 arrived at from the other end. Document 11 section 11.3 has what each of the three answers reaches an object file and a listing as.

`weak` is read today and asks for two different things, and which one it is depends on whether the file defines the name. On a definition it says another object's definition of the same name beats this one, which is how a library ships a default somebody may replace, and it comes out as `.weak` with a body under it and as a weak defined symbol in an object. On a declaration of something the file does not define it says the link may leave the name undefined rather than fail, in which case every reference reads a zero address, which is how a library offers a hook a profiler may fill in: the calls are written under `if (hook)` and the test is false when nobody filled it in. That comes out as `.weak` with nothing under it and as a weak undefined symbol, and it is the half that was missing. zstd declares four tracing hooks that way and defines none of them, so thirty of its files would not link at all, and the libraries table had to compile it with `ZSTD_TRACE=0` until the attribute was there. That is tamnd/rucc#1414.

It is a fact about the name rather than about one declaration of it, the way `visibility` above is, so a header may say it once and the definition below may be written as an ordinary definition. One declaration asking for it is enough, which is the rule `used` is under rather than the one `visibility` is under, because what a second declaration would be taking away is not an answer somebody chose between but the whole of what the first one asked for. It is refused on internal linkage under `E0711`, in gcc's words, since a name the linker never sees has nobody to lose to. One difference from gcc: the directive is written for every name a declaration marked, and gcc writes it only for the ones something in the file refers to, so a file that declares a hook and never calls it gets one undefined weak symbol here that gcc does not put in. A linker has nothing to do about an undefined weak symbol no relocation names, and writing every one of them is what lets the listing and the object read the same list rather than each work the answer out for itself.

`gnu_inline` is read today, and what it changes is which of the two readings of `inline` a name is under. Document 07 section 7.13 has both of them. It is not one attribute out of many here because the C library writes it on every inline definition it has, through its `__extern_inline` macro, and a compiler that walks past it emits an external definition of each of them into every file that includes the header: `stdlib.h` alone would give a program its own `atexit`, and the link fails on the first one that clashes. The attribute is a fact about the name rather than about the declaration carrying it, so it puts the declarations already read under GNU's reading as well, which is the order a header is written in. gcc refuses a name whose declarations disagree about whether they are under it, and this takes the reading the program asked for anywhere instead, which accepts a little more than gcc does and never a program gcc would have compiled differently. Both spellings are read and so is the armoured `__gnu_inline__`, which is the one a header writes.

A body under that attribute is offered for inlining and never emitted, so a program that goes on to define the same name itself is supplying the one definition the name gets rather than writing a second one, and gcc takes it, emits the program's body and drops the header's. That is not a corner: glibc's `bits/stdio.h` defines `vprintf`, `putchar`, `getchar`, `fgetc_unlocked` and a dozen more that way whenever `__USE_EXTERN_INLINES` is on, which is every build at `-O1` and above, and a program with its own small C library then hits every one of them it happens to name. micropython's `shared/libc/printf.c` is that program. It is accepted in that order and no other. A body offered underneath a definition is a second body for a name that already has one, two of these offers are two bodies, and a C99 inline definition on either side of an ordinary one is 6.7.4p7 rather than this rule, so all three are still refused, which is what gcc does with each of them and was measured rather than assumed.

`-fgnu89-inline` is the same reading asked for over the whole unit instead of one name at a time, and document 04 section 4.6 has the flag. What a program written against the older reading relies on is that `inline` alone is an ordinary external definition, so a unit holding one gives the rest of the program something to call, and under C's reading it emits nothing and the link fails on a name the program did define. That is not a compiler defect on either side: gcc fails to link the same program the same way, which was measured rather than assumed, and the flag is how the program says which of the two languages it is written in. Twelve of the programs in `gcc.c-torture/execute` write it in their `dg-options` for exactly this reason. The C89 dialects are under GNU's reading whether the flag was written or not, since that is where the reading came from, so `-fno-gnu89-inline` there is asking a dialect to stop being itself. gcc refuses that command line rather than ignoring it, which is one of the few places this accepts something gcc turns down, and it is accepted because there is nothing the flag could have meant there and no program is compiled differently for it.

`transparent_union` is read today and is the one attribute here that changes what a call means rather than what a declaration lays out. Written on a union it says that passing the union and passing its first member are the same thing, which is a promise about the machine and buys two rules about the language. A parameter of the union type is compatible with a parameter of any member's type, so a program may declare the function either way round and assign a pointer to one to a pointer to the other. And a value passed to such a parameter goes into whichever member it fits, so the call site writes the member's type and says nothing about the union.

The member a value goes into is found the way GCC finds it, in two passes. A member whose type the value already has wins outright, wherever it sits in the list. Failing that a pointer member takes a null pointer constant or a pointer that would be assigned to it without a word said, which is what makes a `void *` member the catch-all it looks like, and the first such member is the answer. What comes back is the same unnamed object that a cast to a union builds, so nothing below the checker has to know the parameter is unusual: it is a union value passed by value like any other, and the promise about the first member is what makes the machine agree with GCC about where it goes.

The promise is checked rather than believed. On anything that is not a union, and on a union that is not the size and the alignment of its first member, the attribute is dropped with a warning and the type goes on being ordinary, which is what GCC does and for the same reason: the program is still a program and still compiles. Both places GCC takes the attribute are read, which are after the closing brace of the specifier and on the declarator of a `typedef`, and the second is the one that matters, because it is where glibc writes it.

Where this bites is every program that opens a socket. `sys/socket.h` declares `__SOCKADDR_ARG` as a transparent union of eleven `struct sockaddr_*` pointers and gives it to `accept`, `bind`, `connect`, `getsockname`, `getpeername`, `recvfrom` and `sendto`, so a call passing a `struct sockaddr_in *` is relying on this and on nothing else. gnulib relies on the other half, by assigning those functions to pointers declared with `struct sockaddr *`.

## 13.5 Builtins

Several hundred. Grouped by how they are implemented:

**Constant-folded in the frontend:** `__builtin_constant_p`, `__builtin_types_compatible_p`, `__builtin_choose_expr`, `__builtin_offsetof`, `__builtin_classify_type`, the `__builtin_*_p` numeric classification family, `__builtin_object_size` and `__builtin_dynamic_object_size`.

`__builtin_constant_p` deserves its own note. Its result depends on how much optimization has run, which makes it the one builtin whose value is not a frontend property. The kernel's `BUILD_BUG_ON` and its `min()`/`max()` macros depend on it folding after inlining, so it must be an IR intrinsic that later passes fold, not a frontend decision, and it must fold to `0` rather than being left unresolved at `-O0`.

`__builtin_object_size` and `__builtin_dynamic_object_size` are what `_FORTIFY_SOURCE` is built on, which means glibc's headers stop working correctly without them: a fortified `string.h` turns every `memcpy` into `__builtin___memcpy_chk` with `__builtin_object_size` of the destination as the fourth argument, so a compiler with no answer for this one has no answer for any copying function either. Both answer how many bytes lie between an address and the end of the object it is inside. The second argument is two bits: the low one asks about the closest member containing the address rather than the whole object it is in, and the high one asks for the smallest answer rather than the largest, so an address whose object is not in sight answers `(size_t) -1` for the kinds wanting the largest and zero for the kinds wanting the smallest. That pair is what the idiom in a fortified header compares against to decide whether to check the copy at all. The two names differ in what a program may do with the answer rather than in what the answer is, since the dynamic spelling is allowed to come back as something computed while the program runs, and a constant satisfies both.

What the front end answers is what the expression says rather than what an analysis found. A declared object, a string literal or a compound literal, with members and constant subscripts on top of it and a constant displacement added to the whole, is an address whose object is read off the layout of a type; a dereference is not, because what is behind `p->f` is a fact about where `p` came from, and neither is the flexible array member at the end of a structure, whose whole meaning is that its length is not written down. The storage duration does not matter, unlike in a constant expression, which is the point: the buffer a program most wants checked is the one on its own stack. The address is not evaluated, which is the rule `sizeof` follows and for the same reason. Two deliberate differences from gcc 16.2.0, both measured rather than assumed: gcc gives up on the subobject question as soon as pointer arithmetic is involved at `-O0` and this answers precisely, which is the number gcc itself gives once its object size pass has run at `-O1`; and gcc refuses either name in a static initializer, because it folds them after the front end has decided what a constant expression is, while here the answer is a constant by the time anything asks.

**Answered as comparisons in the frontend:** the floating point classification family, which is `isnan`, `isinf`, `isfinite`, `isnormal`, `signbit`, `isinf_sign`, `fpclassify`, the six ordered comparison macros and the width bearing spellings of each. None of these may become a call, because `math.h` defines the macros of those names as exactly these builtins and no library defines a function under any of them, so a compiler that lowered one would be emitting a reference to a name that does not exist. Each becomes a comparison against a constant of the format instead: the infinities for `isinf` and `isfinite`, the smallest normal for `isnormal`, and the value being unordered with itself for `isnan`. `signbit` and `isnormal` ask their question of the bits rather than of the number, since the encoding of a value whose sign bit is clear rises with the value in every format here, which is both cheaper and the only way to ask it of the eighty bit format on x86-64, where nothing lowers a cast from an integer back into it. Each is a node of its own rather than a rewriting into the operators, because the value is compared more than once and `isnan(f())` calls `f` once. Each folds where its operand is a constant, which is what lets one initialize an object with static storage duration. `fpclassify` is the one with more than two operands: five integer constant expressions in front of the value, one of which is the answer, and gcc requires them to be constants for the same reason this does.

**IR intrinsics:** the overflow-checked arithmetic family (`__builtin_add_overflow` and friends, including the `_p` predicate forms), `__builtin_expect` and `__builtin_expect_with_probability`, `__builtin_unreachable`, `__builtin_assume_aligned`, `__builtin_prefetch`, `__builtin_trap`, the bit manipulation family (`clz ctz popcount parity ffs clrsb bswap`, each in three widths), the absolute value family in its signed, unsigned and widest spellings, `__builtin_return_address` and `__builtin_frame_address`.

Two of those intrinsics are answered in the front end today rather than built. `__builtin_expect` and `__builtin_expect_with_probability` say which way a branch is expected to go and nothing reads a branch weight until the optimizer, so the value handed back is the first argument, with `Opcode::Expect` left in the IR for the day something reads one. Leaving them as calls in the meantime was not an option, because a builtin nothing lowers reaches the assembler as a call to a name no object file defines, and glibc writes `getc` and `putc` in terms of `__builtin_expect` as soon as `__OPTIMIZE__` is set, so every optimized program that included `<stdio.h>` failed to link on a name it never wrote.

What happens to a side effect written into the hint is decided by the first argument, which is gcc's answer rather than a rule anybody would design. A first argument that is an integer constant expression folds the whole call where it is written and takes the hint with it, so `__builtin_expect(5, side())` never calls `side` and `sizeof(__builtin_expect((char)1, 1))` is still eight. A first argument that is not one leaves the hints standing, evaluated in the order they were written with the value last, which is a comma expression and is what this builds. That was measured across five shapes at `-O0`, `-O1` and `-O2` on gcc 16.2.0, which gives the same answer at all three, and it is matched rather than tidied up because the point of a builtin is that a program written against gcc gets gcc's answer. `gcc.c-torture/execute/pr85156.c` is a program that notices, since the value it returns is an increment written inside a hint.

`__builtin_unreachable` is the third of that kind and is a promise rather than a hint. It becomes a node with nothing under it and lowers to `unreachable_hint`, which the code generator writes no instruction for, so the promise costs nothing to honour and reading it later costs nothing to add. What is deliberately not done with it is treating the rest of the block as dead. gcc does, and that is an optimization and not the meaning: the promise being false is undefined behaviour, a compiler may do anything at all with the code below, and continuing to translate it is the choice that keeps a program built at `-O0` behaving the way its author watched it behave. The case the builtin is usually written for arrives at the right instruction anyway, because a `switch` whose default arm is `__builtin_unreachable()` and which has no return after it is a function body that runs off the bottom, which the walk already ends with the `unreachable` terminator. That terminator writes no instruction either, and the epilogue lands at the end of the block the way it does on any block that goes nowhere, which is what gcc 16.2.0 emits at `-O0` for both spellings.

The rest of the intrinsics are not built yet, and a call to one is refused where it is written with `E0686` naming the builtin. That is the general rule rather than a list: a row in `crates/rucc-gnu/features.toml` whose status is not `implemented` and which carries no `library` is a name nothing here builds anything for and nothing outside here defines, so a call to it would go to a symbol no object file has. Refusing it is what `__has_builtin` already answers for the same set, and the alternative is a linker asking the programmer to supply a builtin. What the rule does not touch is the name: `sizeof` does not evaluate its operand, so the type of a call to one of these is still answered, and a program that defines the name itself gets the function it wrote.

**Library calls with known semantics:** the `mem*` and `str*` family, the math functions, so that `strlen` of a literal folds and `memcpy` of a small constant size becomes loads and stores. `-fno-builtin` and `-fno-builtin-<name>` disable this per document 04.

The first of that family is the integer absolute value, which is `abs`, `labs` and `llabs`. These are the family where the plain name is enough: the names are reserved to the implementation by C23 7.1.3, so a program that writes one means the function the library promises and a compiler that knows what that one does may write the arithmetic instead of the call. What it writes is the sign of the value spread over every bit, an exclusive or with that, and a subtraction of it, which is four instructions with no branch and no condition code. The most negative value comes back as itself, because that is what the arithmetic gives and its magnitude is not representable, which is where C says the result is undefined and where gcc's own pair of instructions lands too.

The plain name is only the library's where nothing else has taken it, so the declaration is looked at as well as the name. It has to be a function rather than a pointer some object holds, it has to have external linkage, and its type has to be the one the library gives that name, spelled with a prototype. A `static long long llabs(long long)` is a program meaning its own function and gcc calls it, measured on 16.2.0. `-fno-builtin`, `-fno-builtin-<name>` and `-ffreestanding` are the same question asked from the command line, and the last of the three is there because a freestanding program has no C library for the name to be the name of. The `__builtin_` spellings go on meaning the library's function through all of it, which is what the prefix is for and what lets a freestanding build reach one deliberately.

Nothing here waits for a constant. gcc expands the call inline at `-O0` and so does this, because the point is not that `llabs(-1)` is one, it is that the call does not happen: `gcc.c-torture/execute/20021127-1.c` defines `llabs` to abort and expects never to reach it.

Which plain names are the library's depends on the dialect, and the rule was measured against gcc 16.2.0 one name per dialect. Under a GNU dialect every name in the family is the library's whatever standard it came from, so `gnu89` expands `llabs` and `gnu17` expands `uabs`. Under a strict ISO dialect a name is the library's only from the standard that added it, so `-std=c89` writes a call to `llabs` and `-std=c23` writes a call to `uabs`, since those names belong to the program there. `abs` and `labs` are C89, `llabs` and `imaxabs` are C99, and `uabs`, `ulabs`, `ullabs` and `umaxabs` are C2y, which answer the magnitude in the unsigned type of the same width so that the most negative value has one. `gcc.c-torture/execute/builtins/uabs-2.c` is compiled with `-std=c2y` and defines all four to abort when called from inside `main`.

The rest of the math family is the opposite arrangement, and the difference is the link line rather than anything about the arithmetic. `fabs` and `copysign` are the sign bit and nothing else, so gcc emits no call for either on any target and leaving one behind would turn a program that never asked for `-lm` into one that does not link. `ceil`, `floor`, `trunc`, `round`, `rint`, `nearbyint`, `fmax` and `fmin` are not like that. gcc emits `jmp ceil` for `__builtin_ceil` on x86-64 at the default architecture, measured on 16.2.0, and reaches the `roundsd` instruction only under `-msse4.1`, which is not what a program gets unless it asks for it. So a program that writes one of these and links without `-lm` fails under gcc too, and each of the eight is a row carrying a `library`, in three widths, which makes the call a call to the plain name the way every other library builtin is.

What is added on top of the call is the answer where the arguments are constants, which is what a static initializer written with one needs and is the only thing a call cannot be. `double x = __builtin_ceil(1.5);` at file scope initializes an object with static storage duration, so there is no point in the program at which a call could be made, and gcc folds it. Six of the eight fold: the four that take a number to an integer and the two that pick one of two. The direction is part of the name rather than a mode the operation ran under, so nothing here reads a rounding mode, and a half goes away from zero for `round` rather than to even, which is the one place C and the default rounding of IEEE 754 disagree.

The other two are deliberately not folded, and so is one case of the two that are. What `rint` and `nearbyint` answer depends on the rounding mode the program is running under, which is not known until it runs, and gcc refuses `static double x = __builtin_rint(2.5);` as not a constant expression for exactly that reason. `fmax` and `fmin` of a nan are the same refusal turned around: the answer is the other operand, which is 7.12.12.2 and is the library's rule rather than the machine's, and gcc will not fold that one either. Matching gcc on what is a constant expression matters more here than answering more than it does, because the programs that notice are the ones whose initializers either compile or do not.

Both spellings again, for the reason the absolute value family has them. `math.h` declares `ceil` and glibc's copy of it does not spell the prefixed name anywhere, so the plain name is the one every program that includes the header reaches, and the same three questions are asked of its declaration before it is taken to mean the library's function. `-fno-builtin` and `-fno-builtin-ceil` turn that off and leave the prefixed spelling alone, measured against gcc 16.2.0 one flag at a time.

Last of the math family are the three that name a half of a complex value, which are `conj`, `creal` and `cimag` in three widths each. These are `~`, `__real__` and `__imag__` under the names `complex.h` gives them, and the operators were in the language before the names were, so what is added here is the names rather than the operation. `~` on a complex operand is the conjugate and has been since gcc had complex types at all, which is the reading the front end takes: the real half stands and the imaginary one is negated, so there is one negation in a conjugate where a complex negation has two. Nothing about any of the three needs a library, and all three are in the math library rather than the C one, which is the arrangement `fabs` is in and which means a call left behind would not link for a program that never asked for `-lm`. So each is a row carrying a signature, the call is checked against it the way an ordinary call is, and the answer replaces it. Both spellings again, and the same three questions of the declaration behind the plain one. What a value of the `long double` width does below the front end is issue 326 and is the same wherever that type is written.

Before those come the stdio family, which is seventeen rows. Eleven are handed a stream, and those are `fprintf`, `vfprintf`, `fputs`, `fputc`, `putc` and `fwrite` with the `_unlocked` form of five of them, and the other six are `vprintf`, `vsprintf`, `vsnprintf`, `printf_unlocked`, `puts_unlocked` and `putchar_unlocked`. The stream is why none of them was in the table, including the six that do not take one, since a family half declared is worse than one not declared at all: a signature is written out of a closed set of words, and none of those words said `FILE`. gcc has no answer for that word either. Its type for one of these is a copy of `void *` under another name, which is why `extern __typeof__(__builtin_fputs) f;` beside `extern int f(const char *, FILE *);` is two conflicting declarations on 16.2.0 and the note it prints about the first one says `int(const char *, void *)`. So the set grows one word, which the reader turns into `void` and which the build refuses without a star after it, since a parameter of type `void` is one the reader drops and the prototype would come out an argument short of what the builtin takes. What a program hands over is the `FILE *` its own `stdio.h` declared, and the conversion into a `void *` is one C already allows and has nothing to say about.

What none of that group does yet is fold. `printf("hello world\n")` is `puts("hello world")` under gcc and `fprintf(f, "%s", s)` is `fputs(s, f)`, and `gcc.c-torture/execute/builtins/printf.c`, `fprintf.c` and `fputs.c` are three programs that define the library function to abort and check that the call never happens. All three build and run here at `-O0`, where the definition is guarded on `__OPTIMIZE__` and gcc folds nothing either, and above that they reach the abort. That is issue 1636, and it is a rewrite over a format string rather than anything about the declaration, so it belongs where the other library folds are.

Last of the library family are the sixteen `_chk` spellings, which are what a fortified glibc header turns every copy and every formatted write into. Under `_FORTIFY_SOURCE` the `memcpy` a program writes becomes `__builtin___memcpy_chk` with `__builtin_object_size` of the destination behind it, so a program that includes `string.h` on a distribution's compiler reaches these whether its author has heard of them or not. Ten are the copying and concatenating ones, which is `memcpy`, `memmove`, `mempcpy`, `memset`, `strcpy`, `stpcpy`, `strcat`, `strncpy`, `stpncpy` and `strncat`, and six are the formatted ones, which is `sprintf`, `snprintf`, `vsprintf`, `vsnprintf`, `printf` and `vprintf`.

Each is a library builtin whose library name is the checking function, so a call to one is a call to `__memcpy_chk` and the object size argument goes with it. The name is the one place the family reads like an exception and is not one, since the rule is the same one every library builtin follows: `__builtin___memcpy_chk` with `__builtin_` taken off is `__memcpy_chk`, and the three underscores in the middle are two of the builtin's prefix and one of the library's. The three `v` spellings are the first rows in the table whose signature names `__builtin_va_list`, which is a type the target chooses the shape of rather than the width of, and which is why a parameter in a signature is adjusted the way a parameter in a declaration is: it is an array of one on x86-64, so the prototype has to hold the pointer that array decays to or no argument could ever match it.

A call whose object size argument says nothing is known is the plain library call, which is what the checking function would have done with it anyway. `(size_t) -1` is what the checking function reads as do not check and what the fortified header passes when the destination's object is not in sight, so the call it was going to make is the function it guards with a fourth argument nobody reads, and the argument goes along with the name. Ten of the sixteen fold that way and the six formatted ones never do, however constant the size is, because the flag argument is a second thing they were asked to do: a `%n` in a format the program can write to is refused whether or not a size is known, and `printf` will not refuse it. Both halves of that were measured on gcc 16.2.0 rather than read off a manual.

The fold is in the walk to the IR rather than in the front end, which is where the name of the function to call is decided and is the one thing the checker cannot do, since interning a name it did not see needs a table it only borrows. What decides it is the all ones value of the target's own `size_t`, so the width is worked out where the target is known and `rucc_sema::unchecked_name` holds only the half that is a fact about the name.

Where this lands relative to gcc is at `-O1` rather than at `-O0`, and the reason is the difference recorded above rather than a second one. gcc answers `__builtin_object_size` in a pass that has not run at `-O0`, so at that level the size argument is not yet a constant and none of the ten folds; here the answer is a constant by the time anything asks, so the fold happens wherever it is going to happen. Measured on 16.2.0 over twenty shapes at all three levels, the calls rucc emits and the calls gcc emits are the same list at `-O1` and at `-O2` but for one, which is a `__mempcpy_chk` whose result is dead and which gcc turns into `memcpy` rather than `mempcpy` on that account. That is a rewrite on top of the fold and not part of it: with the result live, gcc folds name to name for all ten.

`__builtin_setjmp` and `__builtin_longjmp` are a pair rather than two builtins, and neither of them is the library function whose name it borrows. The save writes down where the function is and answers zero, the restore reads that back and goes there, and the save answers one the second time round. There is no function of either name for a call to reach, the buffer is five words rather than a `jmp_buf`, and nothing about the signal mask is promised by either, which is what makes them cheap enough for the exception machinery and the interpreters that write them. What the buffer holds on x86-64 is the frame pointer, the address to come back to and the stack pointer, in that order, which is the shape gcc 16.2.0 writes at `-O0` and is measured rather than read off the manual.

The second argument of the restore has to be the constant `1`. The library's `longjmp` carries a value back and turns zero into one, because a `setjmp` answering zero twice would say it had not been jumped to, and this pair carries nothing: what the save answers is decided by which way control reached it. So the argument is a place-holder with one allowed value, and gcc refuses every other one in a sentence of its own, which `check/builtin/jump.rs` reports under `E0710`.

Each becomes one instruction in the IR, `setjmp_marker` and `longjmp_marker`, and the save is the one instruction here whose value depends on how control reached it. It is one instruction rather than a branch and a block nothing jumps to, because the edge a restore travels is not an edge of this function: it is written into the buffer and taken while the program runs, so a block standing where control comes back would be a block nothing in the graph reaches and the first pass to walk the edges would take it away. The restore is not a terminator either, for the same reason, so what follows it is written and never reached.

What the pair costs the function it is written in is that nothing stays in a register across the save, and that is said at both ends of the compiler. Coming back through the buffer puts two registers back and no others, so anything else the program still wants has to be in the frame those two reach. The back end says it to the register allocator with a write of every register the allocator hands out, both files, on an instruction carrying nothing else, which is the same thing a call already says about the registers a callee may destroy. The walk to the IR says it about the locals, by giving every automatic object in such a function a slot rather than keeping it in a value.

The second half of that is the one that is easy to miss, because where it goes wrong is not about registers at all. A local kept in a value is a local the SSA construction renames, and what it renames each read to is the write that reaches it along the edges the graph has. The edge a restore travels is not one of those, so the last write to run before control came back was not on any path the renaming looked at, and the read answers a value the program has overwritten. `gcc.c-torture/execute/pr60003.c` is exactly that, a variable set to zero before the save and to one inside the loop after it where the branch the restore comes back to has to see the one. A slot has no such question in it, since a load reads whatever the last store wrote whichever way control got there.

The save writes four words rather than the three gcc writes, and the fourth is where the answer arrives. gcc has no word for the answer because it puts a block after the point the restore arrives at that sets the answer to one, and a machine IR whose blocks are walked from the entry has nowhere to keep such a block: the register allocator lays a function out in the order it is going to be emitted in, and a block no edge reaches is not in that order. So the save writes a zero into a word of its own frame, puts the address of that word in the buffer, and reads the word back on the instruction after, and the restore writes a one through the address it finds there. One load answers zero on the way past and one on the way back, and neither path has to agree with the other about a register. None of the four words is an interface, and a buffer one compiler wrote was never going to be one another compiler could come back through.

Writing down where control comes back to is what splits the block. Everything after the save goes into a new machine IR block and the address of that block is what goes in the buffer, because an address points at a label and a block is the only thing in this representation that has one. Two more things follow from a function saving a place. It keeps a frame pointer whatever the flags say, since the epilogue has to find the caller's frame after control has come back and the restore puts back nothing else that would reach it. And it is not a leaf whatever it called, because what a leaf buys is the red zone, and by the time a restore arrives whatever the function called and whatever that called have each written over those bytes.

The restore takes everything out of the buffer before it puts anything back, and holds it in registers it names outright rather than in values the allocator places. Both of those are about the same moment: a value the allocator sent to the stack is reached through the stack pointer, and between the instruction that moves the stack pointer and the jump there is no stack this function owns any more. The jump reads the stack pointer and the frame pointer as well as the address it goes through. Neither of the two is printed, since the target spells an indirect jump with one argument, and they are there because the code control arrives at reaches its frame through them: without them the two instructions that put them back write registers nothing reads, and the scheduler at `-O2` is free to move the jump in front of both.

**Atomics:** the `__atomic_*` family with memory orderings and the legacy `__sync_*` family, mapped onto document 08's atomic instructions.

The accesses and the barrier are built: `__atomic_load_n`, `__atomic_store_n`, `__atomic_thread_fence` and the legacy `__sync_synchronize`. Each is a family rather than a function, so none has a signature in the table: the type of what is read or written comes from the pointer it is handed, and the result of a load is whatever that pointer points at with the qualifiers dropped. A pointer to something that is not an object type, or a store of a value that will not convert to what the pointer points at, is refused where it is written. `__atomic_load` and `__atomic_store` without the suffix are built too, and are the same two accesses for an object too big to come back in a register: the value travels through a second pointer the caller hands over rather than being taken or answered. The access through that second pointer is a plain one, because the object at the end of it is the caller's own and no other thread has its address, which is the entire reason the shape exists.

The ordering is an argument rather than part of the name, and the standard says it has to be a constant, so it is folded and read at the point of the call. The numbers are the ones the standard fixes and gcc uses: relaxed is 0, consume is 1, acquire is 2, release is 3, acquire release is 4 and sequentially consistent is 5. Consume is read as acquire, which is what every compiler in production does and what the committee has proposed removing the distinction over. An ordering an operation cannot carry, a release on a load or an acquire on a store, and an ordering that is not one of the six at all, are `W0333` and the operation is read at the strongest, because the alternative is refusing to compile a program gcc compiles and the strongest ordering is never the wrong answer for correctness.

The compare and exchange is built in four spellings: `__atomic_compare_exchange_n`, `__atomic_compare_exchange` and the legacy `__sync_bool_compare_and_swap` and `__sync_val_compare_and_swap`. All four compare what is at the address against what the program expected and write the desired value there if the two matched. The two `__atomic_` ones answer whether they matched and write what was actually found back over the expected object when they did not, which is the whole reason that operand is a pointer, and the difference between the pair is only where the desired value comes from: the suffixed one takes the value and the unsuffixed one takes a pointer to it. The two `__sync_` ones take the expected value itself and are sequentially consistent by definition, so neither has an ordering argument at all, and what they differ in is the answer, one giving whether it matched and the other giving what was found.

Two of gcc's arguments are read and then dropped. The `weak` flag says a spurious failure is acceptable, and the machine instruction here does not fail spuriously, so a strong exchange is a legal answer to a weak request and no target this compiler has would give a different one. The failure ordering is folded and diagnosed like any other ordering, including the rule that it may not be a release, and then dropped, because what it selects on x86-64 is the same instruction the success ordering already selected.

The write back is a branch rather than a store the program always makes, and that is not an optimization. `__atomic_compare_exchange_n(&x, &x, v, 0, o, o)` is a legal program in which the object and the expected object are the same object, and a store made whether or not the exchange succeeded would put the old value back over the value the exchange had just written. So the store sits in a block reached only when the comparison failed, which is what the operation actually says.

The read modify writes are built for six of the operations and twenty eight of the names. The exchange is `__atomic_exchange_n` and the legacy `__sync_lock_test_and_set`, with `__atomic_exchange` beside them passing both values through pointers for the reason the accesses above do, the addition and the subtraction are `__atomic_fetch_add` and `__atomic_fetch_sub` with `__atomic_add_fetch` and `__atomic_sub_fetch` beside them and the four `__sync_` spellings of the same four, the bitwise four are `__atomic_fetch_and` and `__atomic_fetch_nand` and `__atomic_fetch_or` and `__atomic_fetch_xor` with the four `_fetch` spellings beside them and the eight `__sync_` ones, and `__sync_lock_release` is the twenty eighth. Each of them reads the object, does something to what it read, and writes the answer back, with nothing able to get between the three. Which of the two spellings of an operation a program wrote decides only which value it gets: the machine instruction answers what was there before, and a name that asked for what is there afterwards gets that instruction with the arithmetic written behind it, which is an ordinary add or subtract or bitwise operation that costs nothing when nothing reads it. The exchange has one spelling rather than two, because the value afterwards is the value the caller just handed over and no name in the family asks for it.

The two lock names are the two halves of a lock rather than full barriers, and they are the only two in the older family that are not sequentially consistent. `__sync_lock_test_and_set` is an exchange at acquire and `__sync_lock_release` is a store of zero at release, which is what gcc documents them as and what makes them the pair a spin lock is written out of. The zero is a zero of the object's type rather than an integer, so the name works on a pointer object and a floating one the way it works on a counter.

The object may be a pointer, and what happens then is worth writing down because it is not what the arithmetic in the rest of C would give. gcc does not scale the operand by the size of what the pointer points at: `__atomic_fetch_add` of one on an `int *` moves it one byte and not four, measured on 16.2.0. That is matched rather than corrected, since the whole point of the family is that a program written against gcc gets gcc's answer, and the kernel and glibc are the programs in question. The operand is converted to the type of the object and the addition happens on the address as a number.

The nand is the one of the six that is two operations rather than one, and it means the and with every bit of the answer flipped. That is what gcc has meant by the name since 4.4 and both families agree on it, which is worth saying because the name reads as though it might mean the other order and the older documentation for a while did not say.

`__atomic_test_and_set` and `__atomic_clear` are the same lock again over a byte, and they are built as their own pair rather than as the two lock names with a different argument. The object is one byte whatever the pointer they were handed points at, including a `void *`, which is the standard's reading rather than a liberty taken here: the object is an `atomic_flag` and there is no way to read or write one except through these two names, so the type the pointer carries says nothing about the access and the width is the implementation's to fix. gcc 16.2.0 writes a one byte exchange through an `int *` here too.

So is the value that means set, and this writes a one. Writing it in one place is the whole point, since what makes the pair work is that `__atomic_clear` puts back exactly the byte `__atomic_test_and_set` reads as evidence the flag was already held. What the first answers is a comparison of what it found against zero rather than the byte itself, because the type of the call is `_Bool` and a byte that is neither zero nor one is not one. gcc answers the raw byte, and the two agree wherever the object is only ever touched through this pair, which is the only way C says it may be touched at all.

`__atomic_always_lock_free` and `__atomic_is_lock_free` are built and are the two names in the family that are not operations. Both ask whether an object of a given size and alignment is one the machine handles without taking a lock, and both are folded to a constant here: the size has to be a power of two no wider than the widest access this compiler writes an instruction for, which is eight bytes on every target, and the pointer says what the object is aligned to or is null to mean the type's own alignment. gcc lets the second one become a call into libatomic when it cannot decide; there is no libatomic behind this compiler, so both give the same answer, which is the stronger of the two and is never wrong where it says yes. A size the compiler cannot fold is answered no rather than refused, because the header idiom these appear in writes a size that is a macro from some other platform.

`__atomic_signal_fence` is the one name in the family that is not built, and it is deliberately out. The IR's fence is a barrier the machine executes, and a signal fence has to constrain the compiler and emit nothing, so the two are not the same instruction with a different argument.

What an ordered access becomes on x86-64 is document 10's business, but the short of it is that the hardware already gives every load an acquire and every store a release, so the only ordering that costs an instruction is a sequentially consistent store, which is the plain store and a barrier behind it. A compare and exchange is `lock cmpxchg` at the width of the object and a byte that reads the condition code, whatever ordering was asked for, since a locked instruction is a full barrier on this machine and there is no weaker form to fall to. A read modify write is `xchg`, which needs no prefix because an exchange against memory is locked whether it was asked or not, or `lock xadd` with a subtraction reaching it through a negation, and for the four bitwise operations, which the machine has no single instruction for, it is a loop around the compare and exchange written in the back end before the selector runs.

**Varargs:** `__builtin_va_start`, `va_arg`, `va_end`, `va_copy`, plus `__builtin_va_arg_pack` and `__builtin_va_arg_pack_len` for the FORTIFY wrappers.

The pack pair is the one entry above that is accepted rather than done, and the reason is worth writing down here rather than only in the code. Neither is a function: the first stands for every anonymous argument of the function around it and the second for how many of those there were, and gcc fills both in while inlining that function into its caller, which is why gcc accepts them only inside a function marked `always_inline`. This compiler does not inline, so nothing here could fill them in. What it accepts instead is the one position where nothing has to be filled in, which is a variadic definition that nothing is emitted for: GNU's `extern inline` gives exactly that, the body is read, checked and then dropped, and a call in a dropped body never reaches the IR and never has to be given a meaning. All three headers that use the pair, `bits/stdio2.h`, `bits/wchar2.h` and `bits/fcntl2.h`, write it in a wrapper declared `__extern_always_inline`, so the one position this accepts is every position anybody writes. Anywhere else it is refused, since anywhere else the call would reach the IR as a call to a name no object file defines. What that costs is the fortification and nothing else, and it costs it in the company of every other wrapper in those headers: the fortified `memcpy` needs no pack, compiles, and still ends up as a call to `memcpy` rather than to `__memcpy_chk`, because it is an inline definition and none of those is emitted either. Fortifying anything at all needs an inliner, and that is one piece of work rather than two.

**Target-specific:** the x86 intrinsic headers (`immintrin.h` and the tree below it), the ARM NEON intrinsics, and the RISC-V vector intrinsics. This is a large body of work that is mostly mechanical and mostly generated from the same tables that drive instruction selection. It is required by any project doing SIMD by hand, which includes every video codec and most cryptography.

**Not implemented and diagnosed as such:** the OpenMP builtins, the coroutine builtins, and the C++-specific ones.

Whatever a builtin lowers to, something has to declare it first. No header does and none could, since the name is reserved to the implementation and that is the whole point of the prefix, so the compiler declares it. The type comes from the same `features.toml` the matrix above is built from, one row per builtin carrying the prototype as a string, which is what keeps the answer to `__has_builtin` and the type the builtin is called at from being two lists that drift. It is a string rather than a structure because `size_t` is a different type on two targets and the table has no target, and the vocabulary it may be written in is closed and checked by that crate's build script, so a typo fails the build rather than the compile of whoever first calls the builtin. A builtin whose type depends on what it is handed has no signature and the absence is the record of that: `__builtin_constant_p` takes anything, the overflow family takes three integer types that need not agree and does its arithmetic at whichever type represents every value of all three, and the atomics are a family rather than a function.

The declaration is made when a name is looked up and not found rather than before the first line is read, which is where GCC makes it. The two reach the same place, because the declaration goes in the file scope either way and a program that declares a builtin itself has its own declaration found first, and the difference is a couple of thousand names that never enter the symbol table of a translation unit that does not use them.

## 13.6 Pragmas

`#pragma GCC diagnostic push/pop/ignored/warning/error` with the full warning-name vocabulary, `#pragma GCC visibility`, `#pragma GCC optimize` and `#pragma GCC target` (both of which change per-function codegen state and therefore become function attributes in the IR, per document 04's rule about per-function flags), `#pragma pack`, `#pragma weak`, `#pragma once`, `#pragma message`, `#pragma STDC FP_CONTRACT/FENV_ACCESS/CX_LIMITED_RANGE`, and `_Pragma`'s destringizing operator.

Unknown pragmas are ignored silently in the default mode and warned under `-Wunknown-pragmas`, matching GCC.

## 13.7 The flags the kernel forces

The kernel's build sets a specific and unusual flag set, and every one of these must work, not merely be accepted:

`-ffreestanding`, `-fno-common`, `-fno-strict-aliasing`, `-fno-delete-null-pointer-checks`, `-fno-stack-protector` (per-file, in some places), `-mno-red-zone`, `-mcmodel=kernel`, `-fno-asynchronous-unwind-tables`, `-fno-omit-frame-pointer` or its opposite depending on the ORC configuration, `-fno-PIE`, `-mno-sse`/`-mno-mmx`/`-mgeneral-regs-only` to keep FPU state out of kernel code, `-fcf-protection`, `-mfunction-return=thunk-extern` and `-mindirect-branch=thunk-extern` for the Spectre mitigations, `-fpatchable-function-entry` for ftrace, `-falign-functions`, `-fconserve-stack`, `-fmacro-prefix-map`, and `-fsanitize=kernel-address`/`kernel-hwaddress` for KASAN.

Three deserve emphasis. **`-mgeneral-regs-only`** must be a hard constraint on the register allocator and on the optimizer's vectorizer, not a hint. A single auto-vectorized loop in kernel code corrupts userspace FPU state. **`-fno-delete-null-pointer-checks`** removes a specific optimizer assumption and must be threaded as a per-function attribute so LTO stays correct. **`-mfunction-return=thunk-extern`** replaces every `ret` with a jump to an external thunk, which touches the epilogue, the unwind info, and every tail call.

`-fno-strict-aliasing` is the one that most simplifies our life: it turns off document 07's TBAA entirely for kernel code, which removes a whole class of possible miscompilation from the hardest target on the ladder.

## 13.8 Testing

The matrix generates a test per feature, but per-feature tests only prove the feature exists in isolation. Three stronger mechanisms:

**Header compilation.** Compile every header in glibc, musl, and the kernel's `include/linux` standalone, in every relevant mode. Headers use extensions in combinations no test writes.

**Preprocessed-output diffing** against GCC on the corpus, per document 05, which catches `__has_*` disagreements before they become mysterious build failures.

**The corpus itself**, document 15. Real projects are the only complete specification of what "GCC compatible" means, which is uncomfortable but true, and it is why the target ladder in document 14 is the real test plan for this document rather than anything written here.
