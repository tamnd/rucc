# ABIs and the runtime libraries

An ABI bug is invisible until the moment you link against code someone else compiled, and then it is a wrong answer with no diagnostic. This is the part of a compiler where "mostly right" has no value at all, so this document is a list of specific obligations rather than a design discussion.

## 12.1 The ABI description

An ABI is data, held in `rucc-target` as a description consumed by document 10's lowering:

- integer, floating-point and vector argument register sequences, and the rules for exhausting them
- return value registers and the threshold and mechanism for returning through memory
- the classification algorithm mapping a C type to a sequence of argument slots
- stack argument area layout: slot size, alignment, direction, and who pops it
- caller-saved and callee-saved register sets, and the reserved registers
- red zone size, stack alignment at a call boundary
- struct and union layout rules, including bit-field allocation
- `va_list`'s representation and the `va_arg` algorithm
- TLS models and their access sequences
- name mangling, which for C means the leading-underscore question and little else
- the sizes and alignments of every fundamental type, and `long double`'s format

Five of these are implemented for 1.0: SysV AMD64, AAPCS64, Apple's arm64 variant, Windows x64, and the RISC-V LP64D psABI.

## 12.2 SysV AMD64

The classification algorithm is the hard part and it is genuinely intricate: an aggregate of at most sixteen bytes is split into eight-byte chunks, each chunk classified as INTEGER, SSE or MEMORY by a recursive walk over the fields with a merge rule, and any MEMORY result forces the whole thing to memory. The cases that catch people: a struct containing both an `int` and a `float` in one eight-byte chunk classifies as INTEGER, so the float travels in a general register; unaligned fields force MEMORY; a struct larger than sixteen bytes always goes to memory; `__int128` occupies two INTEGER chunks that must be in consecutive registers.

`long double` is x87 80-bit, stored in sixteen bytes with six bytes of padding, returned in `st(0)`. This is the reason x87 cannot be dropped from the x86-64 backend.

Varargs: `%al` holds the number of vector registers used, which variadic callees read to decide whether to save the SSE register area. `va_list` is the four-field struct with `gp_offset` at zero, `fp_offset` at four, `overflow_arg_area` at eight and `reg_save_area` at sixteen, and `va_arg` is the corresponding branch on offset versus threshold. The save area is one hundred and seventy six bytes, the six general purpose registers first at eight bytes each and the eight vector ones after them at sixteen, and the two offsets a `va_start` writes are past the registers the arguments the signature does name already took. Getting the register save area's layout wrong produces garbage in the seventh argument onward and nowhere else, and the test that finds it is handing a list built here to `vfprintf`, which was compiled by somebody else and reads it by this table.

The 128-byte red zone below `%rsp` is usable in leaf functions in userspace and must be disabled with `-mno-red-zone` in kernel code, because signal and interrupt handlers clobber it.

## 12.3 AAPCS64 and Apple arm64

AAPCS64 is cleaner: x0 to x7 for integers, v0 to v7 for floating point and vectors, everything above sixteen bytes indirect except homogeneous floating-point aggregates of up to four members, which travel in consecutive vector registers. `long double` is IEEE binary128, in software.

**Apple diverges, and the divergences are the bugs.** Arguments on the stack are packed at their natural size rather than promoted to eight-byte slots, so a stack `char` argument occupies one byte. Variadic arguments do not use the register sequence at all (they all go on the stack) which makes `va_list` a plain `char*` and makes a variadic call ABI-incompatible with a non-variadic one, so a function declared without a prototype and called variadically is a real failure. `long double` is `double`. And on Apple platforms x18 is reserved by the OS and must never be allocated.

These are per-target-triple facts in the ABI description, not `#ifdef`s in the lowering code.

## 12.4 Windows x64

Four argument registers only (rcx, rdx, r8, r9) with integer and floating-point positions shared, so a `(int, double, int, double)` call uses rcx, xmm1, r8, xmm3. Anything not exactly 1, 2, 4 or 8 bytes is passed by hidden reference to a caller-allocated copy. A 32-byte shadow space is allocated by the caller for the callee to spill those four registers into, always, even when the callee has no parameters. `long double` is `double`. Variadic floating-point arguments are duplicated into the corresponding integer register.

Unwinding is table-based through `.pdata`/`.xdata`, which constrains the prologue: it must consist only of instructions the unwind opcodes can describe, in a canonical order.

## 12.5 RISC-V

LP64D: a0 to a7 for integers, fa0 to fa7 for floating point, with a struct of two floating-point members passed in two FP registers and a struct of one integer and one float passed in one of each, a rule with no analogue in the other ABIs. Aggregates up to two registers wide go in registers, larger ones by reference. `long double` is binary128 passed by reference. The ILP32 and soft-float variants exist in the description but are not 1.0 targets.

## 12.6 Struct layout and bit-fields

Layout is per-ABI but the C-level rules are shared: members in declaration order, each at the next offset satisfying its alignment, struct alignment the maximum of its members', size rounded up to that alignment. `_Alignas`, `__attribute__((aligned))`, `__attribute__((packed))` and `#pragma pack` modify it; the interaction of `packed` with an aligned member is a place where GCC and Clang have historically differed and where we follow GCC, per document 04's compatibility contract.

**Bit-fields are the worst-specified part of the C ABI.** The allocation unit, whether a zero-width field forces alignment, whether a field may straddle a storage unit boundary, whether the declared type affects the containing object's alignment, and how a bit-field is *accessed*, the width of the load or store the compiler emits, all vary. The last one has a correctness consequence beyond layout: C11 introduced the memory model rule that adjacent non-bit-field members are separate memory locations, so a bit-field store must not write bytes belonging to a neighbouring non-bit-field member. Compilers had this wrong for years and it produces data races in correct code.

Our rule: follow the target psABI for layout, follow GCC for access width, and never widen a store past the end of the bit-field's allocation unit. Validated by a generated test suite that emits several thousand structs with randomized field types and widths, prints every offset and width via `offsetof` and `sizeof` under both compilers, and diffs, the same technique GCC and Clang use against each other, and the only way to get this right.

## 12.7 TLS

Four models: global-dynamic, local-dynamic, initial-exec, local-exec, selected by `-ftls-model=` and by visibility, with the linker permitted to relax a general model to a more specific one when it can prove the symbol is in the executable. The relaxations require emitting the exact instruction sequences the linker recognizes, byte for byte. A semantically equivalent but differently spelled sequence silently fails to relax, or worse, gets relaxed incorrectly.

`__thread` and C23's `thread_local` are the same thing. The kernel uses no TLS; userspace uses it everywhere.

## 12.8 The builtins library

Every compiler needs a support library for operations the target cannot do in one instruction. Ours is `rucc-builtins`, the equivalent of compiler-rt's builtins or libgcc, and we ship it because depending on the platform's is a portability dependency we said we would not have.

Contents: 64-bit and 128-bit division and modulo on targets lacking them; `__int128` arithmetic everywhere; software floating point for `f128` on all targets and for `f16` conversions; float-to-integer and integer-to-float conversions the hardware does not provide; the `__sync` and `__atomic` library calls for atomics wider than the target's atomic instructions; `memcpy`/`memset`/`memmove`/`memcmp` for freestanding targets; and the unwinder's personality-routine support.

It is compiled by us for the target and, importantly, **it is ABI-compatible with libgcc's and compiler-rt's**, meaning identical symbol names and calling conventions, so an object we produce links against a libgcc-based program and vice versa. The soft-float paths are differentially tested against a reference implementation over randomized inputs including the whole hazard list: subnormals, NaN payloads, signed zeros, the rounding-mode boundary cases, and the ties-to-even cases at every exponent.

**What it is written in, and the fact that this section used to say something else.** It is C, compiled by rucc itself for each target. This section said Rust with `#![no_std]`, `runtime/rucc-builtins` is that crate and is what exists today, and section 10.2 of the cross-compilation specification said C and cited this section for it. Two documents describing two different pieces of work is a decision nobody made, so tamnd/rucc#912 made it, and the answer is C for two reasons that are both about thirty targets rather than about taste.

The guard against testing somebody else's routine is the other way round here, and reading undefined symbols would not have found it. gcc puts libgcc on every link line, libgcc is a static archive, so a link that resolved `__udivti3` there rather than in the archive under test has the routine inside the program rather than undefined outside it, and both sides would quietly agree about libgcc's answer. So the script reads what each archive defines and fails on any of the ten names that is not in there. Compiling the file at all is the other thing this measured: it is `unsigned __int128` parameters, a variable shift, a 128-bit compare and a loop, which is most of the wide pass's list used at once, and the archive rucc wrote has all six symbols in it. **The code that calls them, and the first program at this width that anybody ran.** The routines landed before anything called them. `crates/rucc-codegen/src/wide.rs` listed the four divisions among the opcodes it does not understand, and one of them anywhere in a function left the whole function unsplit and refused by the selector by name, which is what every `__int128` division in the torture corpus had been getting since the pass was written. Dividing by zero is not special cased, because it is undefined in C and a test in front of the call would be the compiler deciding what an undefined program does.

What runs it is `cargo xtask wide`, and it exists because of what the evidence for this pass looked like before it. The pass had unit tests that build a function, run the pass and read the IR back, which is the shape of check section 9.8 of the cross-compilation document warns about for the stub writer: the reader and the writer hold the same belief and agree with each other. **The conversions between that width and a float.** `runtime/builtins/convert.c` is the third piece, and it is the other operation at this width the machine has no instruction for: it converts between a float and an integer of at most sixty four bits and no further, so a cast either way between a 128-bit integer and a `float` or a `double` is a call. The eight names are libgcc's: `__floattidf`, `__floattisf`, `__floatuntidf`, `__floatuntisf`, `__fixdfti`, `__fixsfti`, `__fixunsdfti` and `__fixunssfti`. They were read out of gcc 13.3 rather than out of a document, by compiling the eight casts and looking at what the calls were named, which is also what says the differential can go on testing casts instead of calling the routines by name. The eighty bit pair is not here, because this machine has no register that holds an eighty bit float and the back end says so, which is tamnd/rucc#326, and the quad spellings wait on the soft float underneath them.

Going up is two roundings made safe. A value with more than sixty four significant bits cannot be handed to the machine's conversion, so the top sixty four bits go in and the bits below them are folded into the lowest of those: a value that lost nothing keeps the bit it had, and a value that lost something comes out odd. An odd value is never halfway between two floats, so the machine's rounding cannot go the wrong way on it, and rounding to odd and then to nearest lands on the same float as rounding to nearest once. Sixty four bits is enough room for that argument to hold for both formats, since it is more than two bits past either mantissa. Putting the discarded bits back afterwards is a multiplication by a power of two, exact until the answer stops fitting, and where it stops fitting the multiplication produces the infinity that is the right answer anyway. Coming down is exact arithmetic instead: divide by 2^64, truncate that to the top half, multiply it back and subtract, which leaves a remainder below 2^64 that needs no more mantissa than the value it came from, then truncate again.

The reference in `runtime/rucc-builtins/src/convert.rs` assembles and takes apart the bits by hand, a mantissa and an exponent and a rounding decision written out, which shares nothing with the reasoning above, for the reason the division's reference shares nothing with the division's. It has the same thing it cannot do: an `as` between a 128-bit integer and a float in that crate would be a call to the routine being defined, so there is none in it, and both directions are `from_bits` and `to_bits` on a `u64`. What neither side handles is the cases C leaves undefined, which are a value the integer cannot hold, an infinity and a not a number. Both answer zero for all three and both answer zero for a negative value handed to an unsigned conversion, and that is recorded here as an accident of the shape rather than a promise, because the alternative is this library inventing an answer the language says does not exist. It is an accident the two sides have to share to be comparable at all, which is the one place in this file where the reference was written to match.

**The same division at sixty four bits.** The fourth piece is the second one at half the width, and it is in the same file because it is the same routine: `__udivdi3`, `__umoddi3`, `__udivmoddi4`, `__divdi3`, `__moddi3` and `__divmoddi4`, which are what a `/` or a `%` on a `long long` becomes on a target whose registers are thirty two bits. **Soft float, one format at a time.** The fifth piece is `runtime/builtins/float.c`, which is `__addsf3`, `__subsf3`, `__mulsf3`, `__divsf3` and `__negsf2`: what arithmetic on a `float` becomes on a target that has no instruction for it. Section 10.2 of the cross-compilation document puts that row at armv7 without an FPU and at any freestanding target the same way. Single precision alone rather than both widths at once, because the shape of the routine is the same at sixty four bits and the mistakes are in the shape rather than in the width, so one format written and held against a reference is what makes the second one an edit instead of a second design. The negation is in the list because libgcc has it, and it is the sign bit flipped and nothing else, on a not a number as much as on a number.

**What the shipped C does.** It carries three bits below the significand through every routine, which is the arrangement every soft float library in use is built on: a guard bit, a round bit, and one that remembers that something was lost below them. Three is the known bound rather than a guess. Rounding to nearest needs to know whether what was dropped is above half, below half or exactly half, and the only case where more of the dropped value would be needed is a subtraction of two values close enough to cancel, which can only happen when the exponents differ by at most one, and then there is nothing to drop. The rounding itself is done on the packed result rather than on the significand, the leading one masked off and the exponent added in first, so an increment that carries out of the fraction carries into the exponent by itself and one that carries out of the largest finite number lands on the infinity that is the right answer. That is compiler-rt's arrangement and it is worth the sentence because it is three branches replaced by an add.

**What the reference does, and why it is not that.** `runtime/rucc-builtins/src/float.rs` takes each operand apart into an exact integer and the power of two its lowest bit is worth, combines the two exactly, and rounds once at the end from the exact value. There are no guard bits in it because there is nothing to guard: what the rounding reads is the whole remainder. Two places cannot be exact and both are arranged so that what is missing cannot reach the answer. An addition whose operands are more than forty powers of two apart is the larger operand, because the smaller one is then below 2^-16 of the lowest bit the answer can hold, and twenty seven would have done. A division does not terminate, so it runs to forty bits of quotient and carries what the remainder says as "and a little more", which is read where the rounding is otherwise an exact tie and nowhere else. That division is on a `u64` on purpose: a `/` on a `u128` in that crate is a call to `__udivti3` next door, which would leave one reference leaning on another, and the shift that gets forty bits out of a `u64` is worked out from the two significands rather than fixed, because a subnormal operand brings as few as one bit with it.

**The not a number convention is shared, which is a choice.** Both sides hand back the operand quieted, and the left one where both operands are not a number, which is libgcc's rule and is what this machine's own arithmetic does with the operands in that order. An operation with no answer at all, an infinity less an infinity, a zero times an infinity, a zero over a zero, gives the quiet not a number with an empty payload on both sides. This is the second place in this section where the reference was written to match rather than written independently, the first being the conversions C leaves undefined, and the reason is the same: the alternative is comparing the two sides through a canonicalization, and a canonicalization hides exactly the kind of difference the comparison exists to find. What it costs is that the payload is not evidence of anything. What it buys is that every other bit is.

**Where the evidence ends.** The differential says the two implementations agree, which on its own is two things the same person wrote agreeing. So the reference has tests of its own, and what they compare it against is the machine's own floating point unit: the four operations over random bit patterns, over the corner table, and over constructed ties, with `black_box` either side of the hardware operation so that a constant folded at compile time is not mistaken for what the instruction does. Two not a numbers count as equal there whatever their payloads say, because a payload is a per architecture convention and those tests run on three architectures, and holding the payloads to each other is the differential's job, where both sides are on the same machine. The chain is then reference against hardware, shipped C against reference, rather than agreement between two things with no third party.

The differential grew to 2263292 cases in 570 groups. The new 999040 are four families. Random bit patterns read as floats, which is how the infinities, the not a numbers and the subnormals get in without a generator for each, since every one of those is a slice of the patterns and one pattern in every two hundred and fifty six lands outside the ordinary numbers. A value against exactly half the spacing of its own exponent, with the lowest kept bit forced each way, which is the tie that an implementation rounding up and a correct one disagree about on one of the two. The two ends of the range, where a result has fewer bits than the format usually keeps or a rounding carries past the largest finite value. And a table of twenty patterns, each against each, at all four pairs of signs, because the sign of a zero and the sign of an infinity are what a subtraction and a division decide out of the two signs they were handed. All five routines are reached by name for the reason the narrower division is: the host has a floating point unit, so a harness that wrote `a + b` would be a test of the host, and the archive-defines guard is twenty nine names now rather than twenty four.

What that catches was measured rather than assumed, the way the near miss family one width up was. Throw the sticky bit away in the alignment shift, which is the one line that makes carrying three bits worth anything, and all twenty four random, tie and edge groups disagree, along with 6 of the 20 corner groups. Round a tie up instead of to even and the same twenty four disagree and 10 corner groups do. Put the second of those two mistakes in the reference instead and four of its six tests fail, including the one whose name says it is about ties and the one that is nothing but random bits.

**The comparisons, which are the same work eight times.** `a < b` on two floats is a call on a target with no floating point unit as much as `a + b` is, and libgcc answers it with eight names: `__cmpsf2`, `__eqsf2`, `__nesf2`, `__gesf2`, `__gtsf2`, `__lesf2`, `__ltsf2` and `__unordsf2`. There is one comparison behind them and one number that differs, which is what to hand back when an operand is a not a number. Only the sign of the answer is specified, never its magnitude, so the caller compares against zero, and the number for a not a number is whichever sign makes the caller's own test come out false: below zero for the two that test at or above zero, above zero for the two that test at or below it. `__nesf2` is the same work as `__eqsf2` because a caller testing for inequality tests the same answer the other way round, and it is a second function here rather than an alias, because an alias is a linker feature and this file is meant to compile with nothing underneath it.

The two sides differ on the thing that makes the shipped routine short. The C reads the two patterns as unsigned integers and compares them, which works because the format was laid out so that two floats of the same sign order the way their patterns do, and the whole routine after the zeros and the signs are dealt with is one integer comparison. The reference does not use that property at all: it asks which power of two each value's highest set bit is worth, and only where those agree does it line the two significands up and compare them. That is slower and pointless on a real target, which is why it is not the one that ships, and it is independent of the property the shipped one leans on, which is why it is the one that checks it. An infinity needs no case in either: its stored exponent puts its highest bit one power of two above the largest finite value's, so it compares greater than everything finite and equal to another infinity by the ordinary path.

The differential runs the eight beside the five in the families that were already there, so it is 3861756 cases in the same 570 groups, and what it digests for a comparison is the sign of the answer and not the answer, the way it does for `memcmp` and for the same reason: pinning the magnitude would make it a test of an accident rather than of the contract. The reference's own tests hold each of the eight against the machine's `<`, `==` and the rest, including where one operand is a not a number and every test but the last two is false, and they hold the three way answer's whole sign rather than one side of zero, since that is the one routine whose full answer is specified. The guard list is thirty seven names.

Mutated the same way the arithmetic was. Compare two negative values the way their patterns compare, which is the one thing the integer trick has to undo, and the random family disagrees in all 8 groups, the edge family in all 8, and 17 of the 20 corner groups. Take the not a number check out of the front of the comparison, so that a not a number is ordered like an ordinary value, and the random family disagrees in all 8 and every one of the 20 corner groups does. Neither mutation moves the tie family, which is correct rather than a gap: a tie is two values of the same magnitude and a comparison has nothing interesting to say about one.

**The conversions to and from an integer, which is where a cast becomes a call.** Eight more names, four each way: `__floatsisf`, `__floatunsisf`, `__floatdisf` and `__floatundisf` going up, `__fixsfsi`, `__fixunssfsi`, `__fixsfdi` and `__fixunssfdi` coming down. They are in `runtime/builtins/float.c` and not in `convert.c`, which is also nothing but conversions, and the reason is worth writing down because the two files look like the same job. `convert.c` handles 128-bit integers by handing sixty four of their bits to the machine's own conversion instruction, so it exists for a target that has a floating point unit and no wide integer. These exist for a target with the opposite problem, so they are done in integers like everything else in this file and they share its rounding.

Going up is a rounding rather than a widening, which is the part that surprises people: a `long long` carries sixty four significant bits and a single keeps twenty four, so most integers do not convert exactly and the answer has to be the nearest float with a tie going to the even one. The C moves the integer's highest bit to where `round_and_pack` wants it and keeps whatever falls off the bottom in the sticky bit, which is the same alignment the arithmetic does. The reference hands the integer to `round_from` with a scale of zero and does nothing else at all, because an integer already is a significand and the power of two its lowest bit is worth, which is exactly what that routine takes. One line against a dozen is as different as the two shapes get in this section.

Coming down is a shift on both sides and there is no point pretending otherwise: the exponent says how far, and one direction of the shift throws the fraction away while the other moves the significand up into a wider integer. What the two do not agree about by construction is the range, and that is where the comparison has something to say. C leaves four cases undefined here, which are a value the integer type cannot hold, an infinity, a not a number, and a negative value handed to an unsigned conversion, and both sides answer zero for all four. That is the third place in this section where the reference matches rather than being arrived at independently, and it is recorded for the same reason as the other two: a convention that is shared is a thing the differential can hold both sides to, while a convention that differs would have to be canonicalized away and would take real differences with it. A program must not read it as a promise. The one case that looks undefined and is not is a negative value whose integer part is zero, where minus a half to an unsigned type is zero because that is the value and not because of any convention.

The differential runs the eight by name, since a cast in the harness would be the host's own instruction, and it adds two families to the single precision set. One is random integers at both widths and both signednesses together with random patterns coming down, including the patterns with no answer, which is the thing the 128-bit conversion families cannot do because there their oracle is the host. The other is the edges by name: the top of each of the four integer types with its neighbours and its negation, the first integer a single cannot hold and the two either side of it, and the float patterns at 2^31, 2^32, 2^63 and 2^64 with the pattern either side of each, which is where every range check in the four routines coming down gets decided. 2^31 is the one to look at, being one past the largest `int` and exactly the most negative one. That is 4189868 cases in 579 groups, and the archive-defines guard is forty five names.

Mutated like the rest. Drop the sticky bit from the shift that aligns an integer on the way up, so that an integer too wide for the format truncates instead of rounding, and all eight groups of the random family disagree, while the family with the edges in it does not, because the integers named by hand there happen to round the same way from the guard and round bits alone. Use the same bound going up as coming down in the signed range check, which is the off by one that says an `int` holds 2^31, and exactly one group moves and it is the edge family, which is the whole reason that family is there rather than a second sweep of random values. The same off by one in the reference fails one of that crate's thirty five tests, the one that converts floats down, and leaves the other thirty four passing, which is what a mistake in one direction should do to tests that are split by direction.

**The second format, which is four operations and a negation again.** `runtime/builtins/double.c` is `__adddf3`, `__subdf3`, `__muldf3`, `__divdf3` and `__negdf2`, arithmetic on a `double` on the same target the single precision set exists for. It is a second file rather than the first one widened, for the reason the two copies of the bit at a time division are two copies: what a file like this is for is being read against the routine it stands in for, and a macro that expands into two formats is read once and checked neither time. Everything about the shape came over unchanged, which is the whole of the easy half: three rounding bits carried through every routine, the tie to the even significand, the rounding done on the packed result so that an increment carrying out of the fraction carries into the exponent by itself, the not a number handed back quieted and the left one where both operands are one. What changed is the field widths and the number of times round the division loop, fifty seven rather than twenty eight. That is what writing the formats one at a time bought, since the shape was held against a reference at twenty four bits of significand before anybody copied it at fifty three.

**The two routines that are new, and the one difference in this section nobody chose.** The product of two fifty three bit significands is a hundred and six bits and a word holds sixty four, so the shipped C builds it out of the four products of their thirty two bit halves and carries it in two words, with the middle column's carry written out. It cannot ask for an `__int128` instead, because that would be this file calling `__multi3`, which is the one thing a file of builtins must not need, and because a 32-bit target, which is the target this file exists for, does not have the type at all. The reference has no such problem and does not pretend to one: it multiplies in a `u128`, since every machine this crate's tests run on multiplies sixty four bits by sixty four in instructions. The division goes the other way round. The C runs the same loop it runs one format down and needs no more room to run it, because a remainder stays below the divisor. The reference cannot write the obvious `/` on a `u128`, since that is a call to `__udivti3` in `div.rs` next door and a reference leaning on another reference is worth nothing, so it divides a byte at a time, in the widest digit whose running remainder still fits a word: the remainder is below the divisor, the divisor is at most fifty three bits, and eight bits on top of that keeps every division in the loop inside sixty one bits and therefore inside one instruction. Every other difference between a routine here and its reference was chosen, so that two descriptions of one answer could not share a mistake. This one was not chosen. The width makes a product too wide for a word and a quotient too wide for a `/`, and each side is then doing the cheapest thing its own rules leave it.

The differential runs the five in the four families the single precision set already had, which takes it to 5188908 cases in 623 groups. The new 999040 are random bit patterns read as doubles, a value against exactly half the spacing of its own exponent with the lowest kept bit forced each way, the two ends of the range, and a table of twenty patterns each against each at all four pairs of signs. The constructed families carry more of the weight at this width than at the last one, and the arithmetic says how much: one bit pattern in two hundred and fifty six is an infinity, a not a number or a subnormal when it is read as a `float`, and one in two thousand and forty eight is when it is read as a `double`, because the exponent field grew by three bits while the fraction grew by twenty nine. Random patterns alone would reach the ends of the range eight times less often here, which is an argument for naming the cases rather than for drawing more of them. The archive-defines guard is fifty names.

Mutated at the two new routines, since the rest of the shape was already mutated one format down. Throw away the sticky bit in the shift that brings the hundred and six bit product down to what the rounding wants, and all 8 groups of the random family disagree, all 8 of the family with the ends of the range in it, and 2 of the 20 corner groups. Drop the middle column's carry in the product built out of halves, which is the one line a person writing that routine from memory leaves out, and the same 16 groups disagree along with 6 corner groups. Neither mutation moves the tie family at all, and that is worth a sentence because it looks like a gap and is not: the ties are built by adding a value to half the spacing of its own exponent, so the only multiplication in that family is by a power of two, which is exact, and a product that loses nothing has no sticky bit and no carry out of its middle to get wrong. Put a mistake in the reference's division instead, losing the running remainder between two of its byte sized digits, and 5 of that crate's 42 tests fail, including the one whose whole subject is the byte at a time loop and which was written because a quotient the answers only reach indirectly deserves a check of its own.

**The comparisons at this width, which are the eight shapes again and nothing else.** `__cmpdf2`, `__eqdf2`, `__nedf2`, `__gedf2`, `__gtdf2`, `__ledf2`, `__ltdf2` and `__unorddf2`, and the description of them is the paragraph above about the single precision eight with the width of a pattern changed. One comparison behind the eight, one number that differs, which is what to answer when an operand is a not a number and has to be whichever sign makes the caller's own test come out false. The shipped C compares the two patterns as unsigned integers and the reference asks which power of two each value's highest bit is worth and lines the significands up where those agree, which is the same division of labour: one side uses the ordering property the format was designed to have and the other checks it. The property holds at this width for the same reason, the exponent sitting above the fraction with both unsigned, and nothing about the routine noticed that the fraction grew by twenty nine bits. That this is a short paragraph is the point of having written the format one at a time.

The harness runs the eight beside the five it already had at this width, so the groups stay at 623 and the cases go from 5188908 to 6787372, and what it digests for a comparison is the sign of the answer rather than the answer. The reference has the comparison tests the narrower file has, against the machine's own `<` and `==` over random patterns, the corners, and a value against itself, which is the case where an implementation that compares patterns and one that compares values can still differ, since a negative zero against a positive one and a not a number against itself both live there. It has one test the narrower file does not: two values that share an exponent and differ only in the fraction, at a random exponent rather than a named one, and the same pair negated, where the order has to reverse. That is the case the extra twenty nine bits of fraction are actually about. The archive-defines guard is fifty eight names.

Mutated at the two lines where a comparison of patterns is not a comparison of values. Order two negative values the way their patterns order, which is the one thing the integer trick has to undo, and all 8 groups of the random family disagree, all 8 of the ends of the range family, and 17 of the 20 corner groups. The tie family does not move, and this time that is a property of how it builds its pairs rather than of what a tie is: three of its four pairs have a positive operand in them and the fourth has two, so it never asks about two negative values at all. Take out the case that makes a negative zero equal a positive one, so that the sign is read where the format says not to read it, and exactly one corner group disagrees and nothing else does anywhere, which is the measurement worth keeping: a zero is one pattern in 2^63 and a family of random patterns will not find one in a million cases, so the table of twenty named patterns is not a formality. Put a mistake in the reference instead, comparing only which power of two each highest bit is worth and never lining the significands up, and 2 of that crate's 44 tests fail, which are the two that compare against the machine's own ordering, the second of them being the one written for this.

**The conversions at this width, which are the same eight names with one difference nobody arranged.** `__floatsidf`, `__floatunsidf`, `__floatdidf` and `__floatundidf` going up, `__fixdfsi`, `__fixunsdfsi`, `__fixdfdi` and `__fixunsdfdi` coming down, in `double.c` and not in `convert.c` for the reason given three paragraphs up about the single precision eight. Both shapes came over unchanged: the C moves the integer's highest bit to where the packing wants it and keeps what falls off in the sticky bit, the reference hands the integer to `round_from` with a scale of zero and is one line, and coming down is a shift whose direction the exponent decides. The four undefined cases answer zero on both sides here too, and the same warning applies, that it is a convention the differential can hold both sides to and not a promise a program may read. The difference that is real is this. Fifty three significant bits hold every `int` and every `unsigned int` exactly, so the two conversions up from a 32-bit integer never round at this width and their sticky bit is never set, where one format down all four round. That is a property of the format rather than a decision, and it is written down because it means the narrow pair of routines is exercised here without any rounding on top of it, which is where a shift that went the wrong way has nowhere to hide.

Coming down has the case that is genuinely new, and it is about a bound rather than about a shift. At single precision the largest `long long` and the float nearest it are far apart, and at this width they are not quite: 2^63 is exactly a double, the double below it is 2^63 - 1024, and the largest `long long` is not a double at all. So the routines have to hold the value against the bound rather than hold the result of a cast against it, and the harness names 9223372036854774784.0 and 9223372036854777856.0 for that, which are the doubles either side of that integer. The families are the single precision two with the widths changed: random integers at both widths and both signednesses going up, with each value asked again shifted down so that a conversion that is exact runs beside one that rounds, and a third value placed just past 2^53, which is where a double stops holding every integer; then random patterns and patterns with the exponent spread from 2^-27 to 2^67 coming down. The edges by name are the top of each of the four types with its neighbours and its negation, the integers around 2^53, and the patterns at 2^31, 2^32, 2^63 and 2^64 with the pattern either side of each. That takes the harness to 7115500 cases in 632 groups, up from 6787372 in 623, and the archive-defines guard to sixty six names.

Mutated at the three places a conversion can be wrong without being obviously wrong. Drop the sticky bit from the alignment going up, so a wide integer truncates instead of rounding, and all 8 groups of the random family disagree while the named family does not, the same split the single precision mutation produced and for the same reason. Use the bound going up in the signed check coming down, which is the off by one that says an `int` holds 2^31, and one group moves and it is the named family, which is that family earning its place a second time. Shift the significand the wrong way for an exponent above fifty two, which is the case the format does not store because the value is an integer already, and all 8 of the random groups and the named group all move, which is the one mutation here that both families catch. In the reference the mutation worth measuring is that same bound and not the refusal above it, since taking the refusal out panics on a shift wider than a `u128` rather than disagreeing about an answer: hold a negative value to 2^31 - 1 the way a positive one is held and 1 of that crate's 46 tests fails, the one that converts doubles to integers, on the pattern for the most negative `int`.

**The pair between the two formats, which is where the set for these two widths ends.** `__extendsfdf2` and `__truncdfsf2`, what a cast between a `float` and a `double` becomes on the same target, and the first routines in this section that needed both formats to exist, which is why they came last rather than with either format. Both sides put them with the narrow format, in `float.c` and in `float.rs`, and the reason is the same in both directions. A widening never rounds, so all it needs of the wider format is where its fields are. A narrowing is a rounding into the narrow format, so it wants that format's own rounding and again nothing of the wider one but where its fields are. So the pair needs the wide format's field widths and none of its arithmetic, and the file that already knows how to round the narrow format is the place for it.

Why a widening never rounds is the whole of the easy direction: every exponent a `float` holds is inside the `double`'s range and fifty three bits hold twenty four, so the fields move and nothing is lost. The one input where a field move is not enough is a float subnormal, which is a normal double because the wider range reaches far below the smallest float, and the C normalizes it by hand with the same loop the arithmetic uses. The narrowing is the direction with decisions in it, and it makes none of them itself: the significand arrives with its leading one at bit fifty two, the shift down to where `round_and_pack` wants it carries the sticky bit, and the rebiased exponent is then allowed to land anywhere, including far above the top and at or below zero, which are exactly the two departures that routine already allowed for. A value too large becomes an infinity and one too small becomes a subnormal or a signed zero without a line being written for either.

A not a number keeps its payload in both directions, moved by twenty nine bits, which is also the distance between the two quiet bits, so neither direction says anything about that bit and both get it right. Narrowing loses the bottom twenty nine bits of a payload, so one that lived only down there comes back empty, and the quiet bit goes on afterwards in both implementations, which is what keeps the answer a not a number rather than the infinity it would otherwise be. That one is worth calling out because it is the only way either of these routines can be wrong about a kind rather than about a value.

The reference is one line each way and it is the same line: take the input apart into the exact value it is and round that once into the other format, which is what this side does everywhere else in the section. `float.rs` reads the wider format's fields and its rounding from `double.rs` rather than writing a second copy of either. Writing the widening that way costs nothing and buys something: that it never rounds becomes a property of the two formats that the test demonstrates rather than an assumption the code is built on. The test that says so most directly is the round trip, a float widened and narrowed again being the float it started as, with a not a number coming back quieted, and the harness digests that too rather than digesting a `1` that both sides would agree on.

The harness runs the two in a group of their own rather than adding them to the families above, because those are built around pairs of operands and every digest in them would have changed while saying nothing new. The families are random float patterns widened, a guaranteed float subnormal widened, random double patterns narrowed, and doubles whose exponent is spread from below the smallest subnormal float to above the largest finite one, which is the only span where the narrowing has a decision to make. The named group is the two corner tables crossed over, the round trip on each single precision corner, and the doubles at the ends of the narrow format's range: the largest finite float exactly, the pattern just under halfway to 2^128 and the one exactly at it, 2^-126, 2^-149, 2^-150 and a hair above it. That takes the harness to 7181168 cases in 641 groups, up from 7115500 in 632, and the archive-defines guard to sixty eight names.

Mutated at the three places a cast between two formats can go wrong. Widen a float subnormal as a field move, which is the mistake the easy direction invites, and all 8 random groups and the named group disagree, which is the guaranteed subnormal in each round doing its job. Drop the sticky bit from the shift that narrows, and the same nine groups move. Drop the quiet bit from the narrowing, so a signalling not a number can come back as one and a payload that lived only in the lost bits comes back as an infinity, and 4 of the 8 random groups move and the named group does, which is the measurement worth keeping here: a not a number with that bit clear is about one pattern in four thousand and a round of two thousand finds one half the time, so the random families catch this one on a coin toss and the table catches it every time. In the reference, move the payload by twenty eight bits instead of twenty nine and 2 of that crate's 49 tests fail, the two that hold a direction against the machine, while the round trip passes, because a distance that is wrong by the same amount in both directions is a distance that undoes itself. That is the argument for having all three tests rather than the round trip alone.

## 12.9 Sanitizer runtimes

The instrumentation is in the compiler; the runtime is a library. We implement:

**UBSan.** The check set from document 07's UB table: signed overflow, shift amount, null and misaligned pointers, out-of-bounds array indices with a known bound, `bool` and enum range, division by zero, invalid float-to-integer conversion, `__builtin_unreachable` reached, and the two novel ones, `-fsanitize=alias` for effective-type violations and `-fsanitize=restrict` for `restrict` contract violations. These two are the interesting contribution: the aliasing and `restrict` rules are the UBs that most often produce a "the compiler broke my correct code" bug report, and neither GCC nor Clang has a reliable dynamic checker for them. The runtime is a shadow-memory scheme recording the effective type of each byte and the base pointer of each `restrict`-qualified access, and it will be slow. Slow and correct is fine for a debugging tool.

**ASan.** Shadow memory at the standard scale and offset so that our instrumentation is compatible with the existing runtime, redzones around globals and stack objects, quarantine on free. We implement the instrumentation and can either ship a runtime or interoperate with LLVM's; interoperating first is the cheaper path and is what M8 does.

**MSan** requires instrumenting every load and every store and propagating shadow through arithmetic, and it only works if *all* linked code is instrumented, which makes it much more expensive to get right. Post-1.0.

**`-fsanitize=cfi`** and the fine-grained forward-edge checks are post-1.0. `-fstack-protector`, `-fstack-clash-protection`, `-fcf-protection` and `-mbranch-protection` are not sanitizers and are in for 1.0, since production builds and the kernel use them.

## 12.10 Validating the ABI

Three mechanisms, in increasing order of strength.

**Struct layout diffing**, as in 12.6, generated and compared against GCC per target.

**Call ABI differential testing.** Generate a function with a randomized parameter list drawn from the full type space (every scalar type, structs and unions with randomized members, arrays, `__int128`, `long double`, vectors, and variadic tails) compile the caller with `rucc` and the callee with GCC, then the reverse, and check that every parameter arrives with the value it was sent. This is the only test that finds classification bugs, and it finds them immediately. It runs per target under QEMU for the cross targets.

**Linking against the world.** Building SQLite with `rucc` and linking it into a GCC-built program, and vice versa, is a weaker but broader test that the corpus in document 15 performs continuously. An ABI bug that survives the first two mechanisms will surface here as a mysterious failure in a real program, which is exactly the outcome the first two exist to prevent.
