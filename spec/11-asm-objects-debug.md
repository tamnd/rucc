# Assembly, objects, and debug information

## 11.1 The integrated assembler

We encode instructions directly to bytes rather than emitting text and calling `as`. Three reasons: an external assembler is a process spawn and a re-parse per translation unit, which is a large fraction of the compile-throughput budget; it is a dependency on GNU binutils or the Apple toolchain, which contradicts the portability axis; and the assembler is the place where a compiler's own instruction encoding gets validated, so having it in-tree means the validation is in-tree.

`-S` still emits assembly text, because people read it and because the assembly output is a debugging artifact we care about. The text path and the binary path share the same instruction description, so they cannot disagree about what an instruction is.

That shared description lives beside the register file, in `rucc-target`. For each machine opcode it holds the list of real instructions the opcode is, since an opcode is one instruction to the register allocator and is not always one instruction to the machine: a comparison is a compare and a set, an unsigned division is the clearing of the high half and then the division, and the pseudos that say where a value is are no instructions at all. Each instruction in the list is a mnemonic and a list of arguments, and an argument names the operand it is drawn from by its index rather than being the operand itself, because the assembler's order is not the operand vector's order, an instruction may write one operand twice, and an instruction in the middle of an opcode may name none of them. The width an argument is written at is on the argument, since a comparison of two 64-bit registers sets a byte and a shift of one reads its count from a byte.

An opcode nothing selects is described the same way as one a rule selects. A prologue pushes, a spill stores and a copy moves, and none of those is anything a pattern could match, but all of them reach the assembler and the encoder in the same function and are read there the same way. A second table for them would be a second place for an opcode to be missing from.

The bytes of one of those instructions are a second table beside the first, keyed the way an assembler keys one: by the mnemonic, by what kind of thing each argument is, and by the range the immediate falls in. A mnemonic is not an instruction, since `movl` is a different instruction given an immediate, a register, a load or a store, and a smaller immediate is sometimes a shorter instruction, so the key has to carry all three. It is not keyed by machine opcode, because that would be a third description of the same instruction and a third place for the three to disagree. A row is an opcode, what goes in the byte that names the registers, and how many bytes of immediate follow, and the walk that turns an opcode into text and the walk that turns it into bytes are the same walk over the same list, differing only in what they do with an instruction once they have it.

Choosing between two encodings of one instruction is the table's job and not the encoder's. Where the machine has a short form the encoder would need a special case to reach, the short form is a row in front of the general one and the lookup takes the first that holds the number, so the encoder stays a function of the row it was given. Where a short form is a win only on one register, or only for one constant, it is left out and said so, because a row that applies to one register is a row a reader stops checking. A whole-function decision is not a row at all: relaxation is the only one, and it stays a pass.

One row carries a byte that is not part of the instruction, and it is worth saying why it is a field rather than the first byte of the opcode. Three x87 instructions have two names each, where the one with the `n` in it is the instruction and the one without is that instruction with `fwait` written in front of it, so `fstcw` is `fwait` and then `fnstcw`. `fwait` is an instruction rather than a prefix, which decides where it goes: a prefix reaches whatever follows it, and what follows the wait is the store, so a REX byte belongs behind the wait and not in front of it. Written as the first byte of a two byte opcode it would come out in front, because the writer puts the REX byte ahead of the whole opcode and is right to, and the result would be an instruction that assembles and runs and reads the wrong address on exactly the operands that need a REX byte. So a row says whether it is written with a wait and the writer puts the byte down before anything else.

What surrounds the instructions is the object format's answer rather than the machine's, and the three formats do not agree. A Mach-O symbol carries an underscore in front of the C name and an ELF one does not, so a listing that got that wrong would fail to link against every library on the machine. A label local to a function is spelled `.L` on ELF and COFF and `L` on Mach-O, and one not spelled the local way ends up in the symbol table, where a debugger and a backtrace will show it as though it were a function. ELF says how long a function is and Mach-O has no way to. And ELF wants the marker saying the stack is not executable, whose absence makes it executable, which is a security bug rather than a missing nicety. So the directives are held per format, next to the printer and away from the instruction description, which is per machine.

**We also accept assembly as input.** `.s` and `.S` files appear in every real project. The kernel has thousands, and musl, FFmpeg and OpenSSL all ship hand-written assembly. A compiler that cannot assemble them needs an external assembler after all, which forfeits the point. So `rucc-asm` contains a real assembler with a real directive set: `.text .data .bss .section .globl .local .weak .type .size .align .balign .p2align .byte .short .long .quad .ascii .asciz .space .fill .set .equ .org .comm .lcomm`, the CFI directives `.cfi_startproc` through `.cfi_endproc` with the full register-rule set, `.macro`/`.endm`, `.rept`, `.if`/`.else`/`.endif`, and expression evaluation with the symbol arithmetic and relocation-generating operators (`sym@GOT`, `sym@PLT`, `sym@TPOFF` and the rest).

Both the AT&T and Intel syntaxes are accepted for x86, selected by `-masm=` and by `.intel_syntax`/`.att_syntax` directives, because inline assembly in the wild uses both.

**Encoding correctness is verified by differential disassembly.** Every instruction we encode is disassembled by an independent decoder and compared against the intended semantics; additionally, a CI job assembles the corpus's `.s` files with both `rucc` and the system assembler and compares the resulting bytes. Encoding bugs are silent and catastrophic, and this is the cheapest way to find them.

The comparison is of what the two say and not of the bytes they say it in. Both sides go through one decoder, ours from the bytes we wrote and the assembler's from the text we printed for the same instruction, and the two readings have to be the same instruction. Bytes cannot be compared directly, because we choose a longer encoding in the places listed above and will keep doing so until relaxation is written, and a check that fails on a difference we intend is a check nobody runs. A difference in what the two decode to is always a bug.

Relaxation, choosing the short form of a jump when the displacement fits, and growing it when it does not, is an iterate-to-fixpoint pass over the fragment list. It must terminate, and it must be deterministic; both are tested.

The reader of `.s` files does it by reading the file more than once. Every `jmp` and conditional jump to a name starts out two bytes long, and at the end of the file each one whose distance is not a number that fits in a signed byte is marked. The file is then read again with the marked ones written long, and that repeats until a pass marks nothing. A jump that is long stays long, so each pass has more long jumps than the one before and the count of jumps bounds the number of passes, which is the argument for termination. Starting short and only ever growing is also what gas does, so the two come out the same size. A jump out of the section, or to a weak name, is a relocation and is always long.

## 11.2 Inline assembly

GCC's inline assembly is one of the least-specified and most-depended-upon parts of the C ecosystem, and it is a hard requirement for the kernel.

The pieces: a template string with `%0`-style operand references and the `%` modifier letters that select an operand's spelling (`%w0` for the 32-bit form of an AArch64 register, `%b0` for a byte register on x86, and so on); output operands with `=` and `+` and `&` earlyclobber; input operands; constraint strings; a clobber list including `"memory"` and `"cc"`; the `volatile`, `inline` and `goto` qualifiers; and for `asm goto`, a label list making the statement a terminator.

**Constraints are a per-target language** and they must be implemented per target rather than approximated. The common ones (`r` `m` `i` `n` `g` `0`-`9` for matching operands) plus each target's specific set: on x86 `a b c d S D A q Q x y v` and the immediate ranges `I` through `P`; on AArch64 `w x r Q S Y Z` and the logical-immediate classes; on RISC-V `f A I J K`. The constraint determines which register class the allocator must use and whether a memory operand is acceptable, so it feeds directly into document 10's operand constraints.

The `"memory"` clobber is a full compiler barrier for memory: no load or store may be moved across it. The kernel's `barrier()` is exactly this and getting it wrong produces bugs that appear only under concurrency and only sometimes.

**`asm goto` with outputs** is required by current kernels and is the hardest case, because the outputs must be live on the fall-through edge and not on the indirect edges, which interacts with register allocation in a way that needs explicit handling rather than falling out.

Because we cannot verify the contents of an assembly template, inline assembly is a hard barrier for the optimizer: an `inline_asm` instruction with a `"memory"` clobber or the `volatile` qualifier is treated as an unknown call for alias analysis and is never moved, duplicated, or deleted unless its result is unused and it is neither volatile nor clobbering.

**A template with no instructions in it is the case to build first**, and it is not a corner of the feature. A program that wants a value computed where it stands, or a loop the optimizer must not touch, writes `asm volatile ("" : : : "memory")`, and forty years of bug reports about optimizers are full of them. What such a statement asks for is the barrier and the places its operands share, and no instructions at all, so it needs none of the assembler above and none of the allocator hints below. The back end lowers one today: an output an input is tied to, by `+` or by a matching constraint, is the register that input arrived in, because the template wrote nothing over it; an output nothing is tied to is a value the program has no claim on and is written as a zero, since the allocator is owed a definition before the use whatever the program is owed; an operand in memory is an address the front end already built; and the clobber list is not read, because a template with no instructions in it ruins no register.

A template with instructions in it is read into the opcodes this backend already has, which is what 11.1 asks for and is why it is possible at all: the machine is described once, so an instruction a program wrote down is looked up in that description rather than copied through to an assembler with a description of its own. From there an `asm` statement is ordinary machine code, and a spill around one works because there is nothing left about it for a spill to get wrong. An instruction this compiler cannot place is refused out loud rather than guessed at, since the alternative is a program that assembles into something other than what it says, and that covers a mnemonic the machine has not got, an opcode written as more than one instruction, a directive other than the two below, a scaled index, and a prefix that changes what the instruction does.

A template may also be a loop, and a loop is the one shape that cannot stay one instruction of the IR. The template names a place and jumps back to it, which is what `MPN_INCR_U` in libgmp's `gmp-impl.h` is, and a jump the compiler read is a jump the compiler has to lay out, so the statement stops being a single thing: each label becomes a block, each jump ends the block it stands in and gives it the label's block and a fresh one as its two arms, and whatever follows the statement goes into whichever block the walk finished in. That is a decision to make this the lowering's job rather than the front end's, and the reason is the condition state. The instruction that sets it and the jump that reads it are written next to each other by the program, with no value between them that an IR statement could carry, so splitting the template into separate statements before the machine level would put a boundary exactly where the program needs none. The machine IR is in the form where a register is written once, so an operand written inside the loop and read again at the top of it cannot be one register: every block a label made takes one parameter for each operand that is in a register at all, in one fixed order, and every jump carries whichever register held the operand where the jump stands, so an arm's arguments and a block's parameters are the same list read twice. The block an untaken jump falls into is arrived at one way only and takes no parameters. The back edge is a critical edge and gets a block of its own from the pass that already splits them, which is what keeps the moves an arm turns into behind the jump rather than in front of it and is the second half of why the condition state needs no carrying. A jump with no condition on it is refused wherever what follows it is reachable by nothing, which is every place but one and is covered in the paragraph below, and a condition this machine has no opcode for is refused for the reason any unknown mnemonic is.

An output the template reads is read, and what it reads is a zero. A constraint written `=` says the assembly writes the operand and does not read it, and a program may still write an instruction that reads the register before it writes it, which is not a contradiction so much as the program saying it does not care what was in there. libgmp's `add_mssaaaa` is the case and is the reason this is written down: it ends with `sbb %q0, %q0` on an operand declared `=r` and tied to nothing, which subtracts a register from itself and is asking for the borrow bit rather than for the number, so whatever the register held, the answer is the same. Refusing that would be this compiler deciding something the language leaves to the program, and gcc 16.2.0 accepts it without a word, so it is accepted here. What the operand holds there is undefined, which is not the same as the operand being absent: the machine IR is in the form where every use stands behind a definition, so a register nothing filled is not a thing the allocator can be handed. It gets a register holding a zero, which is the same answer an output nothing wrote gets and is the same answer for the same reason. The zero is worth having rather than merely legal, since a `Reuse` tie lands the write in the register that was zeroed, and `sbb x, x` with a zero in `x` is exactly the borrow bit sign extended, which is the number the program was after.

The first of two directives that are read is the alignment. A program that writes `.p2align 5` in front of a loop is saying where the next instruction starts, and that is a fact about the code the compiler is generating rather than a request for something to be copied through, which is why it can be answered here and a section or a symbol cannot. It is carried as an opcode of the machine with no operands and the boundary in bytes on its immediate, so the passes between selection and the writers see it the way they see everything else, and each writer answers it in the terms it has: the listing writes the directive back out with the byte that does nothing as the fill, and the object writer pads to the boundary and raises the alignment of the section it is filling, since a function aligned inside a section that is not is aligned to nothing at all. The timing model calls it fixed, which makes the scheduler treat it as a barrier, and that is the point rather than a detail: what an alignment is about is which instruction comes after it, so an instruction moved across one is an alignment of something other than what the program asked for. `.align` and `.balign` are read as well and say the boundary in bytes where `.p2align` says it as a power. An alignment that asks for more than a boundary is refused like any other directive, which covers a fill byte, a number of bytes to stop after, a boundary that is not a power of two, and one larger than a page.

The second is `.byte`, which is a program writing an instruction out as the bytes it is made of. `xgetbv` is the one that still turns up, written as `.byte 0x0f, 0x01, 0xd0` because the code that asks whether the operating system has agreed to save the wide registers is older than the mnemonic, and libwebp writes it that way in two files. It is read for the reason the alignment is, which is that it is already answered: the program has said what the processor is to be handed, so there is nothing to assemble and nothing to look up, and it is not the same thing as a mnemonic this machine has no table entry for. It is carried as one opcode of the machine per byte with no operands and the byte on its immediate, which is what keeps it something the passes and the writers already know how to hold, since an instruction carries one number and carries no string of them. The listing writes the directive back out a byte at a time and the object writer puts the byte in the text, neither of which has anything left to work out. A number that is not a byte is refused rather than truncated, for the reason a fill byte on an alignment is.

An instruction may also reach a register its text does not name, and the constraint letters are what say whose it is. `cpuid` is the whole of that case at once: the leaf goes in `eax`, the subleaf in `ecx`, the answer comes back in all four registers, and none of the six is written anywhere in a template that says `cpuid` and nothing else. The description already holds every bit of it, so what is left is to match each of those registers against the statement's operands, which is what `"=a"` and `"c"` are for and is why a program writing this instruction has no choice about how it writes its constraints. A register no letter named is a register the statement put nothing in, which is the ordinary case rather than a strange one, since an instruction that answers four questions is written by programs that asked one: a write of one is the register being destroyed and gets a register of its own so the allocator keeps everything else out of it, and a read of one is a register the instruction looks at and the program never filled, which gets a zero for the reason an output nothing wrote gets one.

An instruction may also leave out what the description does say, in two ways, and neither of them is a guess about what the program meant. The first is the width: AT&T spells it as a letter on the end of the mnemonic, and a program writing `cmp %1, %2` leaves the letter off because the registers it names already say it, so the width is taken from the operands and the mnemonic is looked up again with the letter the operands imply. Every operand the instruction reads has to agree on that width or the template is refused, since a mnemonic whose arguments disagree is one where the program and the machine mean different things by it. The second is an operand the description ties to another one. This machine describes a two address instruction with three operands, the third being the destination as it stood before the instruction ran, and a program writes `addq %1, %0` with two because the third is the same place as the first. An operand tied to one the text did name is read as that one, and an output written `+` is what makes the statement willing to have it written over, which is the same claim the tie makes from the other side. An operand nothing says anything about is still refused: not named by the text, not fixed to a register by the description, and not tied to an operand the text named.

A register the template names in its own text is placed as that register. It is the one thing inside a template that belongs to no operand of the statement, and a program writes one when what it is doing cannot be said with constraint letters at all: micropython's non local return saves the callee-saved registers into a buffer one `movq %%r12, 48(%%rdi)` at a time, and the whole point of the buffer is that those exact registers are in it, so there is nothing for a letter to choose. There is no letter for `%rsp` either. What this compiler does with such a name is the thing gcc cannot, because gcc copies the text out and the allocator never learns the register was touched: here the name becomes an operand of the instruction the allocator sees, fixed to the register the program wrote, so a write of one is a definition the allocator knows about and will not leave anything of the program's across, and a read of one is a use it will not have put something else in first. A program that also names the register in its clobber list is then saying the same thing twice rather than adding anything, and a program that forgot to is no worse off here than it meant to be. A register named as the base of an address is the same case and is the half of it every register saving template needs, since such a line names one register as the value and another as where it goes.

The one unconditional jump a template may write is a `jmp` to a name, written last, in a function that is `naked`, and it is a jump out of the function rather than a jump about anything in the statement. `__attribute__((naked))` says the body is the whole of the function and the compiler is to write nothing around it, which is what a function that saves the machine state by hand needs, and micropython's `nlr_push` is the program that asks: it reads the return address out of `(%rsp)` where the call left it, saves the registers the convention preserves into a buffer one at a time, and ends `jmp nlr_push_tail`, handing the frame it just built to a function written in C that never comes back. A push in front of any of that would move the return address the first instruction reads. So the attribute and the jump are one question rather than two, which is worth saying because they look like separate features: an unconditional jump is refused everywhere else because it leaves whatever follows it reachable by nothing, and in a naked function nothing follows it, because a naked function has no epilogue for it to jump over. The name goes into the object file with a relocation against it and is the one name a program wrote inside a template that survives past the reader, since every other name in one is a label compared against other labels in the same template and thrown away. A `jmp` in the middle of a template is still refused, so is a `jmp` to a label the same template carries, and so is one in a function that has a frame to give back, since that would go to the next function with this function's frame still taken.

What `naked` costs the rest of the compiler is a prologue, an epilogue and a return, and nothing else. No register is put away, because the program said it would save what it wants and the first thing one of these usually does is read something the saving would have moved. No bytes are taken. The `ret` a function ordinarily ends with is written by the epilogue, so there is none, and falling off the end of the body becomes a `ud2`, which is where control arrives if the jump is ever not taken and is exactly what gcc puts in the same place. The stack protector is left out whatever the command line asked, because the canary is a word the prologue writes into the frame and the check at the end reads back, so a function with neither has nowhere to put it and nowhere to read it from, and gcc leaves it out too. The landing pad stays, because that is the address of the function being made one an indirect branch may arrive at rather than the compiler adding anything to the body, and gcc writes it in a naked function as well. Because there is no prologue, there is nothing to give the body bytes, so a naked function whose frame comes out with any in it is refused rather than given offsets into a frame nothing set up, which would reach into whatever the caller left below its own stack pointer and is wrong code that assembles. A variable length array in one is the same refusal arrived at from the other side, since a frame that grows is reached from a frame pointer and establishing one is the first two instructions of a prologue there is none of.

The clobber list is read for a template that has instructions in it, as the registers it names being written by every instruction of the template, since the list says the assembly as a whole leaves them ruined and nothing in the compiler knows which line did it. A name this machine has no register for is refused rather than dropped, because the list is the program saying which registers it may not leave anything in and an entry nobody read is a register something may still be left in. `memory` and `cc` are the two entries that are not registers: `memory` is the barrier above and is nothing a register list could hold, and `cc` is already known, because the flag tracking takes every instruction it does not recognise as writing the condition state and every instruction in a template is one this machine describes. A clobber the instruction writes anyway is left off it, which is what a statement listing three of `cpuid`'s four registers is doing, since the allocator would otherwise be handed one register with two definitions.

A template the reader cannot take apart, such as one with an unconditional jump to a label of its own or an instruction the machine description does not have, is kept as its text. The object writer fills it in the way the listing does and hands it to the assembler on its own, and lays down the bytes and relocations that come back where the instruction is, so the unit keeps its line table and its frame rules under `-g`. That works when nothing in the text reaches past it: a numbered label it writes and jumps to is a place in its own bytes, and a name it only uses is left for the linker. A template that defines a name, switches section or aligns what follows only means what it says next to the other templates of the file, so a unit with one of those is assembled from its listing instead, the way gcc assembles every unit, and that path still refuses `-g`. What the text names is spelled into it the way gcc spells it: a constant as `$5`, or `5` under `%c`, the address of a name as the name, and an object in memory as the address the instruction's memory operand ends up at. An operand in a register is spelled after allocation, since the register is not known before then. The text holds a hole that names the instruction's own operand and a width, the modifier's (`b`, `w`, `k`, `q`, `h`) or the operand type's when there was none, and the writer fills it with the register the allocator chose. Outputs go in as definitions, inputs as uses, an output tied to an input by `+` or by a number reuses its register, one written `&` is written early, and every register a call may write is taken away from the inputs for the length of the statement, because the text may write any of them without saying so. A constant is spelled into the text only when its constraint allows one, so `"a" (0x1234)` is a register holding the number and `%h0` of it is `%ah`. A line that names an operand in a register and holds an instruction the reader knows for those arguments, and still could not be read, is refused rather than kept, since the reader said no to it for a reason of its own: `addq %1, %k0` is a quadword add into half a register.

Reading a statement's operands back off the instruction is one rule in one place, `rucc_ir::AsmOperands`, because the constraint list is the only record of which entry took which value and two readers of it would be two chances to disagree. It refuses a list that does not describe what the instruction carries rather than guessing, since which register file an operand travels in is a decision the front end made with the type in hand.

A structure or a union travels in a register when the whole of it fits in one, and as an address whatever its constraint says when it does not. It has no value of its own that a register holds, so the one that fits travels as the integer its bytes spell: the object is read where it is, the number is what the assembly is handed, and an output of that kind is written back into the object the same way. Both accesses are the whole object at once and go through no type at all, which is what a copy does and for the same reason, since the bytes have a type at each end rather than one in the middle. What fits is a size a register has, which is a power of two up to the width of an address, so a three byte structure is not one, because the load and the store either side would touch a fourth byte the object does not own, and neither is a sixteen byte one, because that is two registers and an operand is one. gcc takes both of those and gives the second half of the second one away, which is a thing to do rather than a rule to copy, so those are still refused here. The rule is `rucc_sema::in_a_register` and it is one function because the checking and the walk to the IR have to agree about which operands are which.

Top-level `asm` at file scope contributes to the output in source order, which the kernel uses for building alternative-instruction tables and static call sites, and which the incbin header uses for putting a file's bytes into a program. Verbatim is what a compiler that prints assembly for someone else to assemble does, and this one writes the object file itself, so a template is read rather than copied: the directives in it say that a section holds these bytes under these names with these alignments, and that is what a global is, so the template becomes the globals it defines and both `-S` and `-c` are written from the same ones. The labels of one template land next to each other in the order written, because the object writer lays globals out in module order and the file-scope templates are read before the declarations are walked, so the distance a template computes between two of its labels is the distance the program gets. The same line 11.1 draws applies here: a template with an instruction in it is refused with a message that says so, until there is an assembler that can turn one into bytes.

A `.set` in one of those templates is the one directive that names something without writing any bytes, and what it says is that a name stands for another name, which is a second symbol at the first one's address. That is an alias and nothing else, so it becomes one, and it is written out after the declarations have been walked because the name a template equates may be defined below the template. What the directives around it said about the name is what the name gets: `.globl` and `.weak` say how the linker sees it, `.hidden` and `.protected` say how far it reaches, and a name no directive spoke about is local, which is an assembler's answer rather than a choice made here. A name the file also defines keeps its own definition, the way it does for a function or an object written twice. The target has to be something the file defines, since an alias is a symbol at an address in this object, and the two other shapes of the directive are refused by name until there is somewhere to put them: `.set` of a number is an absolute symbol, which no object writer here can say, and `.set` of a name with a distance on it is an address rather than a symbol, which an alias has no room for.

Bytes a template writes before it writes any label are a global as well, with a name minted for them, since a name is what a global has and nothing outside the template can refer to these bytes. They go into the module in front of the label that follows them and in the same section, so the first byte under that label is the one written under it and a program walking backwards from it reaches the bytes above. A label written as a number is not a global at all. It is local, it may be written again further down, and what it is for is the distance from it to somewhere else in the same template, so it is kept as a position and the run of bytes it stands inside is left alone, which is what keeps the bytes either side of one in the same global the way an assembler keeps them in the same section. A reference to one is read backwards only: `661b` is the last label of that number above the reference, and `661f`, which is the next one below it, is refused by name rather than answered with the one above it, because finding it is a second pass over the template and this reader makes one. `.pushsection` and `.popsection` are the section directive with a stack behind it, which is how a template writes something into another section without having to know which one it was standing in, and a pop with nothing pushed is refused. A distance from one section to another is refused wherever it is written, with the one exception that is what programs actually write: how far a place is from the bytes holding the answer, which is `.long somewhere - .` and is a relocation the linker resolves rather than a number this reader could work out, since the linker is what places the two sections. It becomes a datum of its own in the image, held apart from the address of a name because the two are read differently, and the symbol it names is the global the place stands inside with the distance into that global as the addend, because the place is usually a local label and the object file holds no symbol for one of those. It is four bytes wide and nothing else, which is the width the relocation has on this target and the width every program that writes one of these uses, and the format that has no relocation counting from the front of those four bytes refuses it by name rather than writing one that counts from the back. A table of these in one section naming code in another is what an alternative instruction block in a kernel header is made of, which is the shape this is here for.

## 11.3 Object files

Three formats, all written through the [`object`](https://crates.io/crates/object) crate's writer with our own layer above it for the parts it does not model.

**ELF** for Linux and the freestanding targets. Sections, symbols with the full binding and visibility matrix, `SHF_*` flags, section groups for COMDAT, `.init_array`/`.fini_array` for constructors with priorities, `.note.GNU-stack` (whose absence makes the stack executable, a real and recurring security bug), `.note.gnu.property` for CET and BTI markers, and `-ffunction-sections`/`-fdata-sections` for linker garbage collection. Relocations per target: the x86-64 set including the TLS relaxation-eligible ones, the AArch64 set including the ADRP/ADD pairs and their TLS forms, and the RISC-V set including the `R_RISCV_RELAX` markers and the paired HI20/LO12 relocations, which are their own small nightmare because the LO12 relocation references the HI20's *symbol* through a label.

**Mach-O** for Apple platforms. Segments and sections, the `__TEXT`/`__DATA`/`__DATA_CONST`/`__LD` layout, symbol table plus indirect symbol table, scattered and paired relocations, `.subsections_via_symbols` for dead stripping, and the platform version load command that current linkers require.

**COFF** for Windows. Sections, symbols with storage classes, COMDAT selection kinds, `.pdata` and `.xdata` for SEH unwind, and the associative-section mechanism that makes `-ffunction-sections`-equivalent behavior work.

The layer above `object` handles what it does not: relocation *selection* per target and per addressing mode, symbol attribute mapping from our IR's linkage and visibility, section naming conventions per platform, and the alignment and ordering rules that each linker expects but no format document states.

That layer is one piece of code for all three rather than one per format. Which sections a file has, what goes in each, which symbol says where each thing is and what each relocation is against are the same questions with the same answers whichever format is being written, and the places where a format has an opinion are a short and closed list: the relocation number, the field a visibility goes in, the note saying what the file was built to have checked, and the marker whose absence makes the stack executable. A second copy of the layout would be a fix to one platform every time a bug was found, and which platform got it would be whichever one the person who found it was building for.

The one thing a format asks for outside that layer is on the relocation the assembler produces. ELF measures the distance from where the four bytes start and folds everything else into the addend, so one relocation type covers every instruction. COFF measures from where the instruction ends and says how far that is in the relocation type itself, `IMAGE_REL_AMD64_REL32` through `REL32_5`. Neither number can be recovered from the other, because a displacement of minus four with nothing trailing and a displacement of zero with four bytes trailing add up the same, so the relocation carries the count of trailing bytes alongside the addend it is already inside. Only the assembler knows it: by the time a writer sees a relocation, the instruction it sits in is bytes like any others.

What the assembler hands to that layer is described in `rucc-object` rather than in `rucc-asm`, which is the bytes, where each function sits in them, and every place in them that names something the file does not contain. It goes in the lower crate because the crate that writes the file is the one that has to be able to say what a file is made of, and because two descriptions of the same handover, one on each side of it, would be two things to keep in step for no gain. It is also why a relocation in it names a kind of reference rather than a number: which number that is, is a fact about the file format and belongs to the writer, and which kind of reference an instruction wants is a fact about the instruction and belongs to the assembler.

That handover reaches the same layer the compiled path reaches, and until tamnd/rucc#1514 it stopped at one format. A file the compiler compiles had been written as ELF or as COFF for as long as the list of format opinions has existed, and a file the compiler assembles went through a second copy of the symbol mapping with a refusal of anything that was not ELF in front of it, so `rucc --target=x86_64-windows-gnu -c probe.S` answered that there is no object writer for the target while a `.c` for the same target compiled. That message is what a missing back end says, which is a second cost of the copy: the shape of the code decided what the error sounded like, and it sounded like a much bigger thing being absent. Both paths ask the same list now, so a format that can hold what this compiler compiles can hold what it assembles, and neither path can be the one that was forgotten.

Moving it found the one answer on that list that is not the same question in both formats. A `.globl` on a label with no `.type` beside it is a name with a binding and no type, which ELF records in two fields and says nothing further about. COFF has one field for both, so the writer underneath maps a name of no type to `IMAGE_SYM_CLASS_LABEL` whatever its binding says, and a label is local. The same two lines of assembly gave `T` on ELF and `t` on COFF, and a linker cannot see a `t`. So what the mapping is asked is the type and the binding together rather than the type alone, and an untyped global or weak name on COFF is written as the kind that carries an external storage class. ELF is left exactly as it was, since there the answer to one question was never the answer to the other.

Which relocation an address wants is decided long before the writer sees it, because it depends on something the writer cannot know. Everything we emit is position independent, so the address of a name is normally the distance from the instruction asking to the name, which the assembler leaves a hole for and the linker fills in. The linker only has that distance when it is putting both ends in the same program, and a function this file merely declares may turn out to be in a shared library, so a position independent link refuses the distance rather than guessing one. The answer is `R_X86_64_REX_GOTPCRELX` against the global offset table: the linker gives the name a slot, the slot is in this program so the distance to it is a number the linker has, and the code loads the address out of the slot instead of working it out. It costs one load, and the linker takes the load back out again and writes the `lea` it would have been when the name turns out to have been in this program all along.

Which names want it depends on which link is coming, and there are two answers. Where the link produces an executable it is functions only, and only the ones this file does not define. A variable another file defines is still reached by working the distance out, because the linker answers a reference to one in an executable by making room for it in this program and copying it there, so the name really does end up somewhere this file can measure to. A function cannot be copied: it has exactly one address that every object in the program has to agree on, or two pointers to it compare unequal.

Where the link may produce a shared library, which is `-fPIC`, every replaceable name wants it, defined here or not and function or variable. Replaceable is the question the whole thing turns on: the dynamic linker looks an exported name up in load order and the first definition it finds is the one the entire process uses, so a library that reached its own copy of an exported variable from the instruction pointer would be the one part of the program not using the definition everything else was using. A `static` is never replaceable, and neither is a name marked hidden, which is not in the table to be looked up, or protected, which says a reference from inside the library binds to the definition inside it. That is why `-fPIC -fvisibility=hidden` costs a library nothing.

What `-fvisibility=hidden` marks is the names this file defines, and it stops there. A name this file only declares is one it knows nothing about, so the flag says nothing about it and it stays default and stays in the table. The distinction is easy to lose because the flag is described as a default for declarations and a declaration is what an `extern` is, and losing it is tamnd/rucc#1234: libexpat is built with `-fPIC -fvisibility=hidden`, it reads `stderr`, `stderr` is in libc, and calling it hidden asks the linker to resolve it inside this object, which is a link that stops. An attribute written on the declaration is a different thing and still counts, because a program that writes one has said where the definition is going to come from, and gcc 16.2.0 does the same on both halves: it gives a plain `extern` a table slot and `STV_DEFAULT`, and a marked one the distance and `STV_HIDDEN`.

Nothing here is a judgement call the compiler is free to get wrong quietly. The static linker refuses `R_X86_64_PC32` against a name it can see is replaceable when it is making a shared object, so the cheap form in a library is a link that stops rather than a program that runs on the wrong copy, and the message it stops with is advice to recompile with `-fPIC`. That is how tamnd/rucc#756 was found, and it is the same shape as the visibility bug above: nothing in the suite had ever linked a shared library, so an assumption that only a shared library can falsify went unfalsified for as long as it was there.

The unwind table is subject to the same rule and is easy to forget about, because nothing in the program asked for it. Every function gets a record, and a record has to say where its function is, and if it says so by naming the function then it has named something the loader may answer with a definition from somewhere else. The linker refuses that distance exactly as it refuses the one in the code, so a single record is enough to stop a library from linking, and every function has one. The record measures to the section the function is in with the function's offset as the addend, which is the form gcc reaches by measuring to a local label it emits at the top of each function. The record of where a patcher's room is is written the same way and for a second reason besides, which is that the room is in front of the name.

That check is `cargo xtask dso`. It builds a shared library out of `tests/dso`, where the two files that go into the library are the only thing this compiler compiles and everything around them belongs to the system compiler, because a fixture whose halves are both wrong in the same direction agrees with itself. Then it reads the library's dynamic symbol table, runs a program that opens the library and asks it questions, and runs that program again with another library loaded in front of it. Sixteen answers, and the reason it is not one is that no two of them fail together: a link that succeeds says nothing about `st_other`, a table with the right names in it says nothing about which copy of a variable the library reads, and neither of them says anything about whether a call inside the library can still be interposed. The library is built twice, once from the listings this compiler writes and once from the objects it writes itself, because those are two separate pieces of code and for a long time only the first was ever linked here. The eleven answers about what the library does come off the listing build, so that a failure is something a person can read, and the object build has to link and has to say the same four things about its names. That is the gap the unwind record fell through: a real build never passes `-S` and then runs `as` by hand. `cargo xtask ci` runs it beside the safety suite and skips it the same way, out loud and with the reason, because it wants a Linux runner for the same reason the suite does.

Calls need none of this. A call already asks for `R_X86_64_PLT32`, which is what a call to a name another object may define wants, and which the linker relaxes into a direct call when it turns out not to be one. Which names want the table is a fact about the whole module and about the command line, and the code generator is given one function at a time, so it is worked out once in the driver and handed in.

The same fact is read a second time, and by something else, before any of that. If the dynamic linker may hand the process another definition of a name, then the body of that definition here is not necessarily the body that runs, so an analysis that reads a body and writes down what it found has read the wrong function. That is why `-fPIC` costs more than the load it costs in the code: `nofree` on a call site, the ranges a callee dereferences, which parameters escape, all of them come off a body, and a library may not believe a body it exports. `-fno-semantic-interposition` is the build promising that it may, which is section 4.6, and is what every distribution puts on the line. The rule is the one above and shared with it rather than written twice, but the two answers are worked out separately and only one of them is handed to the code generator, because the promise says nothing about how an address is reached and gcc does not change addressing under it either. The `LD_PRELOAD` row of `cargo xtask dso` is the case the promise turns off, so the check that a change here needs is already there.

The other two formats answer differently and are not given the ELF answer. Mach-O has a two level namespace, so a name a library defines is bound to that library rather than looked up in load order, and it has no copy relocations, so a variable defined elsewhere wants the table whichever link is coming. COFF decides what leaves a DLL by an export table the linker is handed rather than by anything in the object. Neither has an object writer here yet, so both are left where they were until one does.

How far a name reaches is one of the facts that has to survive that handover, and a machine function is the only thing the assembler and the writer are ever given. So a machine function carries its own binding, which is the three an object file can say rather than the five the IR has, and the narrowing from one to the other is done where a function is lowered. A function whose binding did not survive is one every object announces to the linker, which is a `static` helper two files may not both have and a link that fails on the second one.

The visibility travels beside it and is a different question asked of a different linker. The binding is what the static linker does with a name while it is building the output, and the visibility is what the dynamic linker may do with it once that output is a shared library and is being loaded. A hidden name is still global to the static link, so two files in the same library reach each other by it; it is simply not in the dynamic symbol table afterwards, so nothing outside can name it or replace it. All three of `STV_DEFAULT`, `STV_HIDDEN` and `STV_PROTECTED` survive unnarrowed, because ELF records all three and it is the format rather than the machine that decides how many there are.

Both facts are said in the object writer by writing `st_other` rather than by choosing a scope and letting the writer underneath infer one, which is the shape of the bug in tamnd/rucc#733. A writer with one word for the binding and the visibility says something about both every time it means to say something about one, and what it said there was hidden: every global came out `STV_HIDDEN`, so a shared library built out of these objects had an empty dynamic symbol table and `dlsym` could not find a function the file plainly defines. Nothing caught it because a static link does not read the field at all. The check that catches it is one that builds a shared library and reads its dynamic symbol table, and the tests are written against `st_other` itself rather than against the reader's idea of a scope, since the reader's word is the one that was misread.

Which section each name goes in is decided the same way and in the same place. `-ffunction-sections` and `-fdata-sections`, described in section 4.7, reach the writer as one two field answer rather than as two booleans read separately by the two output paths, so the listing `-S` writes and the object `-c` writes cannot come to disagree about where a function went. The name of a split section is worked out once, beside the type that says what kind of place a variable wants, for the same reason. Nothing else about the file moves: the bytes, the symbol values within their own sections, the sizes, the bindings and the relocations are what they were, and the only thing that changes is which section header a symbol points at and, for a relocation, which section it is recorded against and how far into it. A relocation is in whichever function's bytes it fell in, which is a question only the split path has to ask, because when there is one text section every offset in it is already the offset in it. An empty `.text` still opens the file, since that is what the writer underneath starts with and what gcc leaves behind under the flag.

The three formats do not say it the same way. ELF names each section after what is in it, `.text.f` and `.rodata.x`, with the flags of the section it came out of, since splitting must not quietly change whether the page a variable lands in is writable. COFF gives every one of them the name of the section it came out of and a symbol saying which group is which, which is a COMDAT and is more than the ELF form says: the linker keeps one section out of every group naming the same symbol. That is what a Windows toolchain does with `/Gy` and what clang writes for these flags on a Windows target. Mach-O writes what it wrote before, whatever was asked for, because every Mach-O object ends with `.subsections_via_symbols` and so already tells the linker it may split a section at each symbol and drop the parts nothing reaches. Clang answers the same way there.

The listing says the same thing in text. ELF has `.hidden` and `.protected`. Mach-O has one of the two, `.private_extern`, which is a symbol that leaves this object and does not leave the library, and has no spelling of protected because the format cannot say a symbol is exported and cannot be interposed. COFF has neither, since what leaves a Windows DLL is decided by an export table the linker is handed rather than by a bit on each symbol. A `static` name gets no directive on any of them, because a name the static link has already finished with is not in anybody's dynamic table whatever the field says, and gcc writes none for one either.

## 11.4 DWARF

DWARF 5 by default, DWARF 4 under `-gdwarf-4`, written through [`gimli`](https://crates.io/crates/gimli)'s write support.

What is written today is the line table, the types and the functions: `.debug_line`, the strings it names in `.debug_line_str`, a compile unit in `.debug_info` carrying the producer, the language, the file, the directory and the ranges the unit covers, the abbreviation in `.debug_abbrev` that unit is written against, an entry for every type the unit's functions mention, a `DW_TAG_subprogram` for every function it defines, a `DW_TAG_variable` for every variable it defines at file scope, a `DW_TAG_variable` for every local lowering gave a frame slot with a `DW_OP_fbreg` saying where in the frame it is, a `DW_TAG_variable` with a list of stretches in `.debug_loclists` for every local the back end kept in a register instead, a `DW_TAG_lexical_block` with its addresses in `.debug_rnglists` around every local the program declared in an inner scope, and the names all of those carry in `.debug_str`. That is enough for `addr2line` to answer a program counter with a file and a line, enough for a debugger to produce a backtrace with the argument types in it, enough for one to print a variable the program wrote outside every function, enough for one to print a local wherever it is being kept at the address it stopped at, and enough for one to tell two locals of the same name in two scopes apart. A variable that is dead at an address is said to be unavailable there, both one kept in a register and one in the frame whose bytes are handed on, and the differential at the end of this section checks that against another compiler on the same program. The line table came first because a report from the safety monitor carries a program counter and deliberately carries no source location, for the reason `spec/safe-memory/06-instrumentation.md` section 6.5 gives, so until there was one line table every report out of a corpus run had to be read backwards out of a disassembly. Ranges rather than a low and a high PC on the unit, because `-ffunction-sections` puts every function in a section of its own and a single pair cannot cover sections a linker may place anywhere.

The front of a function is the one part of it no instruction accounts for. The pushes, the frame and the moves that put the arguments where the body expects them came from no expression in the source, so every one of them carries a dummy span, and a table built only from instruction spans leaves a hole there. A program counter in that hole gets no answer at all rather than a slightly early one, which is the worse of the two for whoever is reading a backtrace. So a function carries where it was declared, from the lowering down to the assembler, and the assembler opens every function's rows with that line at offset zero. gcc puts the line the opening brace is on over those bytes and this compiler puts the same one. Two rows on one byte is one row and the first of the two wins, which is what a function with no prologue at all looks like, and the declaration is the right answer there as well: it is what gcc says, because gcc always builds a frame at this level and so always has a byte for the brace to be about, and it is what a breakpoint on a function wants rather than the line of whatever its first statement happened to be.

The end of a function has the same hole for the same reason, and the closing brace fills it. An epilogue is the frame going back the way it came, so no expression asked for any of it and none of it carries a span, and without one the bytes are covered by whatever the last statement of the body was. gcc names the closing brace over them. The span of a body runs from its opening brace to one past its closing brace, so both ends come from the one span the function already carries, and the code that builds an epilogue puts the second end on every instruction it writes.

There is a third kind of instruction nothing in the source asks for, and it is a call. The stores into the outgoing argument area, the copies a structure passed by value is made of, and the call instruction itself are the calling convention's answer rather than anything a rule matched a term against, so they have nothing to inherit a span from, and a whole call statement could produce bytes that no row covered. They carry the span of the call now, which is what gcc names over all of it. It is worth more than it sounds: over the SQLite amalgamation, putting a span on the instructions a call is built from moved the share of gcc's lines that this compiler also names from 82 percent to 89, and the closing brace and the front of a function took it to 94.

The fourth kind is the rest of the frame, and it is filed under the opening brace with the prologue rather than under the declaration it came from. A slot exists because the address of something was taken and a store into one exists because the call left the incoming value somewhere else, so neither is anything the program asked for, but both do have a declaration to inherit a line from and that is the trouble. A parameter's declaration is often in a prototype in another part of the file, and a declaration span there puts the front of a function on a line hundreds of lines away from itself, which is a wrong answer rather than an early one: an address resolved that way names another function's neighbourhood. A parameter list written down the page does a smaller version of the same thing. Every slot of a known size is at the top of the entry block above anything the program wrote, and gcc covers all of that with the brace, so that is what it gets. A slot whose size is not known until the declaration is reached is the exception, since it is built where the declaration is and there really is code on that line. Over the SQLite amalgamation this is the whole of the difference in where lines are named: 17 functions named a line outside themselves before it and none do after.

Whether the lines are the right lines is checked by `cargo xtask lines`, which compiles the same source with both compilers, reads both tables back with `readelf` for the reason the unwind check reads its own table with something that is not ours, and counts how far apart they are function by function. It cannot compare addresses, because the two compilers do not write the same instructions and no address in one has a counterpart in the other. What it compares is which line the first byte of each function belongs to, which lines each table names for it, and whether any of them is a line outside the function. The four shares it measures have floors under what the SQLite amalgamation gives today, and what is still between the floors and agreement is enumerated in tamnd/rucc#1613 rather than left as an impression.

What the types are written from is a table of shapes rather than the compiler's own types, and the translation into it happens in the driver. A shape is a DWARF entry with its attributes already decided, so every question C answers and DWARF does not is settled before the crate that writes bytes sees anything: what `long` is on this target, which of two spellings of one width to write, whether a record is complete, where a bit-field's bits sit. The crates are laid out so that the object writer is below the type system rather than above it, which is right, and a description of a type has to cross that line somewhere. It crosses in the driver for the same reason a path does: the driver is the last place the checker's types are still in hand. The IR was never a candidate, because what the IR needs about a type is its size and its lanes and it has never carried anything else. What it buys is that the writer stays unit-testable against DWARF alone, and what it costs is that a table can say something C cannot mean, which is the same trade the machine IR makes and has the same answer: the thing that catches it is a reader rather than the writer, and `readelf --debug-dump=info` is that reader.

Every reference inside the table is an index, so a type that reaches itself is an ordinary entry rather than a special case: `struct node { struct node *next; }` is a pointer whose target is the record that holds it. The entries are created with their tags first and filled in afterwards, which is what lets an attribute name an entry that does not exist yet.

A function whose signature cannot be fully described gets no `DW_TAG_subprogram` at all. The absence of a `DW_AT_type` in DWARF is not silence, it is the word `void`, so an entry for a function whose return type could not be written would say the function returns nothing. A debugger handed no entry falls back to the symbol table, which is what it does for every function this compiler has ever emitted, and a debugger handed a wrong return type has no way to find out. Three kinds of type are undescribable today and each of them needs a field the shapes do not have: `_BitInt(N)` wants a base type with a bit size on it, a GNU vector wants `DW_AT_GNU_vector`, and `_Complex` over an integer half, which is a GNU extension, has no DWARF encoding that means it. A record is the one thing that bends rather than breaking, because losing a record loses every function that takes a pointer to one, which in a real program is most of them: a member whose type cannot be described is left out and the record's size and every other member's offset still stand. The other of the same kind is a typedef. Every typedef name the program wrote at file scope gets a `DW_TAG_typedef` saying what it stands for, and an ordinary typedef binds its name to the very type the name stood for and interns nothing of its own. The names are kept in a list beside the type table, because the alternative is to make each typedef a type of its own, and then two names for one type are two identifiers and the equality of two type identifiers stops meaning the two are the same type, which is the question that table is built to answer in one comparison. A list changes nothing about what a type is. Which of two names a particular declaration was written with is a fact about the declaration rather than the type, so the checker keeps it in a table of its own beside the tree, with the type the name stood for, one entry for each declaration whose specifiers named a typedef. A parameter, a local, a file-scope object or a function's return type then has its type built over that name's entry, walking through the qualifiers, the pointers and the arrays the declaration put on top of it: `size_type n` points at the `size_type` entry, `const size_type m` at a const over it and `size_type *p` at a pointer to it, which is what gcc writes and what makes a debugger print `size_type` for all three. A function type inside is not walked into, since its parameters were not written with the name. Where the name's type is not inside the declaration's at all, because an initializer gave an array its length after the name was read, the declaration points at the type it has. A parameter's entry is also the parameter's own type rather than the one the function type has, so `const int x` keeps its `const`, as it does for gcc. On SQLite at `-O2`, 8527 of the 15452 parameters and variables with a type reach a typedef under their qualifiers, pointers and arrays, against 9005 of 16192 for gcc. A record member written with a typedef name gets the same, from a list the type table keeps beside the records with the record, the member and the name, since a member is not a declaration in the tree and which name it was written with changes nothing about the record's layout or about which records are compatible. Both of these are less than the truth rather than other than it, and both are named here so that a reader of a dump knows which it is looking at.

An enumeration carries its enumerators, which are `DW_TAG_enumerator` children with a name and a value each. The list is not something the type system has any use for, since an enumerator is a name in a scope and what has the type is the enumeration, so it is kept on the enumeration's declaration in `rucc-types` for this one reader: the scope the names are declared into throws away both the order and the tie to the enumeration, and a debugger with no list prints the number where the program wrote the name. Which DWARF form the value goes in follows the value rather than the underlying type, signed data for a negative one and unsigned data otherwise, and a reader wanting the number in the program's own type reads it through the underlying type on the parent. A value wider than sixty four bits has no form that holds it and that one enumerator is left out, which is the answer a record gives for a member it cannot describe and is right for the same reason.

Bit-fields are written with `DW_AT_data_bit_offset` and `DW_AT_bit_size`, which is the DWARF 4 and later spelling that counts from the start of the record. The older one counts from the start of a storage unit the reader has to work out and then depends on which way round the target is, and a writer that picks it is a writer that has two chances to be wrong about the same member. A function's `DW_AT_frame_base`, which is what a local's location is measured from, is `DW_OP_call_frame_cfa`, the call frame address, and that is the stack pointer the caller had at the call. The only other answer worth having is a named register, and the register it would have to be is the frame pointer, which this compiler leaves out of every function it can, so most functions would have nothing right to say. The ones that keep a frame pointer would still be described wrongly over their first few instructions, because a frame pointer is not one until the prologue has set it up, and the front of a function is exactly where a breakpoint on the function lands. The call frame address has neither problem: it is one value for the whole of a function, prologue and epilogue included, and the unwind table this compiler already writes for every function on every target says what it is at every address in it. What it costs is a reader having to consult that table, which is a thing a debugger does before it prints a frame at all. A build that asked for no unwind table gets the same rules in `.debug_frame` instead, which is gcc's answer too, and the frame base is read through that. The section is not loaded, so the program costs what one with no table at all costs. The differences from the unwind table are three and are all in how things are said rather than what: the header is marked with all ones rather than zero and has no augmentation, a record says where its header is as an offset from the front of the section with a relocation against the section, and where its function is as an address the width of a pointer followed by a length the same width, rather than a four byte distance. Only a build with neither table gets no frame base, since an expression a reader cannot evaluate is worse than an attribute that is not there, and that is now a format with no `.debug_frame`, or a unit assembled through its own listing, which refuses `-g` for now. A listing from `-S` does not say `.cfi_sections .debug_frame` yet either, because it carries no debug information at all yet, and it gets it along with the rest.

A variable the program wrote at file scope gets a `DW_TAG_variable` whose `DW_AT_location` is one `DW_OP_addr`, and the address in it is a relocation the linker fills in the same way it fills in a function's low PC. Against the section the variable landed in plus its offset into that section, which is what the object writer already does for a function and what gcc does for both, with one exception: a variable the linker is being asked for zeroed space for has no section to count from, so that one relocation goes by name. Only variables this unit defines get an entry. A name it declares and another unit defines is a name whose address belongs to somebody else, and a debugger wanting the type of one reads the unit that has it. That is one entry fewer than gcc writes, which does emit a declaration for an external variable the unit refers to, and the reason for the difference is that deciding which declarations were referred to needs a use set that nothing between the checker and here carries. The entry is written from the objects the back end laid out rather than from the declarations, so a name with an entry is always a name with a symbol to relocate against: one the checker saw and the back end did not is a `static` nothing read, and one the back end has and the checker does not is a name the compiler made up, a string literal or a compound literal, neither of which anybody can ask the value of by name. A variable whose type could not be described still gets an entry, which is the one place the rule for a function is turned around, and the reason is that the absence of `DW_AT_type` on a `DW_TAG_variable` cannot mean `void`, because nothing in C is a variable of type `void`, so a reader takes it as a type that was not recorded rather than as a wrong one.

A local is a different problem and not a smaller one. Lowering puts a scalar local whose address is never taken into an SSA value rather than a frame slot, at every optimization level, so there is no `-O0` where every local sits at a fixed offset from the frame base and one `DW_OP_fbreg` describes it. The way out that suggests itself is to stop promoting when `-g` is on and no optimization was asked for, which would give the frame gcc gives and one location expression per variable, and it is refused here. A build whose instructions depend on whether it is being described is a build where turning the description on moves the bug, and every report about one would have to be answered by first asking whether the program does the same thing without `-g`. What this compiler emits is the same with the flag and without it, at every level, and the debug information describes what was emitted.

So the order of the work is by where a local ended up rather than by optimization level. A local that has a frame slot is described by one `DW_OP_fbreg` at its offset from the frame base, and that is the first piece, because the offset is a number the frame layout already worked out and the expression is right at every address in the function. That covers every aggregate, every local whose address is taken, every `volatile` and `_Atomic` one, and all of them in a function that saves a place with `__builtin_setjmp`, which is the list of reasons lowering gives a local a slot. A local held in an SSA value needs a location list built over the register allocator's output, saying where the value was over each range of addresses, and that is the `-O2` obligation below arriving at `-O0` as well rather than instead of. The rest of it is on tamnd/rucc#1645. Over the SQLite amalgamation the first piece is 977 locals and 27 parameters with a location, against gcc's 8769 and 6299, and the ratio is the point rather than the shortfall: gcc at `-O0` gives every local a slot and this compiler gives one to the locals that need one, so what is missing is the locals that are in registers rather than locals that were forgotten. It costs 19,641 bytes of `.debug_info` over the amalgamation, which is 12 percent, and part of that is not the entries but the types they need, since a local can have a type no function signature mentioned.

What a slot needs before it can be described is a way back to the declaration it was made for, and there is none by the time the frame places it: a slot is known to the frame by the order the `alloca` for it was lowered in and by nothing else. So the lowering writes the declaration's number on the memory the `alloca` asks for, and the number travels from there. On the memory rather than on the instruction because the memory is what survives: an instruction is rewritten, moved and renumbered by every pass it goes through, and the table of accesses is appended to and never reordered. It is an opaque number rather than anything the IR understands, because the IR sits below the crate that has a type for a declaration and nothing between the front end that writes it and the back end that hands it back reads it. Selection carries it across to the machine function as which local is which declaration, and once the frame is laid out the machine function comes out holding each declared local's distance below the call frame address, which is one subtraction: the frame already knows how far up the caller's first stack argument is, and that is the call frame address. The driver is where the number turns back into a name, a type and a line, because the driver is the last place the checker's declarations are still in hand, which is the same reason the shapes are built there.

A function whose alignment the prologue had to force is left out of that list, and it is the one case with no answer to give. Rounding the stack pointer down to a multiple of what a local wanted throws away however far the caller left it from there, so the distance from the body's stack pointer to the call frame address is a different number every time the function is called. Those locals want a location counted from the frame pointer, which such a function always keeps, and that is a different expression from the one a frame base gives. The red zone and a frame that grows while it runs both do have an answer, because in each of them the offsets and the distance up to the caller are counted from the same register.

A parameter that got a slot is a local like any other, and its location goes on the `DW_TAG_formal_parameter` the signature already wrote rather than on a second entry of its own. Two entries of one name in one scope is a debugger's problem rather than a reader's, and the numbers are in hand to tell which parameter a slot belongs to, since the driver already knows which declaration each parameter of a signature was written from. What is left after the parameters have taken theirs is the locals proper, and they are written as children of the subprogram after them, which is the order DWARF asks for. A slot whose number has no name against it is a compound literal rather than anything the program can ask the value of, so it is left out. A local the program wrote straight into the body of its function is a child of the subprogram and one it declared inside a `{ ... }` of its own is a child of a `DW_TAG_lexical_block` instead, which the paragraphs on scopes below are about.

Nothing is written about a place in the frame in a build that has no table of frame rules at all, which now that `.debug_frame` is written is only a build on a format without that section. An offset from a frame base is unreadable where there is no frame base, so a name with one under it would be a debugger saying it cannot evaluate a variable it can see, which is worse than one that never heard of it. That is the same answer the frame base itself gives in that build and is given in the same place. A place in a register is not measured from anything, so it is as good in such a build as in any other and is written there, and a local that is in a register over part of a function and in the frame over the rest keeps the part that can be said and loses the rest. The addresses the lost part covered become addresses no stretch covers, which is a debugger saying the variable is unavailable, and a local that is only ever in the frame loses its entry altogether.

A local held in a value needs the same way back to its declaration and cannot be given it the same way, because there is no memory to write the number on: having none is what holding it in a value means. So it goes in a table on the function keyed by value, filled in by the SSA construction as it hands each variable's writes their values, and a variable nothing named leaves nothing behind, which is every temporary an expression needed somewhere to put. A marker instruction in the stream is the other way to carry it and is refused for the reason above: an instruction that reads a value keeps the value alive, so a function that is being described would get different code from one that is not, and a table nothing walks cannot change what comes out.

One declaration is many values, since every assignment to it makes one and so does every block parameter that collects two of them where control joins, and one value can be many declarations, since a pass that finds two values equal points the readers of one at the other and both names then mean the one that is left. Neither is a mistake to be ruled out, so it is a list of pairs rather than a map in either direction. A pass that substitutes moves the names the way it moves the readers, which is the rule that keeps them true: the declaration still holds the value it held, and the value is now spelled the other way. A pass that deletes a value without giving its readers somewhere else to look has deleted something nothing reads, and a declaration whose value went that way is one nothing can be said about over those addresses, which is the right answer rather than a lost one. What the pairs do not say is which of a declaration's values it holds at a given address, and nothing in the IR can say it. That is a question about where the definitions ended up in the code that came out and how long each of them survived there, which the back end knows and the IR does not, and answering it is the location list the paragraphs below are about.

A location that changes is written as a list rather than an expression, and the list goes in `.debug_loclists` with a `DW_AT_location` of `DW_FORM_sec_offset` pointing at it. Each entry is a `DW_LLE_start_length`: where the stretch starts, how many bytes it covers, and the expression that says where the local is over it. The start is the function's own symbol plus how far into the function the stretch begins, so the linker resolves it the same way it resolves the function's low PC, and a pair of plain numbers would have been wrong under `-ffunction-sections`, which puts every function in a section a linker may place anywhere. An address no entry covers is an address the local is nowhere, and a debugger stopped there says the variable is not available. That is the answer rather than a gap: a value that has not been computed yet, or whose last reader is already behind, is somewhere for part of a function and nowhere for the rest, and a debugger printing whatever is in the register now would be printing something else's number. A local that is nowhere over the whole of a function gets no `DW_AT_location` at all rather than an empty list, since both say the same thing to a reader and one of them is fewer bytes, and it keeps its name, because a debugger that knows a variable exists and says it is not available is telling the truth and one that has never heard of it cannot.

A place in one of those entries is either an offset from the frame base or a register, and a register is named by the number the target's DWARF numbering gives it rather than by the one the back end uses. The two agree on some targets and not on others, and the translation belongs to whatever knows which target this is, which is the driver for the same reason the shapes are built there. It is a fact about the class and the register together rather than about either alone, so the class travels with the register all the way from the allocator.

Selection carries a declaration across to the machine function the same way it carries a slot's and by the same opaque number, so a local the front end kept in a value comes out as which declaration each virtual register holds a value of. The pairs are written down as each register is handed out rather than once at the end over the map from values to registers, because that map remembers only the last register a value was written into and a constant is written again in every block that wants one. A local held in a constant would otherwise be findable in the last block of a function and nowhere else. One declaration is many registers for the same reason it is many values, so this is a list of pairs and not a map in either direction, which is the shape the list in the IR has. What turns a register into a place over a stretch of addresses is the allocator, and that is the next paragraph.

The allocator turns it into a place, and where the place holds is the value's live range, which the allocator already worked out and which is read rather than asked again for the reason the stack slot allocator reads it: two answers about one function are free to disagree and the one the machine runs is the allocator's. A stretch runs from the instruction after the one that wrote the value to the last instruction that reads it, both ends in it. The front is one instruction along because a register does not hold a value until the instruction writing it has run, and the back is where it is because nothing reads the value afterwards, so whatever goes in the register next cannot be seen by anybody asking. A value nothing reads has no stretch, which is the same sentence read the other way. A value the allocator had to spill is in the frame over its stretch rather than in a register, at the same distance from the call frame address a local with a slot is given, and a function whose alignment the prologue had to force has no answer for either of them.

A stretch is named by the instruction at each end of it rather than by a count of bytes, because a machine instruction has no length until it is encoded. So the join is made at the very end of the back end, after everything that is free to take an instruction out or move one has run, and a stretch stops at the end of its block. The pass that lays the blocks out runs after the allocator and may put them in any order it likes, so a value live from one block into the next gets a stretch in each of them rather than one stretch that would cover whatever the layout happened to put in between. Inside a block the allocator's order is usually the order the instructions are in, and then a stretch is a run of points. At `-O2` and above the scheduler runs after the allocator and moves instructions about inside a block, so there a run of points is no longer a run of instructions, and a stretch is found by where its two ends went instead. That is sound because of what the scheduler has to keep for the program to mean the same thing: it runs after the registers are handed out, so every write of a register stays in order with every read of it and every other write of it, and every access to memory stays where it was in the order of accesses. So a value is in its register from the instruction after the one that wrote it to the last one that reads it, wherever the two went, and a local in the frame is in its bytes from the first touch to the last. An end that is a spill, a reload or an edge move is not an instruction the liveness has a point for, and a piece with such an end gets no stretch in a reordered block rather than a guess. Over the SQLite amalgamation at `-O2` this takes the functions with no location list at all from 1931 of 2548 to 79. An allocator that splits a live range needs the same reading, since it has to say where each piece went.

The instruction at each end gets an address from the assembler, which already writes a row per instruction for the line table: the row says how far into the function an instruction begins and the row after it is where it ends, the last one ending where the function does. Turning a pair of instructions into a pair of addresses is the whole of what the driver adds, and what comes out is the list of stretches a `DW_AT_location` is written from, on the entry the signature already made for a parameter or on an entry of its own for anything else.

A local in the frame is usually in one place for the whole of its function, and that is what one `DW_OP_fbreg` says. From `-O1` up it may not be, because the stack slot allocator of section 36.7 puts two locals that are never wanted at the same time in the same bytes, and then the bytes are one local's over part of the function and the other's over the rest. One `DW_OP_fbreg` for each would have a debugger stopped where the second is live print the second under the first one's name, which is the stale place this section refuses to write. So a local that went in beside something else is written as a list instead, with one stretch in the frame over each piece of where the allocator says it is wanted, worked out the same way as a spilled value's, and an address outside them is one where the variable is unavailable. A local whose bytes are its own keeps its one `DW_OP_fbreg`, which is every local at `-O0` and under `-fstack-reuse=none`. A block whose instructions were scheduled is read by where the two ends of each piece went, for the reason given above for a local kept in a register. It keeps its name either way.

Two stretches of one declaration can cover the same address and disagree about where it is. What makes two of them arise is a name written a value that was already live, which is what `int m = a;` is, since the assignment computes nothing and both names are then behind the one value. Putting `m` on the value for the whole of its life would have the whole of `a` answer to `m` as well, everywhere either of them is, which is wrong from the moment the program writes one of them again. So the lowering records where the assignment was, as its block and the instruction in front of it, since an assignment that computes nothing is not an instruction and the one in front of it is the nearest thing that is. A pass that takes that instruction out leaves the point where the instruction was, as the one that was in front of it, and a pass that moves the instruction takes the point along, since the function remembers where each instruction a point was after last was rather than rewriting the point when it goes. A block merged into the one before it hands its top over as the place after that block's last instruction. The back end turns the point into the first machine instruction after it, and `m` holds the value's register from there to the end of that stretch and over the value's whole stretches in the blocks the assignment's block dominates, and nowhere else. A stretch stops at the end of its block, so two that overlap are in one block, and one that starts inside the other starts where the declaration was given its value, so the one that started first is cut there. What is left is two stretches that start at the same address, which is two values of one variable both live into a block, most often the one from the last trip round a loop and the one computed on this trip. Which of them the variable holds there is a question about the order the assignments ran in, so it is asked of the IR before selection rather than of the registers after it. Every assignment is a place: where a named value was computed, a block parameter a variable is, and a start point. A forward walk over the blocks takes the value the last assignment on every path in gave the variable, and a block whose paths disagree, or the entry, has no answer. For this to be sound no assignment can go missing, so a variable written a value it already holds records a start as well, and a name on a value that a pass takes out or renames into another becomes a start where the value was computed. Selection maps the answer onto the machine blocks and registers, and a piece of a register's live range that comes into a block the answer names another register for gets no stretch there. A piece that starts inside the block starts at an assignment and is kept. Where two stretches still disagree, which is now only where the paths into a block give the variable different values and the registers stay live, the address is left out of the list rather than answered with whichever of the two the walk reached first. A debugger then says the variable is unavailable there, which is the honest answer, and a wrong one would be worse than none. Where they agree the answer is the same either way and the two become one stretch. Over the SQLite amalgamation at `-O2` that leaves 1273 addresses out, against 39834 without the entry values, and about 28000 more bytes of variables have a location; tamnd/rucc#1801 has the numbers.

Two locals of one name in two inner scopes are one name to a debugger unless something says which addresses each of them covers, and `DW_TAG_lexical_block` is what says it. Over the SQLite amalgamation that is 12 functions of 2604 where the name alone is ambiguous, which is few, and the ones it is wrong for are the ones somebody is most likely to be standing in when they ask: a name is reused in a nested block precisely because the outer one is still live around it. A block is written for a scope a local of that function was declared in, or for one that holds a scope that was, and for nothing else. Every `if` body and every loop body in C is a scope, so writing them all would put an entry around most of the instructions in most programs and buy nothing by any of them, since telling two names apart is the whole of what a block is for and a block holding no name has none to tell apart. Deciding which ones are worth writing is one pass backwards over the scopes marking the ancestors of every scope that has a local, then one pass forwards building the entries, which works in one pass each because a scope is always numbered after the scope it sits inside.

Where a block's addresses come from is the source, rather than anything new carried down the compiler. A scope is a run of source bytes, every row of the line table already says which source bytes its instruction was built for because that is what a line table is, and the rows already say where each instruction is. So the addresses of a scope are the addresses of the rows whose bytes are inside it, joined up wherever they meet. Nothing had to be threaded through lowering, selection, the allocator or the assembler for this, and the nesting comes out right on its own: a scope's bytes hold the bytes of every scope written inside it, so its addresses hold theirs, whatever the back end did with the order. One stretch is written as a `DW_AT_low_pc` and a `DW_AT_high_pc` and several as a `DW_AT_ranges` into `.debug_rnglists`, which is the choice the compile unit itself makes and is made here for the same reason. A scope with no stretches at all, which is one whose code all went away, gets neither and is written anyway, since a reader takes that as covering whatever the parent covers while leaving the entry out would move the local up into the function and make it answer to a name it was not declared under.

A `for` whose first clause declares something is a scope covering the whole statement, which is what C 6.8.5p5 says it is, and a `for` whose first clause is an expression or is empty is not a scope at all. The difference is worth making rather than opening one either way: the second kind is most of the `for` loops in most programs, and an entry for each would cost a block per loop and hold no name.

A block's addresses are the addresses its own code went to, and they are not widened to cover the location lists of the locals declared in it. The two can differ, because a value lives for as long as something reads it and a name written in one block can be read in the next one along. Widening a block until it covered its locals' locations would let two sibling blocks overlap, and a debugger standing in the overlap would have two `i`s to choose between again, which is the thing the block was written to stop. Not widening cannot go wrong that way: a location outside its own block is simply never consulted, and what a debugger says there is that the variable is not in scope rather than another variable's value. Between an answer that is missing and one that is wrong this takes the missing one, which is the same choice the paragraph above makes for two stretches of one declaration that disagree.

At `-O0` the obligation is complete: every function has a `DW_TAG_subprogram` with correct low and high PC and frame base; every local variable has a location valid over its whole scope; every type is described, including the C-specific cases that are easy to get wrong: bit-fields with their offsets and widths, anonymous struct and union members, flexible array members, variably-modified array types whose bounds are runtime values referencing a location expression, and function pointer types with their parameter types.

At `-O2` the obligation is best-effort and honest. A variable that lives in different registers at different points gets a location list. A variable that is dead at a point is marked as such rather than given a wrong location, because a debugger showing a stale value is worse than one saying "optimized out". Inlined functions get `DW_TAG_inlined_subroutine` with the call site's location, so a backtrace through inlined frames is correct. This is the feature that makes `-O2 -g` usable at all and it requires the inlining chain from document 08 to survive every subsequent pass.

Line tables are generated from the source locations in the IR. The rules that matter for debugger behavior: `is_stmt` marks the instruction a breakpoint should attach to; the prologue-end marker tells the debugger where to stop for a function breakpoint so that arguments are already in place; a line entry with line 0 marks compiler-generated code with no source correspondence, which is better than attributing it to an arbitrary line.

Unwind tables are separate from the rest of the debug information and are not controlled by `-g`. An unwinder is handed a return address and has to answer two questions about the function it landed in: where the frame it is standing in ends, and where the callee saved registers went. The answer is a table indexed by address, kept in `.eh_frame`, and it has to be there in an ordinary release build because C++ exceptions, `backtrace`, profilers and crash handlers all read it. Every ELF function gets a record, including the leaves that need no rows in theirs, because an unwinder that lands on an address no record covers cannot tell an undescribed function from a described one and has to stop. In the assembly listing the rows are `.cfi_` directives placed after the instruction that changed the answer, which is where the assembler wants them and which is also how the integrated path builds the section, so the two cannot disagree. `-fasynchronous-unwind-tables` is the default on x86-64 Linux and `-fno-asynchronous-unwind-tables` turns the table off for a build that knows nothing will read it, which in practice is a kernel or a freestanding image. What it saves is the section rather than any instruction, since the table describes what the prologue already did and nothing is emitted differently because it is there. Whether either request is standing is asked once, of the options, rather than worked out at each of the two places that write a table, for the reason section 11.1 gives.

In an object this compiler writes, the section holds one header and one record per function. The header carries what every function on the target starts out with, which is what keeps a record down to the handful of bytes that say what changed, and the record carries the distances between the rows. A record cannot know where the linker will put its function, so the address it covers is left at zero with a relocation in `.rela.eh_frame` and what is written is a distance from the record to the function, which is what the augmentation string `zR` in the header announces.

Windows reads a different table and this compiler writes that one too. There is no header and no program per function there: `.pdata` holds one fixed row per function of three image relative addresses, saying where the function starts, where it ends and where its description is, and `.xdata` holds the descriptions, each four bytes of header and then a list of two byte codes saying that the prologue pushed a register, took so much frame, or put a register in a slot. The codes are in decreasing order of where in the prologue they happened, because the runtime reads them from the address it is unwinding at and works back to the front of the function, and the offsets they carry are from where the stack pointer ends the prologue rather than from the end of the frame, which is the one translation the two tables need. Both are built from the same rows, since what a row says is what one instruction of the prologue did to the frame and that is the question both tables answer. A row reaches its description by a local name of the form `$unwind$f`, which is what MSVC writes and what a dump shows, rather than by the section and an offset, which links the same and reads as a number. There is a fourth code and it is the frame pointer, which the header carries rather than the list: the low four bits of the fourth header byte are the machine's number for the register and the four above them are how far above the end of the prologue it was left, in sixteens. That one is why the prologue on this target is ordered the way it is. The codes count from where the stack pointer ends the prologue and reach that place by taking the header's constant off the named register, so a register pushed after the pointer was established sits below the place the codes count from and has no row the format can write. The order that does have one is the pushes, then the frame in one subtraction, and only then the pointer, which is what section 10.7 says the Windows prologue emits and what the writer turns into the header's register when it sees the row for it. A prologue whose shape is not one the codes have a spelling for is still refused by name rather than described as the nearest thing, which is the one place the two tables differ in kind, and the shape left over is the frame that forces its own alignment: the mask leaves the pushes at no constant distance from anything, so the pointer has to go up before it and there is nothing for the header to count them from. A build that needs one of those can pass `-fno-asynchronous-unwind-tables -fno-unwind-tables` until that shape has an answer of its own.

That is checked by `cargo xtask unwind`, which builds `tests/unwind` three ways and counts the frames a backtrace walks. Two of the three are this compiler's, the object and its listing assembled by `as`, because section 11.1 asks that those two cannot disagree, and the third is the system compiler's build of the same source. The count is compared against that rather than against a number written down here, because how deep a program's own entry is is the C library's business and differs between one and the next. Seven more answers on top of the count come from `readelf`, which is not ours, because a reader written beside the writer can hold the same wrong belief the writer does and agree with it. `cargo xtask ci` runs it beside the shared library check and skips it the same way, out loud and with the reason.

`-gsplit-dwarf` writes the bulk into a `.dwo` file and leaves a skeleton in the object, which on a large C++ project is transformative and on a large C project still meaningful. `-gz` compresses debug sections. `-fdebug-prefix-map` and `-ffile-prefix-map` rewrite paths for reproducible builds, and `SOURCE_DATE_EPOCH` is honored per document 03.

**Correctness testing** is by differential debugging: compile a corpus program with `-O0 -g` and with `-O2 -g`, run it under a scripted GDB and LLDB session that sets breakpoints and prints variables at defined points, and compare against the same script run against GCC's output. This finds the errors that a DWARF *validator* cannot, because syntactically valid DWARF can still describe the wrong thing.

The first of those is `cargo xtask debugger`, which builds `tests/debugger` twice and stops in the same function under `gdb` both times. One program either way, and the only difference is which compiler produced the object holding the function whose locals are being read: everything around it, the C library, the entry and the function the breakpoint is on, is the system compiler's in both, so a difference in what comes back is a difference in what was written about the locals. The breakpoint is a call rather than a line, because a line number would be comparing the two line tables as well and `cargo xtask lines` already does that, and the frame above the call is where the questions are asked. Five values have to come back the same as gcc's, and they are chosen to be five different ways for the answer to be wrong: a parameter, which is the case where the location has to land on the entry the signature already wrote rather than on a second one of that name, a local in a register that is live across the call, so where it is at the breakpoint is not the register it was computed into, the one of two same-named locals that belongs to the block the breakpoint is in, an array printed by value, and a read through a pointer parameter, which is the location and the type together since a wrong type reads the right address wrongly and still prints a number. Which names `info locals` reports is compared as well, because a name in scope that gcc does not have there is a block covering addresses the name was not declared over, and the same name twice is two entries under one parent, which is what the lexical blocks are for.

There is one question where the two are meant to differ and it is checked rather than skipped. A local nothing reads after a certain point has no value anywhere after it, and this compiler says the variable is unavailable, while gcc at `-O0` prints the frame slot it gives every local whether or not the value is still wanted. So that question is asked the other way up: gcc has to print a real value, which is what says the name is a real name and the question a fair one, and this compiler has to refuse. An answer that agreed with gcc there would be a register read that happened to still hold the number, which is the stale place this section spends several paragraphs refusing to write. Reading it back through something that is not ours is the point, for the reason the unwind check gives: a reader written beside the writer can hold the same wrong belief and agree with it. The same is asked of a second function built at `-O1`, where two arrays share their bytes and one of them is dead at the breakpoint: the live one has to read back as gcc's does and the dead one has to be unavailable rather than read out of bytes that now hold the other. `cargo xtask ci` runs it beside the unwind check and skips it the same way, out loud and with the reason, since a machine with no `gdb` on it is a check that did not run rather than one that passed.

## 11.5 Other metadata formats

**CTF and BTF.** The kernel generates BTF for BPF and for its own runtime type information, currently via `pahole` reading DWARF. Emitting BTF directly is not a 1.0 requirement (the kernel build's existing `pahole` step works on our DWARF if the DWARF is correct) but "our DWARF is correct enough for `pahole`" is an M11 exit criterion in document 14 and it is a strictly stronger test than a validator.

**Sanitizer metadata.** ASan needs global variable descriptors with redzones and their metadata section; UBSan needs static check descriptors with source locations. Document 12 owns their layout, which must match the runtime library's expectations exactly.

## 11.6 Linking

We invoke an external linker before 1.0, per document 04. The interesting question is whether that stays true.

**The case for an internal linker after 1.0.** The kernel's build uses linker scripts of real complexity, `--emit-relocs`, section garbage collection interacting with `KEEP`, and a two-pass link with `objtool` in between. Every one of those is a place where the external linker's behavior differs between `ld.bfd`, `lld` and `mold`, and where diagnosing a problem means understanding three linkers. Owning the linker would also close the portability story: one binary that compiles and links on all three hosts without a platform toolchain installed. And link time is a large share of a full-project build, so the throughput axis is partly gated on someone else's code.

**The case against.** A linker is a substantial project on its own; `mold` is already very fast and free; and the failure mode of a subtly wrong linker is worse than that of a subtly wrong compiler because it is harder to bisect.

The decision is deferred to document 19 and gated on a measurement: at M11, what fraction of a kernel build's wall time is linking, and how many of the bugs found during M10 and M11 were linker interaction bugs. If both numbers are high the project is justified; otherwise `mold` is the answer.

Until then the driver's obligation is to construct a correct link line per target and to pass through everything the build system asks for, which document 04 specifies and which the corpus in document 15 tests far more thoroughly than any unit test could.
