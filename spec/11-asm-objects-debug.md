# Assembly, objects, and debug information

## 11.1 The integrated assembler

We encode instructions directly to bytes rather than emitting text and calling `as`. Three reasons: an external assembler is a process spawn and a re-parse per translation unit, which is a large fraction of the compile-throughput budget; it is a dependency on GNU binutils or the Apple toolchain, which contradicts the portability axis; and the assembler is the place where a compiler's own instruction encoding gets validated, so having it in-tree means the validation is in-tree.

`-S` still emits assembly text, because people read it and because the assembly output is a debugging artifact we care about. The text path and the binary path share the same instruction description, so they cannot disagree about what an instruction is.

That shared description lives beside the register file, in `rucc-target`. For each machine opcode it holds the list of real instructions the opcode is, since an opcode is one instruction to the register allocator and is not always one instruction to the machine: a comparison is a compare and a set, an unsigned division is the clearing of the high half and then the division, and the pseudos that say where a value is are no instructions at all. Each instruction in the list is a mnemonic and a list of arguments, and an argument names the operand it is drawn from by its index rather than being the operand itself, because the assembler's order is not the operand vector's order, an instruction may write one operand twice, and an instruction in the middle of an opcode may name none of them. The width an argument is written at is on the argument, since a comparison of two 64-bit registers sets a byte and a shift of one reads its count from a byte.

An opcode nothing selects is described the same way as one a rule selects. A prologue pushes, a spill stores and a copy moves, and none of those is anything a pattern could match, but all of them reach the assembler and the encoder in the same function and are read there the same way. A second table for them would be a second place for an opcode to be missing from.

The bytes of one of those instructions are a second table beside the first, keyed the way an assembler keys one: by the mnemonic, by what kind of thing each argument is, and by the range the immediate falls in. A mnemonic is not an instruction, since `movl` is a different instruction given an immediate, a register, a load or a store, and a smaller immediate is sometimes a shorter instruction, so the key has to carry all three. It is not keyed by machine opcode, because that would be a third description of the same instruction and a third place for the three to disagree. A row is an opcode, what goes in the byte that names the registers, and how many bytes of immediate follow, and the walk that turns an opcode into text and the walk that turns it into bytes are the same walk over the same list, differing only in what they do with an instruction once they have it.

Choosing between two encodings of one instruction is the table's job and not the encoder's. Where the machine has a short form the encoder would need a special case to reach, the short form is a row in front of the general one and the lookup takes the first that holds the number, so the encoder stays a function of the row it was given. Where a short form is a win only on one register, or only for one constant, it is left out and said so, because a row that applies to one register is a row a reader stops checking. A whole-function decision is not a row at all: relaxation is the only one, and it stays a pass.

What surrounds the instructions is the object format's answer rather than the machine's, and the three formats do not agree. A Mach-O symbol carries an underscore in front of the C name and an ELF one does not, so a listing that got that wrong would fail to link against every library on the machine. A label local to a function is spelled `.L` on ELF and COFF and `L` on Mach-O, and one not spelled the local way ends up in the symbol table, where a debugger and a backtrace will show it as though it were a function. ELF says how long a function is and Mach-O has no way to. And ELF wants the marker saying the stack is not executable, whose absence makes it executable, which is a security bug rather than a missing nicety. So the directives are held per format, next to the printer and away from the instruction description, which is per machine.

**We also accept assembly as input.** `.s` and `.S` files appear in every real project. The kernel has thousands, and musl, FFmpeg and OpenSSL all ship hand-written assembly. A compiler that cannot assemble them needs an external assembler after all, which forfeits the point. So `rucc-asm` contains a real assembler with a real directive set: `.text .data .bss .section .globl .local .weak .type .size .align .balign .p2align .byte .short .long .quad .ascii .asciz .space .fill .set .equ .org .comm .lcomm`, the CFI directives `.cfi_startproc` through `.cfi_endproc` with the full register-rule set, `.macro`/`.endm`, `.rept`, `.if`/`.else`/`.endif`, and expression evaluation with the symbol arithmetic and relocation-generating operators (`sym@GOT`, `sym@PLT`, `sym@TPOFF` and the rest).

Both the AT&T and Intel syntaxes are accepted for x86, selected by `-masm=` and by `.intel_syntax`/`.att_syntax` directives, because inline assembly in the wild uses both.

**Encoding correctness is verified by differential disassembly.** Every instruction we encode is disassembled by an independent decoder and compared against the intended semantics; additionally, a CI job assembles the corpus's `.s` files with both `rucc` and the system assembler and compares the resulting bytes. Encoding bugs are silent and catastrophic, and this is the cheapest way to find them.

The comparison is of what the two say and not of the bytes they say it in. Both sides go through one decoder, ours from the bytes we wrote and the assembler's from the text we printed for the same instruction, and the two readings have to be the same instruction. Bytes cannot be compared directly, because we choose a longer encoding in the places listed above and will keep doing so until relaxation is written, and a check that fails on a difference we intend is a check nobody runs. A difference in what the two decode to is always a bug.

Relaxation, choosing the short form of a jump when the displacement fits, and growing it when it does not, is an iterate-to-fixpoint pass over the fragment list. It must terminate, and it must be deterministic; both are tested.

## 11.2 Inline assembly

GCC's inline assembly is one of the least-specified and most-depended-upon parts of the C ecosystem, and it is a hard requirement for the kernel.

The pieces: a template string with `%0`-style operand references and the `%` modifier letters that select an operand's spelling (`%w0` for the 32-bit form of an AArch64 register, `%b0` for a byte register on x86, and so on); output operands with `=` and `+` and `&` earlyclobber; input operands; constraint strings; a clobber list including `"memory"` and `"cc"`; the `volatile`, `inline` and `goto` qualifiers; and for `asm goto`, a label list making the statement a terminator.

**Constraints are a per-target language** and they must be implemented per target rather than approximated. The common ones (`r` `m` `i` `n` `g` `0`-`9` for matching operands) plus each target's specific set: on x86 `a b c d S D A q Q x y v` and the immediate ranges `I` through `P`; on AArch64 `w x r Q S Y Z` and the logical-immediate classes; on RISC-V `f A I J K`. The constraint determines which register class the allocator must use and whether a memory operand is acceptable, so it feeds directly into document 10's operand constraints.

The `"memory"` clobber is a full compiler barrier for memory: no load or store may be moved across it. The kernel's `barrier()` is exactly this and getting it wrong produces bugs that appear only under concurrency and only sometimes.

**`asm goto` with outputs** is required by current kernels and is the hardest case, because the outputs must be live on the fall-through edge and not on the indirect edges, which interacts with register allocation in a way that needs explicit handling rather than falling out.

Because we cannot verify the contents of an assembly template, inline assembly is a hard barrier for the optimizer: an `inline_asm` instruction with a `"memory"` clobber or the `volatile` qualifier is treated as an unknown call for alias analysis and is never moved, duplicated, or deleted unless its result is unused and it is neither volatile nor clobbering.

**A template with no instructions in it is the case to build first**, and it is not a corner of the feature. A program that wants a value computed where it stands, or a loop the optimizer must not touch, writes `asm volatile ("" : : : "memory")`, and forty years of bug reports about optimizers are full of them. What such a statement asks for is the barrier and the places its operands share, and no instructions at all, so it needs none of the assembler above and none of the allocator hints below. The back end lowers one today: an output an input is tied to, by `+` or by a matching constraint, is the register that input arrived in, because the template wrote nothing over it; an output nothing is tied to is a value the program has no claim on and is written as a zero, since the allocator is owed a definition before the use whatever the program is owed; an operand in memory is an address the front end already built; and the clobber list is not read, because a template with no instructions in it ruins no register. A template with anything in it is refused with a message that says so, until the assembler in 11.1 can turn one into bytes.

Reading a statement's operands back off the instruction is one rule in one place, `rucc_ir::AsmOperands`, because the constraint list is the only record of which entry took which value and two readers of it would be two chances to disagree. It refuses a list that does not describe what the instruction carries rather than guessing, since which register file an operand travels in is a decision the front end made with the type in hand and a structure goes as an address whatever its constraint says.

Top-level `asm` at file scope contributes to the output in source order, which the kernel uses for building alternative-instruction tables and static call sites, and which the incbin header uses for putting a file's bytes into a program. Verbatim is what a compiler that prints assembly for someone else to assemble does, and this one writes the object file itself, so a template is read rather than copied: the directives in it say that a section holds these bytes under these names with these alignments, and that is what a global is, so the template becomes the globals it defines and both `-S` and `-c` are written from the same ones. The labels of one template land next to each other in the order written, because the object writer lays globals out in module order and the file-scope templates are read before the declarations are walked, so the distance a template computes between two of its labels is the distance the program gets. The same line 11.1 draws applies here: a template with an instruction in it is refused with a message that says so, until there is an assembler that can turn one into bytes.

## 11.3 Object files

Three formats, all written through the [`object`](https://crates.io/crates/object) crate's writer with our own layer above it for the parts it does not model.

**ELF** for Linux and the freestanding targets. Sections, symbols with the full binding and visibility matrix, `SHF_*` flags, section groups for COMDAT, `.init_array`/`.fini_array` for constructors with priorities, `.note.GNU-stack` (whose absence makes the stack executable, a real and recurring security bug), `.note.gnu.property` for CET and BTI markers, and `-ffunction-sections`/`-fdata-sections` for linker garbage collection. Relocations per target: the x86-64 set including the TLS relaxation-eligible ones, the AArch64 set including the ADRP/ADD pairs and their TLS forms, and the RISC-V set including the `R_RISCV_RELAX` markers and the paired HI20/LO12 relocations, which are their own small nightmare because the LO12 relocation references the HI20's *symbol* through a label.

**Mach-O** for Apple platforms. Segments and sections, the `__TEXT`/`__DATA`/`__DATA_CONST`/`__LD` layout, symbol table plus indirect symbol table, scattered and paired relocations, `.subsections_via_symbols` for dead stripping, and the platform version load command that current linkers require.

**COFF** for Windows. Sections, symbols with storage classes, COMDAT selection kinds, `.pdata` and `.xdata` for SEH unwind, and the associative-section mechanism that makes `-ffunction-sections`-equivalent behavior work.

The layer above `object` handles what it does not: relocation *selection* per target and per addressing mode, symbol attribute mapping from our IR's linkage and visibility, section naming conventions per platform, and the alignment and ordering rules that each linker expects but no format document states.

What the assembler hands to that layer is described in `rucc-object` rather than in `rucc-asm`, which is the bytes, where each function sits in them, and every place in them that names something the file does not contain. It goes in the lower crate because the crate that writes the file is the one that has to be able to say what a file is made of, and because two descriptions of the same handover, one on each side of it, would be two things to keep in step for no gain. It is also why a relocation in it names a kind of reference rather than a number: which number that is, is a fact about the file format and belongs to the writer, and which kind of reference an instruction wants is a fact about the instruction and belongs to the assembler.

Which relocation an address wants is decided long before the writer sees it, because it depends on something the writer cannot know. Everything we emit is position independent, so the address of a name is normally the distance from the instruction asking to the name, which the assembler leaves a hole for and the linker fills in. The linker only has that distance when it is putting both ends in the same program, and a function this file merely declares may turn out to be in a shared library, so a position independent link refuses the distance rather than guessing one. The answer is `R_X86_64_REX_GOTPCRELX` against the global offset table: the linker gives the name a slot, the slot is in this program so the distance to it is a number the linker has, and the code loads the address out of the slot instead of working it out. It costs one load, and the linker takes the load back out again and writes the `lea` it would have been when the name turns out to have been in this program all along.

Which names want it depends on which link is coming, and there are two answers. Where the link produces an executable it is functions only, and only the ones this file does not define. A variable another file defines is still reached by working the distance out, because the linker answers a reference to one in an executable by making room for it in this program and copying it there, so the name really does end up somewhere this file can measure to. A function cannot be copied: it has exactly one address that every object in the program has to agree on, or two pointers to it compare unequal.

Where the link may produce a shared library, which is `-fPIC`, every replaceable name wants it, defined here or not and function or variable. Replaceable is the question the whole thing turns on: the dynamic linker looks an exported name up in load order and the first definition it finds is the one the entire process uses, so a library that reached its own copy of an exported variable from the instruction pointer would be the one part of the program not using the definition everything else was using. A `static` is never replaceable, and neither is a name marked hidden, which is not in the table to be looked up, or protected, which says a reference from inside the library binds to the definition inside it. That is why `-fPIC -fvisibility=hidden` costs a library nothing.

Nothing here is a judgement call the compiler is free to get wrong quietly. The static linker refuses `R_X86_64_PC32` against a name it can see is replaceable when it is making a shared object, so the cheap form in a library is a link that stops rather than a program that runs on the wrong copy, and the message it stops with is advice to recompile with `-fPIC`. That is how tamnd/rucc#756 was found, and it is the same shape as the visibility bug above: nothing in the suite had ever linked a shared library, so an assumption that only a shared library can falsify went unfalsified for as long as it was there.

That check is `cargo xtask dso`. It builds a shared library out of `tests/dso`, where the two files that go into the library are the only thing this compiler compiles and everything around them belongs to the system compiler, because a fixture whose halves are both wrong in the same direction agrees with itself. Then it reads the library's dynamic symbol table, runs a program that opens the library and asks it questions, and runs that program again with another library loaded in front of it. Eleven answers, and the reason it is not one is that no two of them fail together: a link that succeeds says nothing about `st_other`, a table with the right names in it says nothing about which copy of a variable the library reads, and neither of them says anything about whether a call inside the library can still be interposed. `cargo xtask ci` runs it beside the safety suite and skips it the same way, out loud and with the reason, because it wants a Linux runner for the same reason the suite does.

Calls need none of this. A call already asks for `R_X86_64_PLT32`, which is what a call to a name another object may define wants, and which the linker relaxes into a direct call when it turns out not to be one. Which names want the table is a fact about the whole module and about the command line, and the code generator is given one function at a time, so it is worked out once in the driver and handed in.

The same fact is read a second time, and by something else, before any of that. If the dynamic linker may hand the process another definition of a name, then the body of that definition here is not necessarily the body that runs, so an analysis that reads a body and writes down what it found has read the wrong function. That is why `-fPIC` costs more than the load it costs in the code: `nofree` on a call site, the ranges a callee dereferences, which parameters escape, all of them come off a body, and a library may not believe a body it exports. `-fno-semantic-interposition` is the build promising that it may, which is section 4.6, and is what every distribution puts on the line. The rule is the one above and shared with it rather than written twice, but the two answers are worked out separately and only one of them is handed to the code generator, because the promise says nothing about how an address is reached and gcc does not change addressing under it either. The `LD_PRELOAD` row of `cargo xtask dso` is the case the promise turns off, so the check that a change here needs is already there.

The other two formats answer differently and are not given the ELF answer. Mach-O has a two level namespace, so a name a library defines is bound to that library rather than looked up in load order, and it has no copy relocations, so a variable defined elsewhere wants the table whichever link is coming. COFF decides what leaves a DLL by an export table the linker is handed rather than by anything in the object. Neither has an object writer here yet, so both are left where they were until one does.

How far a name reaches is one of the facts that has to survive that handover, and a machine function is the only thing the assembler and the writer are ever given. So a machine function carries its own binding, which is the three an object file can say rather than the five the IR has, and the narrowing from one to the other is done where a function is lowered. A function whose binding did not survive is one every object announces to the linker, which is a `static` helper two files may not both have and a link that fails on the second one.

The visibility travels beside it and is a different question asked of a different linker. The binding is what the static linker does with a name while it is building the output, and the visibility is what the dynamic linker may do with it once that output is a shared library and is being loaded. A hidden name is still global to the static link, so two files in the same library reach each other by it; it is simply not in the dynamic symbol table afterwards, so nothing outside can name it or replace it. All three of `STV_DEFAULT`, `STV_HIDDEN` and `STV_PROTECTED` survive unnarrowed, because ELF records all three and it is the format rather than the machine that decides how many there are.

Both facts are said in the object writer by writing `st_other` rather than by choosing a scope and letting the writer underneath infer one, which is the shape of the bug in tamnd/rucc#733. A writer with one word for the binding and the visibility says something about both every time it means to say something about one, and what it said there was hidden: every global came out `STV_HIDDEN`, so a shared library built out of these objects had an empty dynamic symbol table and `dlsym` could not find a function the file plainly defines. Nothing caught it because a static link does not read the field at all. The check that catches it is one that builds a shared library and reads its dynamic symbol table, and the tests are written against `st_other` itself rather than against the reader's idea of a scope, since the reader's word is the one that was misread.

Which section each name goes in is decided the same way and in the same place. `-ffunction-sections` and `-fdata-sections`, described in section 4.7, reach the writer as one two field answer rather than as two booleans read separately by the two output paths, so the listing `-S` writes and the object `-c` writes cannot come to disagree about where a function went. The name of a split section is worked out once, beside the type that says what kind of place a variable wants, for the same reason. Nothing else about the file moves: the bytes, the symbol values within their own sections, the sizes, the bindings and the relocations are what they were, and the only thing that changes is which section header a symbol points at and, for a relocation, which section it is recorded against and how far into it. A relocation is in whichever function's bytes it fell in, which is a question only the split path has to ask, because when there is one text section every offset in it is already the offset in it. An empty `.text` still opens the file, since that is what the writer underneath starts with and what gcc leaves behind under the flag.

The three formats do not say it the same way. ELF names each section after what is in it, `.text.f` and `.rodata.x`, with the flags of the section it came out of, since splitting must not quietly change whether the page a variable lands in is writable. COFF gives every one of them the name of the section it came out of and a symbol saying which group is which, which is a COMDAT and is more than the ELF form says: the linker keeps one section out of every group naming the same symbol. That is what a Windows toolchain does with `/Gy` and what clang writes for these flags on a Windows target. Mach-O writes what it wrote before, whatever was asked for, because every Mach-O object ends with `.subsections_via_symbols` and so already tells the linker it may split a section at each symbol and drop the parts nothing reaches. Clang answers the same way there.

The listing says the same thing in text. ELF has `.hidden` and `.protected`. Mach-O has one of the two, `.private_extern`, which is a symbol that leaves this object and does not leave the library, and has no spelling of protected because the format cannot say a symbol is exported and cannot be interposed. COFF has neither, since what leaves a Windows DLL is decided by an export table the linker is handed rather than by a bit on each symbol. A `static` name gets no directive on any of them, because a name the static link has already finished with is not in anybody's dynamic table whatever the field says, and gcc writes none for one either.

## 11.4 DWARF

DWARF 5 by default, DWARF 4 under `-gdwarf-4`, written through [`gimli`](https://crates.io/crates/gimli)'s write support.

At `-O0` the obligation is complete: every function has a `DW_TAG_subprogram` with correct low and high PC and frame base; every local variable has a location valid over its whole scope; every type is described, including the C-specific cases that are easy to get wrong: bit-fields with their offsets and widths, anonymous struct and union members, flexible array members, variably-modified array types whose bounds are runtime values referencing a location expression, and function pointer types with their parameter types.

At `-O2` the obligation is best-effort and honest. A variable that lives in different registers at different points gets a location list. A variable that is dead at a point is marked as such rather than given a wrong location, because a debugger showing a stale value is worse than one saying "optimized out". Inlined functions get `DW_TAG_inlined_subroutine` with the call site's location, so a backtrace through inlined frames is correct. This is the feature that makes `-O2 -g` usable at all and it requires the inlining chain from document 08 to survive every subsequent pass.

Line tables are generated from the source locations in the IR. The rules that matter for debugger behavior: `is_stmt` marks the instruction a breakpoint should attach to; the prologue-end marker tells the debugger where to stop for a function breakpoint so that arguments are already in place; a line entry with line 0 marks compiler-generated code with no source correspondence, which is better than attributing it to an arbitrary line.

Unwind tables are separate from the rest of the debug information and are not controlled by `-g`. An unwinder is handed a return address and has to answer two questions about the function it landed in: where the frame it is standing in ends, and where the callee saved registers went. The answer is a table indexed by address, kept in `.eh_frame`, and it has to be there in an ordinary release build because C++ exceptions, `backtrace`, profilers and crash handlers all read it. Every ELF function gets a record, including the leaves that need no rows in theirs, because an unwinder that lands on an address no record covers cannot tell an undescribed function from a described one and has to stop. In the assembly listing the rows are `.cfi_` directives placed after the instruction that changed the answer, which is where the assembler wants them and which is also how the integrated path builds the section, so the two cannot disagree. `-fasynchronous-unwind-tables` is the default on x86-64 Linux and `-fno-asynchronous-unwind-tables` turns the table off for a build that knows nothing will read it, which in practice is a kernel or a freestanding image. What it saves is the section rather than any instruction, since the table describes what the prologue already did and nothing is emitted differently because it is there. Whether either request is standing is asked once, of the options, rather than worked out at each of the two places that write a table, for the reason section 11.1 gives.

In an object this compiler writes, the section holds one header and one record per function. The header carries what every function on the target starts out with, which is what keeps a record down to the handful of bytes that say what changed, and the record carries the distances between the rows. A record cannot know where the linker will put its function, so the address it covers is left at zero with a relocation in `.rela.eh_frame` and what is written is a distance from the record to the function, which is what the augmentation string `zR` in the header announces.

That is checked by `cargo xtask unwind`, which builds `tests/unwind` three ways and counts the frames a backtrace walks. Two of the three are this compiler's, the object and its listing assembled by `as`, because section 11.1 asks that those two cannot disagree, and the third is the system compiler's build of the same source. The count is compared against that rather than against a number written down here, because how deep a program's own entry is is the C library's business and differs between one and the next. Seven more answers on top of the count come from `readelf`, which is not ours, because a reader written beside the writer can hold the same wrong belief the writer does and agree with it. `cargo xtask ci` runs it beside the shared library check and skips it the same way, out loud and with the reason.

`-gsplit-dwarf` writes the bulk into a `.dwo` file and leaves a skeleton in the object, which on a large C++ project is transformative and on a large C project still meaningful. `-gz` compresses debug sections. `-fdebug-prefix-map` and `-ffile-prefix-map` rewrite paths for reproducible builds, and `SOURCE_DATE_EPOCH` is honored per document 03.

**Correctness testing** is by differential debugging: compile a corpus program with `-O0 -g` and with `-O2 -g`, run it under a scripted GDB and LLDB session that sets breakpoints and prints variables at defined points, and compare against the same script run against GCC's output. This finds the errors that a DWARF *validator* cannot, because syntactically valid DWARF can still describe the wrong thing.

## 11.5 Other metadata formats

**CTF and BTF.** The kernel generates BTF for BPF and for its own runtime type information, currently via `pahole` reading DWARF. Emitting BTF directly is not a 1.0 requirement (the kernel build's existing `pahole` step works on our DWARF if the DWARF is correct) but "our DWARF is correct enough for `pahole`" is an M11 exit criterion in document 14 and it is a strictly stronger test than a validator.

**Sanitizer metadata.** ASan needs global variable descriptors with redzones and their metadata section; UBSan needs static check descriptors with source locations. Document 12 owns their layout, which must match the runtime library's expectations exactly.

## 11.6 Linking

We invoke an external linker before 1.0, per document 04. The interesting question is whether that stays true.

**The case for an internal linker after 1.0.** The kernel's build uses linker scripts of real complexity, `--emit-relocs`, section garbage collection interacting with `KEEP`, and a two-pass link with `objtool` in between. Every one of those is a place where the external linker's behavior differs between `ld.bfd`, `lld` and `mold`, and where diagnosing a problem means understanding three linkers. Owning the linker would also close the portability story: one binary that compiles and links on all three hosts without a platform toolchain installed. And link time is a large share of a full-project build, so the throughput axis is partly gated on someone else's code.

**The case against.** A linker is a substantial project on its own; `mold` is already very fast and free; and the failure mode of a subtly wrong linker is worse than that of a subtly wrong compiler because it is harder to bisect.

The decision is deferred to document 19 and gated on a measurement: at M11, what fraction of a kernel build's wall time is linking, and how many of the bugs found during M10 and M11 were linker interaction bugs. If both numbers are high the project is justified; otherwise `mold` is the answer.

Until then the driver's obligation is to construct a correct link line per target and to pass through everything the build system asks for, which document 04 specifies and which the corpus in document 15 tests far more thoroughly than any unit test could.
