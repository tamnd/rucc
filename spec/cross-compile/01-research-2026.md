# The landscape, verified

Checked 7 September 2026. Where a version or a date appears it was read from the release notes or the repository rather than remembered, and the source is named so that the claim can be found to have gone stale.

The question this document answers: **other people ship cross compilers. What exactly do they ship, what does it cost them, and which of their techniques survive contact with a compiler that is not LLVM?**

## 1.1 `zig cc`, the thing to beat

Zig 0.16.0 shipped 14 April 2026, 244 contributors, 1,183 commits over eight months ([release notes](https://ziglang.org/download/0.16.0/release-notes.html)). It is the only self-contained cross toolchain in wide production use and it is the benchmark document 02 sets.

**What is in the box.** LLVM 21 (with loop vectorization disabled for regressions), musl 1.2.5, glibc 2.43, Linux 6.19 headers, macOS 26.4 headers, mingw-w64, FreeBSD 15.0 libc, NetBSD libc, WASI libc. Minimum OS versions: Linux 5.10, macOS 13.0, Windows 10, FreeBSD 14.0, NetBSD 10.1, OpenBSD 7.8, DragonFly 6.0.

**The four-tier support model**, which is the part worth stealing:

| tier | meaning |
|---|---|
| 1 | all non-experimental language features work; machine code without LLVM |
| 2 | stdlib accounts for it; debug info and stack traces; **libc cross-compilable**; CI on every push |
| 3 | LLVM codegen; linker produces objects and executables; not experimental to LLVM |
| 4 | assembly generation via LLVM only |

Note where "libc cross-compilable" sits: tier 2, not tier 1. Zig treats *having a sysroot for the target* as a lower bar than *generating good code for it*, which is the opposite of the intuition and is correct, the sysroot is bounded work and the backend is not.

**What 0.16 added and removed** is a map of where the effort goes. Added: native CI for `aarch64-freebsd`, `aarch64-netbsd`, `loongarch64-linux`, `powerpc64le-linux`, `s390x-linux`, `x86_64-freebsd`, `x86_64-netbsd`, `x86_64-openbsd`; initial `loongarch32-linux` (no libc, LLVM ABI unstable); `aarch64-maccatalyst` and `x86_64-maccatalyst`; basic Alpha, KVX, MicroBlaze, OpenRISC, PA-RISC and SuperH, which require GCC or an external LLVM fork and are therefore tier 4 in all but name. Removed: Solaris, AIX, z/OS, with the stated reason that **the project cannot support proprietary operating systems that make obtaining system headers unreasonably difficult**; illumos stays because it is open. That sentence is a policy, and document 04 adopts it verbatim.

Also in 0.16: a new ELF linker implementation, import library generation from `.def` files without LLVM, BE8 object files for big-endian ARM on ARMv6+, and fixes to big-endian *host* support, a reminder that "cross" has two ends and the host end is where the bugs are least expected.

0.15.1 is where the BSD work landed: FreeBSD 14+ and NetBSD 10.1+ cross compilation via stub libraries "similar to how glibc is handled", with all system and libc headers provided, plus glibc 2.42 and permission to link native glibc statically.

**The glibc trick, in detail**, because document 09 rebuilds it. From [`lib/libc/glibc/README.md`](https://github.com/ziglang/zig/blob/master/lib/libc/glibc/README.md):

- `lib/libc/glibc/abilist` is a Zig-specific *binary blob* listing every supported glibc version and the symbol set each defines, generated by the separate `ziglang/glibc-abi-tool` from upstream `.abilist` files.
- `src/glibc.zig` parses it at compile time and synthesizes stub shared objects on demand. The stubs carry symbol name, type, size and version, and no implementation. They exist only to satisfy the link; the real glibc on the target machine answers at run time.
- Alongside the stubs it builds `crti.o`, `crtn.o`, `Scrt1.o` and `libc_nonshared.a` from source, because those are statically linked into the output and cannot be stubbed.
- `libc_nonshared.a` is version-dependent in ways that bite: before glibc 2.32 it contained the `fstat()` → `__fxstat()` redirects, so the stub set and the headers have to agree about which era they are in.
- Headers live in `lib/libc/include/generic-glibc/`, one set with Zig-specific `#ifdef`s covering every supported version, hand-patched where a version introduced a feature (`reallocarray`) or changed an implementation (the `stat()` family).
- `zig cc` supports glibc back to 2.2.5; Zig itself only back to 2.17 because the stdlib needs symbols from there.
- Native glibc version detection is by `readlink` on the process's own `libc.so.6` to recover `libc-2.27.so`, falling back to probing `/usr/bin/env`.

**Where it has gone wrong** is as instructive as where it works. [ziglang/zig#3291](https://github.com/ziglang/zig/issues/3291) is the `_STAT_VER` bug: header include order let the *host's* `_STAT_VER` be picked instead of the target glibc's, so AArch64 `stat()` returned `EINVAL`. The failure mode is exactly the one that makes this class of work dangerous, no diagnostic, wrong answer at run time, on one target only.

**The unfinished half.** [`ziglang/universal-headers`](https://github.com/ziglang/universal-headers) exists because the hand-maintained multi-version header sets do not scale. Its README states the technique, near-identical files merged with preprocessor conditionals, very different files kept in per-target subdirectories and selected by an include, and the obstacle: *there is no predefined macro that distinguishes gnu from musl*, so the project has to invent its own. The endgame is parsing the `.h` files, extracting type information, computing what differs per target, and generating the merged headers, with the repository having headers as both input and output. It has been in that state for years. This is the honest state of the art on the hardest part of the problem, and document 08 treats it as such.

**Documented complaints about `zig cc`**, worth recording because document 02 promises not to inherit them:

- Flag fidelity. [ziglang/zig#16704](https://github.com/ziglang/zig/issues/16704): `-Ofast` maps to `ReleaseFast` which is `-O2`, so a build that asked for `-Ofast` silently got less. The reporter's objection is the right one, a drop-in replacement that reinterprets the flags is not one.
- Non-neutral defaults. `zig cc` passes `-fsanitize=undefined -fsanitize-trap=undefined` by default, which turns latent UB in existing C into `ud2` at run time. Real code has latent UB.
- Not a sysroot. Kelley's own framing: for a large dependency tree you want a full cross environment such as `mxe.cc` or `musl.cc`; `zig cc` is for when you do not need that. It ships a compiler and a libc, not a populated third-party tree.
- Licence ambiguity around the glibc-derived shims, raised in the Rust internals thread on bundling `zig cc` in rustup, and never fully answered.

## 1.2 GCC, and why its cross story is what it is

GCC 16.1 released 30 April 2026; 16.2 on 7 August 2026 ([gcc.gnu.org/gcc-16/changes.html](https://gcc.gnu.org/gcc-16/changes.html)). Relevant to this document:

- **LoongArch32** is new, with ilp32d (default), ilp32f and ilp32s ABIs, covering LA32 and the reduced LA32R, gated on matching binutils and glibc. Function multi-versioning via `target_clones` for LSX/LASX.
- **x86-64** gains Zen6, Wildcat Lake and Nova Lake tuning.
- **AArch64** gains a pass turning 64-bit x-register writes into w-register writes when the top half is provably zero (`-mcpu=olympus` only), FUJITSU-MONAKA FP8 features, build attributes for GCS, and packed boolean vectors for SVE predicates.
- **C23 `_BitInt` extended to RISC-V, ARM, S/390 and LoongArch**, which is a data point about how long a new fundamental type takes to reach every psABI: `_BitInt` is four years old and this is the year it became portable.

The structural fact about GCC is that **a gcc is built for one target pair**. `--target=` at configure time bakes in the assembler, the linker, the start file directories, the header directories, the multilib set and the default ISA. `aarch64-linux-gnu-gcc` and `x86_64-linux-gnu-gcc` are separate binaries with separate `libgcc` builds. This is why a distribution ships one cross-gcc package per target and why the packages are large, and it is the constraint rucc's `library.rs` and `link.rs` already refuse to accept: both of them look for directories on the machine at run time precisely because one binary has to run wherever it is copied.

The GCC multilib mechanism, `-print-multi-lib`, `-print-multi-directory`, the `MULTILIB_OPTIONS` tables, is the closest thing GCC has to a target model, and it is a string-matching scheme over flag sets. Clang's `multilib.yaml` (below) is the modern rewrite of the same idea.

## 1.3 Clang and LLVM as of 22.1

LLVM/Clang 22 branched mid-January 2026, 22.1 stable end of February ([release notes](https://releases.llvm.org/22.1.0/docs/ReleaseNotes.html)). What matters here:

- `wasm32-wasi` renamed `wasm32-wasip1`, which is a triple-normalization change in a released compiler and a reminder that the triple namespace is not stable.
- Google Native Client support removed entirely, targets do get deleted.
- RISC-V `Ssctr`/`Smctr` and Qualcomm `Xqci`/`Xqccmp` promoted out of experimental.
- x86 `-mcpu=wildcatlake`, `-mcpu=novalake`, consolidated AVX10 feature handling.
- AArch64 assembler support for Armv9.7-A, Ampere1C and the Arm C1 family; **FEAT_TME removed because Arm withdrew it**. Architectures shrink as well as grow.
- The driver now *warns* about the auto-detected GCC installation directory, silenced by `--gcc-install-dir=`. Clang's cross story still ultimately depends on finding a GCC tree, which is the dependency `zig cc` exists to remove.
- ABI break: MSVC vector deleting destructors, causing memory corruption when mixing clang 21 and clang 22 objects. An ABI change in a point release of the reference compiler, in the year we are writing this.

**`multilib.yaml`** ([clang/docs/Multilib.html](https://clang.llvm.org/docs/Multilib.html)) is the current best design for "given these flags, which sysroot directory". Its properties: YAML 1.2 with a mandatory `MultilibVersion`; a list of variants and a list of regexes that map command-line flags to matching flags; ordering significant when more than one variant matches; custom flags with `Name`/`Values`/`Default` and `MacroDefines` fed back as `-D`; default location `lib/clang-runtimes` with no target suffix so architectures can share an include directory; overridable with `--multi-lib-config=`. The active [RFC on target-triple-specific include paths](https://discourse.llvm.org/t/rfc-support-target-triple-specific-include-paths-derived-from-sysroot-via-multilib-yaml-or-driver-logic/86925) contains the argument document 12 adopts: this belongs in a data file that ships with the library set, not in driver code that has to be recompiled for a different one.

## 1.4 The triple is not a data structure

The single most useful piece of writing on this is Miguel Young de la Sota's "What the Hell Is a Target Triple?" and the discussion it produced. The facts that matter:

- LLVM's `Triple` is documented as a wrapper for autoconf configuration names, still called a triple though it has four fields: `ARCH-VENDOR-OS-ENVIRONMENT`.
- **The constructor does not normalize.** Clients that want to handle what users actually type must call `normalize()` explicitly. That split is a permanent footgun for every downstream consumer.
- Normalization gets it wrong. `thumbv7a-vita-eabihf` normalized to `thumbv7a-vita-unknown-eabihf`, Vita is an OS, and it landed in the vendor field. The Rust fix was to pick `sony` as vendor because LLVM tolerates unknown vendors.
- Apple Clang spells the architecture `arm64`; upstream spells it `aarch64`; both exist in tree because Apple and Arm upstreamed AArch64 backends independently under embargo.
- GNU `config.sub` canonicalization and LLVM canonicalization are different functions over overlapping inputs. The `target-tuples` crate exists to parse the intersection.
- Rust has an accepted MCP for `--print=llvm-target-tuple` ([compiler-team#846](https://github.com/rust-lang/compiler-team/issues/846)) purely so that `cc-rs` can ask what string to hand a C compiler. Two toolchains on the same machine cannot agree on the name of the machine.
- WG21 discussed P1864 "Defining Target Triplets" and polled in favour of describing the format in an ancillary document, while questioning whether it is WG21's business.

Conclusion for document 03: the triple is a *serialization format for user input*, not a model. rucc parses it, and stores something else.

## 1.5 Linkers

**lld** is the portable default and the one every self-contained toolchain uses. MaskRay's [April 2026 performance analysis](https://maskray.me/blog/2026-04-12-recent-lld-elf-performance-improvements) puts a 200 ms parse gap at ~35% of the 565 ms wall-clock difference to wild on `clang-relassert`, and correctly notes the comparison is not apples to apples: lld handles `__start_`/`__stop_` edges, `SHF_LINK_ORDER` dependencies and linker-script `KEEP`.

**mold** claims, on its own August 2026 benchmarks over nine large programs on a 64-core Threadripper 7980X and an M1 Ultra, 4.9× lld and 1.9× wild at the median. Its architecture coverage is the widest of the three: x86-64, i386, ARM32/64, RISC-V 32/64, PowerPC 32/64, s390x, LoongArch 32/64, SPARC64, m68k, SH-4. Relicensing to MIT happened with mold 2.0; verify before depending on it.

**wild** ([wild-linker/wild](https://github.com/wild-linker/wild)), David Lattimore's, dual MIT/Apache-2.0, written in Rust, tested on Linux x86-64, AArch64 and RISC-V only, with partial linker-script support and no LTO. Its bet is incremental linking, which nothing else offers; it does not do it yet. **Being Rust and permissively licensed makes it the only candidate rucc could ever vendor**, and being Linux-only ELF makes it useless for the cross problem today. Parent document 19's linker question should be re-read with wild in view.

For the non-ELF formats there is no choice: `lld-link` for COFF and `ld64.lld` for Mach-O, or the platform tools. Mach-O deserves its own note. Chained fixups replaced `LC_DYLD_INFO` with `LC_DYLD_CHAINED_FIXUPS` (`0x34 | LC_REQ_DYLD`) and `LC_DYLD_EXPORTS_TRIE` (`0x33 | LC_REQ_DYLD`), introduced macOS 10.15 / iOS 13, and `__DATA,__la_symbol_ptr` is gone with lazy binds folded into ordinary binds; ld64 synthesizes `__init_offsets` from `__mod_init_func` when they are on. LLD's Mach-O port initially failed against Homebrew dylibs targeting macOS 12 with "LC_DYLD_INFO_ONLY not found" until it learned to read the exports trie. Anything that only parses `LC_DYLD_INFO` is broken against every current dylib.

For COFF, ARM64EC and ARM64X are the interesting case and the work is almost entirely Jacek Caban's in `lld/COFF`. On ARM64X, ARM64 and ARM64EC inputs live in **separate symbol namespaces that cannot reference each other**, so lld carries two `SymbolTable` instances and binds each `InputFile` to one ([llvm/llvm-project#119294](https://github.com/llvm/llvm-project/pull/119294)). `-machine:arm64x` works in both MSVC-style and MinGW-style driver modes; `llvm-lib` grew dual symbol tables so one archive can serve pure ARM64, pure ARM64EC and mixed links.

## 1.6 Getting the closed platforms

**Windows/MSVC.** [`xwin`](https://github.com/Jake-Shadle/xwin) downloads and repacks the Microsoft CRT and Windows SDK into a directory usable by clang-cl and lld-link from a non-Windows host, including a symlink layer that fixes the Windows SDK's casing (`windows.h` → `Windows.h`, `kernel32.lib` → `kernel32.Lib`) for case-sensitive filesystems. Full fetch and unpack is about 27 seconds on a fast link. [`msvc-wine`](https://github.com/mstorsjo/msvc-wine) installs the real toolchain and runs it under Wine, and can also just unpack the headers and libraries for use with clang/lld in MSVC mode with nothing running under Wine. **Neither can be baked into a public image: Visual Studio is not redistributable, so each machine downloads its own copy under its own acceptance of the licence.**

**Darwin.** `osxcross` is the established path and it does not ship the SDK either, you generate the tarball yourself. The binding constraint is Xcode licence §2.5, which permits use only on Apple-branded hardware; the Apple developer forum thread on exactly this question ends with "you will have to build on a Mac" and a recommendation to talk to a lawyer. The clean-room route is hand-written `.tbd` files: they are plain YAML listing symbol names and install paths, so if you know the symbols and the install path you can write your own, and permissively licensed stub SDKs exist. `zig cc` ships headers and stubs rather than the SDK.

**Android.** The NDK bakes the API level into the driver name (`x86_64-linux-android31-clang`) and ships public stub libraries under `platforms/android-API/usr/lib`, the same stub-library technique as glibc, arrived at independently. One trap worth carrying forward: before API 35 a bug applied RELR relocations after packed relocations, so ifunc resolvers referenced by `R_*_IRELATIVE` in a packed relocation section could read not-yet-relocated globals; third-party toolchains must keep `R_*_IRELATIVE` out of packed relocation sections for compatibility below API 35.

## 1.7 glibc, musl, and the version-node problem

glibc 2.43 released 23 January 2026 ([announcement](https://lists.gnu.org/archive/html/info-gnu/2026-01/msg00005.html)). New symbol version node `GLIBC_2.43`; C23 `free_sized`, `free_aligned_sized`, `memset_explicit`, `memalignment`; `mseal`, `openat2`; CORE-MATH replacements for seven functions; Unicode 17.0; three CVEs. Experimental support for *building glibc itself with Clang 18+* on AArch64 and x86-64. **s390-linux-gnu (31-bit) deprecated in 2.43, removed in 2.44.**

The version node is the whole reason stub generation is necessary. A binary linked on a 2.43 machine acquires `GLIBC_2.43` references and will not start on 2.41, and the failure is at `execve` with no useful message. Yocto builds were already hitting this in March 2026. The stub technique inverts it: you pick the version node you want at compile time and the binary carries exactly those references, so cross compiling to an old glibc no longer needs an old machine, which is the actual user-facing value of the whole `zig cc` design and the thing document 02 must reproduce.

musl 1.2.5 is what Zig 0.16 carries. musl has no symbol versioning and is statically linkable without caveat, which makes it the *easy* target and the right first cross target for rucc: no stub generation, no version node, one `libc.a`.

## 1.8 ABI validation: the tooling exists and it finds bugs immediately

**ABI Cafe** ([faultlore.com/abi-cafe/book](https://faultlore.com/abi-cafe/book/)) is the direct prior art for parent document 12.10's call-ABI differential testing, and it is better than what that document describes. Its design: declare an interface abstractly, generate a caller and a callee in two different languages or toolchains, have both sides *report every value they saw through callbacks*, run, and diff the reports. It needs no model of what the ABI should be, it produces concrete minimized reproducers, and it is explicitly descriptive, "we're here to learn not lecture", so it will happily generate UB.

Its results are the argument for building this early. It reproduced the rustc/clang `__int128` disagreement immediately. More usefully, when gcc support was added *to establish a baseline of it working*, `gcc_calls_clang` and `clang_calls_gcc` did not work: **all three compilers disagreed on x86-64 Linux.** The reference implementations do not agree with each other. Any plan that treats "match GCC" as a well-defined target needs to know that.

Prior art beneath it: David Majnemer's 2014 LLVM dev meeting talk "Fuzzing Clang to find ABI Bugs", whose framing is the one to keep, an ABI is anything that N > 1 compilers must agree upon.

## 1.9 Verification that scales to many backends

Parent document 00 already cites Crocus (ASPLOS 2024) as the model for the verified rule set. The follow-on matters more for this document, because the cost that kills a many-target verified compiler is *writing a specification per instruction per architecture*.

**Arrival** (OOPSLA 2025, [preprint](https://cs.wellesley.edu/~avh/scaling-isa-preprint.pdf)) takes vendor-validated ISA semantics written in ASL as input, has the developer configure instruction families through a Rust library, and **generates the ISLE specifications automatically**, succinct enough to read and check in. Deriving from authoritative semantics gave it the fidelity to catch an `sdiv` bug and the coverage for industrial-scale verification. This is the difference between "we verify x86-64's rules and assert the rest" and "verification is a property of the target description".

Adjacent and relevant: **MISAAL** (PLDI 2025) generates rewrite rules offline from formal semantics of the input language, the IR and the target ISA, then does term rewriting at compile time, explicitly to avoid paying synthesis cost per compilation. The TUM work on [synthesizing instruction selection back-ends from ISA semantics](https://db.in.tum.de/~drescher/paper-isel-syn.pdf) derives selection rules from formal ISA specifications and is *IR-agnostic*, applicable to RTL, CLIF or a custom IR, no SSA required. Buchwald, Fried and Hack (CGO 2018) is the predecessor. **ACT** (arXiv 2510.09932) extends the same idea to accelerator ISAs.

Read together, the 2025 to 2026 literature says the same thing: a per-target rule set written by hand is the bottleneck, and generating it from a machine-readable ISA description with a solver in the loop is now a working technique rather than a research direction. Document 05 takes a position on how much of that rucc should attempt.

## 1.10 Emulation as the execution oracle

QEMU user mode with `binfmt_misc` runs foreign binaries transparently, translating guest syscalls to the host, across roughly 30 architectures. It is how every cross toolchain tests, and its limits are known:

- No KVM when host and guest differ, so everything goes through TCG's IR-based translation. [arXiv 2501.03427](https://arxiv.org/abs/2501.03427) argues TCG's intermediate-representation model is the performance bottleneck and can be foregone.
- The validation caveat, from the binary-translation patent literature: verifying an emulator by running compiler-generated applications through it is incomplete *because compiler-generated code covers only the subset of the ISA the compiler emits*. Passing under qemu-user validates your code's portability far more than it validates QEMU.
- Practical knobs from libunwind's cross-testing guide: `QEMU_LD_PREFIX` for the dynamic loader and runtime libraries, and a strong preference for `-static`, because testing shared libraries under QEMU is painful.
- The community heuristic for maximum ABI mismatch is a 32-bit big-endian guest (PowerPC) on a 64-bit little-endian host. Document 14 adopts it.

## 1.11 The runtime library split nobody documents

compiler-rt's builtins are a drop-in replacement for libgcc's compiler support routines and are documented as such, with hand-tuned assembly for hot conversions. The failure cases are known and narrow: **ARM32 AEABI divmod has genuinely divergent calling conventions between GCC and LLVM**, and everything else on x86-64 and AArch64 is small well-known assembly where divergence is not expected.

The trap is that **the unwinder is a separate decision that libgcc bundles**. `libgcc_s` has an integrated unwinder; compiler-rt does not, so `--rtlib=compiler-rt` leaves you needing LLVM's `libunwind` separately. Android's NDK had to make `--rtlib=compiler-rt` implicitly pass `-l:libunwind.a` because the unwinder was not exported from `libc.so`. The hard rule that falls out, and that document 10 states: **never let both `libgcc_s` and LLVM `libunwind` into one process**, because duplicate `_Unwind_*` symbols resolve unpredictably and break exception propagation across shared-library boundaries. Also: clang does not auto-link `libatomic` when using `libgcc_s`, so `__atomic_*` link errors are a configuration question, not a compiler bug.

This bears directly on rucc, whose `link.rs` currently puts `librucc_builtins.a` first and the machine's `libgcc` after it "for the parts we have not written, which today is the unwinder and its personality routine". That arrangement is correct on a native glibc host and is not portable: on a target where we ship the sysroot there may be no `libgcc` to fall back to.

## 1.12 What the architectures are doing

**RISC-V.** RVA23 ratified 21 October 2024, ratified state, no revisions permitted. Mandatory in RVA23U64: V, Zvfhmin, Zvbb, Zvkt, Zihintntl, Zicond, Zimop, Zcmop, Zcb, Zfa, and Supm pointer masking with PMLEN=0 and PMLEN=7 selectable. Zabha is a development option intended to become mandatory later. **RVA23 is the baseline for the Android RISC-V ABI**, which makes it the profile that matters commercially rather than one of several.

**x86-64.** APX and AVX10.2 are confirmed for Nova Lake in Intel's 60th ISA extensions manual, with LLVM/GCC enablement landing through 2026 (EGPR, ZU, CCMP, Push2Pop2, PPX, NDD, eNF). APX doubles the GPR file to 32 and gives integer instructions a distinct destination; Intel reports 10% fewer loads and 20% fewer stores. The psABI question is unresolved and is on the x86-64-abi list: whether x86-64-v5 inherits from v4, whether passing or returning 512-bit vectors should be a compile-time error, and whether the ABI should be changed so 512-bit vectors always travel in memory so that AVX10-256 and AVX10-512 code can interoperate. **There is an open ABI question about the current generation of x86 hardware.** Document 06 records where we sit and does not guess.

**AArch64.** Armv9.7-A in LLVM 22 assembler; FEAT_TME withdrawn and removed. Apple M3 tuning in GCC 16. GCS build attributes. The Apple divergences from AAPCS64 are already in parent document 12.3 and remain the highest-value four facts in that document.

**LoongArch.** psABI v2.x; LP64D is the only fully supported ABI and every shipping distribution uses it; the ILP32 ABIs are known incomplete, which GCC 16's LA32 work begins to change. `$r21` is reserved by the psABI and used by Linux as the percpu base (`$u0`). LSX is 128-bit, LASX 256-bit. Object-file ABI v0 → v1 migration is done, with binutils 2.40+ interlinking both.

**ppc64le / s390x.** ELFv2 is not exclusively little-endian, FreeBSD/powerpc64 uses it big-endian, and getting that consistent has been an ongoing source of lld/LTO bugs. s390x is the only realistic big-endian target with a commercial user base, and glibc is dropping 31-bit s390 in 2.44.

**CHERI.** CheriBSD ships a spatially memory-safe kernel and userspace with 10,000+ packages and default heap temporal safety, on hybrid and pure-capability ABIs. CHERIoT is purecap-only, unlike Morello which also understands bare addresses. The Rust CHERIoT port needed an upstream change so the compiler accounts for datalayout bits describing valid address spaces. **This is where "a pointer is an integer of pointer width" stops being true**, and document 03 notes what that would cost rucc's target model even though CHERI is out of scope.

**Wasm.** WASI 0.3.0 is released, ending the `0.3.0-rc-DATE` churn. `wasm32-wasip3` exists in Rust and is mid-promotion to tier 2. The LLVM change that matters: on `wasm32-wasip3`, `__stack_pointer` and `__tls_base` stop being Wasm globals and become component-model `context.get`/`context.set` builtins, with no opt-out on that target and no change to earlier targets; lld errors on `--shared-memory` with wasip3. So wasm is not one target with a version number, it is two ABIs.

## 1.13 What the evidence says to do

1. **Stub libraries are the technique.** glibc, Android and the BSDs all converged on it independently. Document 09.
2. **Headers are the unsolved part.** `universal-headers` is the state of the art and it is unfinished. Document 08 must not assume it is easy.
3. **The triple is input, not a model.** Document 03.
4. **Tiering by execution evidence, not by "it builds".** Zig's four tiers, with libc-cross at tier 2 and codegen quality at tier 1. Document 04.
5. **ABI differential testing finds real bugs on day one and the reference compilers disagree with each other.** Build the ABI Cafe equivalent before the fourth ABI, not after. Document 14.
6. **Generate the per-target rule specifications from ISA semantics or accept that verification stops at target two.** Document 05.
7. **The unwinder and the builtins are two decisions.** Document 10.
8. **Two platforms are legally closed and the honest answer is a fetch step, not a bundled tree.** Document 13.
